Zanzibar 论文在 [§5 相关工作](../../#s5)中描述了自己的渊源。它在数据模型方面引用了 Multics、UNIX、POSIX ACL、VMS 和 Taos；在角色方面引用了 RBAC；在“通过 RPC API 提供统一 ACL 存储”的思路上引用了 Amazon、Google 和 Microsoft 的 IAM 系统；把 Facebook 的 TAO 作为规模相近的系统；在一致性问题上引用了 Lamport 时钟、Spanner、Chubby 和 ZooKeeper。本页按时间顺序沿着同样的几条线索展开。

## 这些思想如何通向 Zanzibar

最早的多用户系统必须决定谁能接触什么。1966 年，Dennis 和 Van Horn 为每个计算赋予一份*能力*（capability）列表，能力是一种不可伪造的令牌，它指名一个对象并授予对它的权限（[Dennis 和 Van Horn](https://doi.org/10.1145/365230.365252)）。Lampson 1971 年的访问矩阵表明，能力和访问控制列表是存储同一张表的两种方式，分别按行或按列存储（[Lampson](https://cseweb.ucsd.edu/classes/fa01/cse221/papers/lampson-protection-osr74.pdf)）。Multics 采取了按列的视角：每个段和目录都带有一个 ACL（[Saltzer](https://dl.acm.org/doi/10.1145/361011.361067)）。Zanzibar 也站在 ACL 这一边：它回答的是“谁能接触这个对象？”。

随后，操作系统先把列表变得更廉价、更粗粒度，之后又变得更丰富。论文自己追溯了这一过程：在 UNIX 第一版中，文件标志说明 "whether owner and non-owner can read or write the file"（所有者和非所有者能否读写该文件）；到第四版，有了 "for owner, group, and others"（针对所有者、组和其他人）的读、写和执行位；POSIX ACL 增加了 "an arbitrary list of users and groups"（任意的用户和组列表）；VMS "supports ACL inheritance for files created within a directory tree"（支持对在目录树中创建的文件进行 ACL 继承）（§5）。权限、用户、组和继承这四个词，正是 Zanzibar 的数据模型着手支持的内容。

从 1970 年代起，模型逐渐脱离按对象的列表。Bell–LaPadula 和 Biba 让系统而不是所有者依据标签作出决定；Zanzibar 是自主访问控制，因此它们是对照而不是祖先。基于角色的访问控制（1992）在用户和权限之间放入了角色；论文说角色 "are similar to Zanzibar relations"（与 Zanzibar 的关系相似）（§5）。基于属性的访问控制由 NIST 2014 年的指南 SP 800-162 定义，在请求时根据属性计算决策。基于关系的访问控制由 Gates 于 2007 年命名、由 Fong 于 2011 年形式化，它根据“是……的成员”或“是……的父文件夹”这类关系作出决定，而这些关系可以组合（[Fong](https://pages.cpsc.ucalgary.ca/~pwlfong/Pub/codaspy2011.pdf)）。论文从未使用 ReBAC 这个词，但它的关系元组就构成这样一张图。

Google 的新东西在于规模和一致性。论文说，截至 2019 年 7 月论文发表时，Zanzibar "has been in production use for more than 5 years"（已在生产环境中使用超过 5 年）（§4），因此它最晚在 2014 年就已运行；没有任何公开来源给出开始的年份。它为 Calendar、Cloud、Drive、Maps、Photos 和 YouTube 提供服务（§1）。论文拿来比较的 TAO 提供 "eventual global consistency"（最终的全局一致性），而 Zanzibar 提供 "external consistency and snapshot reads with bounded staleness"（外部一致性和有界陈旧度的快照读），从而防范“new enemy”问题（§5）。Lamport 时钟被排除，因为它们 "require explicit participation of all “processes”"（需要所有“进程”显式参与），而 Zanzibar 的某些“进程”是 "external clients or even human users"（外部客户端甚至是人类用户）。Chubby 不支持 "high volumes of data, efficient range reads, or reads at a client-specified snapshot with bounded staleness"（大量数据、高效的范围读取，或在客户端指定的快照上进行有界陈旧度的读取），ZooKeeper 既不提供跨节点的外部一致性，也不提供有界陈旧度的快照读（§5）。保证来自 Spanner 及其 TrueTime 时钟（[Spanner，OSDI '12](https://www.usenix.org/system/files/conference/osdi12/osdi12-final-16.pdf)）。

论文发表之后，其他人以开源方式重建了这一设计。Ory Keto 于 2021 年围绕它进行了重写，SpiceDB、OpenFGA、Permify 和 Topaz 在之后约十八个月内相继出现。与此同时，ABAC 一脉的策略引擎 OPA 和 Cedar 日趋成熟，而 OpenID 基金会于 2023 年成立的 AuthZEN 工作组对“应用如何向授权引擎请求决策”进行了标准化：其 Authorization API 1.0 于 2026 年 1 月成为 OpenID 最终规范。各系统的细节见生态系统页面。

## Zanzibar 从何处取得了什么

论文仔细区分了“构建于某物之上”与“与某物相似”。它运行在 Spanner 和 Leopard 之上；它支持早期 ACL 系统的功能；它称 RBAC 的角色与其关系相似，称 Abadi 等人的 "blessings" 与其元组相似（§5）。

注意其中的划分。上半部分的数据模型是旧思想的重新组合；论文自己声称的贡献是统一，用元组建模 "allows us to unify the concepts of ACLs and groups"（使我们能够统一 ACL 与组的概念）（§2.1），而 Abadi 等人则把二者分开（§5）。下半部分则是让它能在 Google 的规模下工作的东西：提供 "external consistency and snapshot reads with bounded staleness"（外部一致性和有界陈旧度的快照读）的 Spanner（§5），以及 Leopard，"an indexing system used to optimize operations on large and deeply nested sets"（一个用于优化大型和深度嵌套集合上操作的索引系统）（§3），用于指针追逐无法足够快地处理的组（§3.2.4）。

<Callout kind="note" title="构建于其上的 IAM">

论文还指出，Google 的 Cloud IAM 系统 "is built as a layer on top of Zanzibar’s ACL storage and evaluation system"（构建为 Zanzibar 的 ACL 存储与评估系统之上的一层）（§5）：一个运行在关系存储之上的基于角色的产品。各种模型如何结合，见 [ACL、RBAC、ABAC、ReBAC](../access-control-models/)。

</Callout>
