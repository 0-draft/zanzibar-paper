Zanzibar 把权限存储为*关系元组*：每行一条事实，读作“该用户与该对象具有该关系”。本页其余的内容，即重写规则、Check 和 Expand，都是根据这些行计算出来的。

贯穿全站的示例：Anne、Beto 和 Chen（`user:anne`、`user:beto`、`user:chen`）；位于 `folder:A` 中的文档 `doc:readme`；组 `group:eng`。Anne 拥有 readme，Beto 属于 eng，eng 的成员可以查看 readme，Chen 可以查看文件夹 A。

## 语法

论文（§2.1）用四条规则给出了文本表示法：

```text
⟨tuple⟩   ::= ⟨object⟩ ‘#’ ⟨relation⟩ ‘@’ ⟨user⟩
⟨object⟩  ::= ⟨namespace⟩ ‘:’ ⟨object_id⟩
⟨user⟩    ::= ⟨user_id⟩ | ⟨userset⟩
⟨userset⟩ ::= ⟨object⟩ ‘#’ ⟨relation⟩
```

一个元组由三部分组成。*对象*是命名空间加一个 ID，例如 `doc:readme`。*关系*是命名空间所定义的名称，例如 `owner` 或 `viewer`。*用户*要么是单个用户 ID，要么是一个*用户集*。在论文中用户 ID 是整数；本站写作 `user:anne`，以便示例易读。

## 用户集：指向一个组的元组

语法的第四条规则最值得关注。用户集本身就是一个对象加一个关系：`group:eng#member` 表示“与 `group:eng` 具有 `member` 关系的每一个用户”。当一个元组的用户是用户集时，一行就把某种权限授予了一整组用户，而这组用户由其他行来定义。

同样的手法可以嵌套。组的成员可以是另一个用户集，例如 `group:eng#member@group:sre#member`（一个假设的子团队，不属于贯穿示例），成员关系随后会沿着元组所描述的层级一直传递下去。论文用一句话概括了这一点："a ⟨*userset*⟩ allows ACLs to refer to groups and thus supports representing nested group membership"（⟨*userset*⟩ 允许 ACL 引用组，从而支持表示嵌套的组成员关系）（§2.1）。论文也说明了这样做的好处：用元组而非按对象的 ACL 来建模 "allows us to unify the concepts of ACLs and groups"（使我们能够统一 ACL 与组的概念）（§2.1）。组只是一个对象，其 `member` 关系就是一个 ACL。

## 把表 1 画成一张图

论文的表 1 列出了四个示例元组。把用户 10 和 11 改名为 Anne 和 Beto，再为 Chen 添加一个元组，它们是：

| 元组 | 含义 |
| --- | --- |
| `doc:readme#owner@user:anne` | Anne 是 readme 的所有者 |
| `group:eng#member@user:beto` | Beto 是 eng 的成员 |
| `doc:readme#viewer@group:eng#member` | eng 的成员是 readme 的查看者 |
| `doc:readme#parent@folder:A#...` | readme 位于文件夹 A 中 |
| `folder:A#viewer@user:chen` | Chen 是文件夹 A 的查看者（不在表 1 中） |

第四行中的 `#...` 是论文的记法，表示 "a relation that does not affect the semantics of the tuple"（一个不影响元组语义的关系）（表 1 标题）：该元组指向文件夹本身，而不是指向其用户的某个集合。

## 命名空间配置

在存储元组之前，客户端要先配置一个*命名空间*，例如 `doc` 或 `folder`（§2.3）。配置列出该命名空间的关系，每个关系有一个名称和一个*关系配置*，此外还有存储参数：分片设置和对象 ID 的编码方式。

仅靠元组并不能定义有效 ACL。许多客户端希望每个编辑者同时也是查看者。为每个对象的每个编辑者额外存储一个 `viewer` 元组，用论文的话说，会 "wasteful and make it hard to make modifications across all objects"（既浪费，又使得跨所有对象的修改变得困难）（§2.3.1）。因此，关系配置可以带有一条*用户集重写规则*：一个以对象 ID 为输入、返回一棵用户集表达式树的函数。

以下是论文的图 1，原样照录：

```text
name: "doc"

relation { name: "owner" }

relation {
 name: "editor"
 userset_rewrite {
  union {
   child { _this {} }
   child { computed_userset { relation: "owner" } }
} } }

relation {
 name: "viewer"
 userset_rewrite {
  union {
   child { _this {} }
   child { computed_userset { relation: "editor" } }
   child { tuple_to_userset {
     tupleset { relation: "parent" }
     computed_userset {
       object: $TUPLE_USERSET_OBJECT  # parent folder
       relation: "viewer"
   } } }
} } }
```

> 图 1：针对文档的具有同心关系的简单命名空间配置。所有所有者都是编辑者，所有编辑者都是查看者。此外，父文件夹的查看者也是该文档的查看者。

重写树的叶节点有三种（§2.3.1）：

| 叶节点 | 返回什么 | 在图 1 中 |
| --- | --- | --- |
| `_this` | 针对该对象和关系所存储的元组中的用户，包括这些元组所指向的用户集。关系没有规则时的默认行为。 | 存储在 `doc:readme` 上的 `viewer` 元组 |
| `computed_userset` | 同一对象上另一个关系的用户集。 | 同一文档上的 `editor`；对于 `editor` 则是 `owner` |
| `tuple_to_userset` | 从对象读取一个*元组集*，再根据找到的每个元组计算出一个用户集。 | 读取文档的 `parent` 元组，然后取每个父文件夹上的 `viewer` |

叶节点通过并集、交集和排除进行组合（§2.3.1）。图 1 只用到了并集。交集要求用户属于每一个子节点，例如“同时属于 eng 的编辑者”；排除会去掉一个集合，例如“除黑名单之外的查看者”。这两个例子只是示意，并非出自论文。

## 把 Check 看作图搜索

Check 请求给出一个用户集 ⟨*object#relation*⟩ 和一个用户，询问该用户是否属于其中（§2.4.4）。不考虑重写规则时，论文把评估写成一个递归公式（§3.2.3）：如果存在元组 ⟨*object#relation@U*⟩，或者存在元组 ⟨*object#relation@U′*⟩ 且 U′ 是一个用户集、该用户属于 U′，则该用户属于 ⟨*object#relation*⟩。论文把这种递归称为“指针追逐”。重写规则 "are also translated to boolean expressions as part of check evaluation"（在检查评估过程中也会被转换为布尔表达式）（§3.2.3），因此上面的表达式树变成三个分支的 OR。

接下来四幅图要回答的问题是：Chen 能否查看 `doc:readme`？每一帧使用同一张图，并高亮当前分支所读取的边。`folder` 命名空间配置不在论文中；这些帧假定 `folder#viewer` 没有重写规则，因此它就是 `_this`。

<Callout kind="note" title="分帧展示，而非时间线">

这些帧一次只展示一个分支，以便每一帧都能单独阅读。Zanzibar 并不会这样依次等待：它 "all leaf nodes of the boolean expression tree concurrently"（并发地评估布尔表达式树的所有叶节点），并在某个节点决定了子树的结果后取消该子树其余的部分（§3.2.3）。

</Callout>

## Read 与 Expand

有两个 API 调用从不同的高度观察同一份数据。

**Read**（§2.4.1）只返回已存储的元组。请求给出一个或多个*元组集*：单个元组键，或命名空间中某个对象 ID 或某个用户集的所有元组，并可选地限定为一个关系。论文明确指出 "Read results only depend on contents of relation tuples and do not reflect userset rewrite rules"（Read 的结果仅取决于关系元组的内容，不反映用户集重写规则）（§2.4.1）。在贯穿示例中，以关系 `viewer` 读取 `doc:readme` 会返回一行：

```text
doc:readme#viewer@group:eng#member
```

虽然每个所有者都是查看者，但结果中没有 Anne；虽然 Chen 能查看 readme，结果中也没有 Chen。

**Expand**（§2.4.5）"follows indirect references expressed through userset rewrite rules"（会追踪通过用户集重写规则表达的间接引用）。它返回一棵*用户集树*：叶节点是用户 ID 或指向其他 ⟨*object#relation*⟩ 对的用户集，中间节点是并集、交集或排除。

Expand 对 `doc:readme#viewer` 返回什么？

注意这两个虚线叶节点。根据 §2.4.5，叶节点可以是指向别处的用户集，因此想得到每一个个人（Beto、Chen）的客户端需要再依次展开这些叶节点。论文没有说明单次 Expand 调用会递归多深；本图停在该文档自身规则所能到达的用户集处。论文点明了用途：Expand 让客户端能够 "reason about the complete set of users and groups that have access to their objects, which allows them to build efficient search indices for access-controlled content"（推断有权访问其对象的完整用户和组集合，从而为受访问控制的内容构建高效的搜索索引）（§2.4.5）。
