Zanzibar 是位于一组 Spanner 数据库前面的一组服务器。本页先列出各个组成部分，再跟随一次 Check 请求穿过它们，然后看数据在磁盘上如何布局。最后的数字是论文所报告的 2018 年生产环境数据。

注意，客户端与两类服务器打交道。`aclservers` 回答四种请求；`watchservers` 只以流的形式发送变更。用论文的话说，`aclservers` "are organized in clusters and respond to Check, Read, Expand, and Write requests"（以集群形式组织，响应 Check、Read、Expand 和 Write 请求），而 `watchservers` "tail the changelog and serve a stream of namespace changes to clients in near real time"（跟踪变更日志，并以近乎实时的方式向客户端提供命名空间变更流）（§3）。Leopard 是面向大型和深度嵌套组的索引，有[单独的页面](../leopard/)。

离线流水线生成 "dumps of the relation tuples in each namespace at a known snapshot timestamp"（各命名空间在某个已知快照时间戳上的关系元组转储），并对 "tuple versions older than a threshold configured per namespace"（早于按命名空间配置的阈值的元组版本）进行垃圾回收（§3）。

## 一次 Check 的逐步过程

要跟随的请求：Beto 是 readme 的查看者吗？在贯穿示例中，readme 的查看者包括 `group:eng` 的成员，而 Beto 是其中之一，因此答案是“是”。Zanzibar 必须通过读取两个对象 `doc:readme` 和 `group:eng` 才能得出这一结论。

### 请求可落在任意服务器上，再由它扇出

由哪台服务器来做这项工作？任何一台都可以接收请求，之后工作按对象分散出去。

服务器 A 并不需要负责其中任何一个对象。论文描述的正是这种形态："Requests arrive at any server in a cluster and that server fans out the work to other servers in the cluster as necessary. Those servers may in turn contact other servers to compute intermediate results. The initial server gathers the final result and returns it to the client."（请求到达集群中的任意服务器，该服务器根据需要将工作扇出到集群中的其他服务器。这些服务器又可能联系其他服务器来计算中间结果。最初的服务器汇集最终结果并将其返回给客户端。）（§3）

### 一致性哈希选出对端

A 如何知道应该就 readme 去问 B？一个集群的服务器构成一个分布式缓存："Cache entries are distributed across Zanzibar servers with consistent hashing"（缓存条目通过一致性哈希分布在 Zanzibar 服务器上）（§3.2.5）。该方案出自 [Karger 等人（STOC '97）](https://people.csail.mit.edu/karger/Papers/web.pdf)，论文将其引为 [20]。对大多数命名空间而言，转发键根据对象 ID 计算（§3.2.5）。

注意，readme 上的 `viewer` 和 `owner` 落在同一台服务器上。这正是以对象为键的意义所在："processing a check on ⟨*object#relation*⟩ often involves indirect ACL checks on other relations of the same object and reading relation tuples of the object. These checks and reads can be processed by the same server since they share the same forwarding key with the parent check request."（处理针对 ⟨*object#relation*⟩ 的检查，往往涉及对同一对象其他关系的间接 ACL 检查以及读取该对象的关系元组。由于这些检查和读取与父检查请求共享同一个转发键，它们可以由同一台服务器处理。）（§3.2.5）Karger 等人设计一致性哈希时，使得增加或移除一个缓存时，只需移动为保持负载均衡所需的最少比例的对象，这正是它适合缓存的原因。

对于热点键，论文补充说它使用 [Slicer](https://www.usenix.org/conference/osdi16/technical-sessions/presentation/adya) "to help distribute hot keys to multiple servers"（帮助把热点键分布到多台服务器上）（§3.2.5）。

调用方的缓存和被调用方的缓存叠成一棵树："To handle hot forwarding keys, we cache results at both the caller and the callee of internal RPCs, effectively forming cache trees."（为处理热点转发键，我们在内部 RPC 的调用方和被调用方都缓存结果，实际上形成了缓存树。）（§3.2.5）缓存键包含快照时间戳，而时间戳会被 "rounded up to a coarse granularity, such as one or ten seconds"（向上取整到较粗的粒度，例如 1 秒或 10 秒），从而使大多数近期请求共享缓存条目（§3.2.5）。在生产环境中，检查缓存 "a 10% hit rate on the delegate’s side"（在被委托方的命中率为 10%），在委托方为 "a 2% hit rate"（命中率为 2%）；论文指出，这些命中率看起来虽低，但 "they prevent 500K internal RPCs per second from creating hot spots"（它们防止了每秒 50 万次内部 RPC 形成热点）（§4.4）。

### 锁表合并相同的请求

缓存只有在存有答案之后才有用。如果在第一个请求完成之前就到达了许多相同的请求，它们都会未命中，并全部发往 Spanner：这就是[缓存踩踏](https://en.wikipedia.org/wiki/Cache_stampede)（论文的参考文献 [3]）。C 如何避免这种情况？

论文写道："we maintain a *lock table* on each server to track outstanding reads and checks. Among requests sharing the same cache key only one request will begin processing; the rest block until the cache is populated."（我们在每台服务器上维护一个*锁表*，用于跟踪未完成的读取和检查。在共享同一缓存键的请求中，只有一个请求会开始处理；其余请求阻塞，直到缓存被填充。）（§3.2.5）对于检查，锁表在被委托方 "an additional 12%"（额外节省了 12%），在委托方 "an additional 3%"（额外节省了 3%）（§4.4）。

后来又有两项改进（§3.2.5）。对于非常热门的对象，Zanzibar 一次性读取并缓存 ⟨*object#relation*⟩ 的*全部*元组，"trading read bandwidth for cacheability"（以读取带宽换取可缓存性）。此外，由于被取消的子检查会让其缓存键留空，它会推迟 "eager cancellation when there are waiters on the corresponding lock table entry"（在相应锁表条目上有等待者时的及早取消）。

叶节点并发执行："we evaluate all leaf nodes of the boolean expression tree concurrently. When the outcome of one node determines the result of a subtree, evaluation of other nodes in the subtree is cancelled."（我们并发地评估布尔表达式树的所有叶节点。当某个节点的结果决定了子树的结果时，子树中其他节点的评估会被取消。）（§3.2.3）它们的读取被归并："We apply a pooling mechanism to group reads for the same ACL check to minimize the number of read RPCs to Spanner."（我们采用一种池化机制，把同一 ACL 检查的读取归并在一起，以尽量减少发往 Spanner 的读取 RPC 数量。）（§3.2.3）随后 parent 元组指向 `folder:A`，`folder:A#viewer` 被转发给负责 `folder:A` 的服务器，并在那里找到 Chen。论文没有说明一个池会变成多少次 RPC；它只说到“更少”为止。

元组的布局让这件事代价很低：主键顺序 "allows us to look up all relation tuples for a given object ID or *(object ID, relation)* pair"（使我们能够查找给定对象 ID 或 *(对象 ID, 关系)* 对的所有关系元组）（§3.1.1，参见下文的[存储](#存储)）。

### 对缓慢的 Spanner 读取进行对冲

有些读取会因为与请求本身无关的原因而变慢。对于发往 Spanner 和 Leopard 的调用，Zanzibar 使用请求对冲，该方法出自 [Dean 和 Barroso 的“The Tail at Scale”（CACM，2013）](https://research.google/pubs/the-tail-at-scale/)，即论文的参考文献 [16]。第二个请求何时发出？

对冲是指 "we send the same request to multiple servers, use whichever response comes back first, and cancel the other requests"（我们把同一请求发送到多台服务器，使用最先返回的响应，并取消其他请求）（§3.2.7）。第二个请求会等待："we first send one request and defer sending hedged requests until the initial request is known to be slow"（我们先发送一个请求，并推迟发送对冲请求，直到确知初始请求较慢），延迟由一个估计 "*N*th percentile latency based on recent measurements"（基于近期测量的第 *N* 百分位延迟）的估计器设定（§3.2.7）。在生产环境中，"1% of Spanner reads, or 200K reads per second, benefit from hedging"（1% 的 Spanner 读取，即每秒 20 万次读取，从对冲中受益）（§4.4）。

<Callout kind="note" title="aclserver 之间不做对冲">
Zanzibar 不对其自身的内部调用进行对冲。各个检查的代价差别很大："Hedging check requests would result in duplicating the most expensive workloads and, ironically, worsening latency."（对冲检查请求会导致重复执行代价最高的工作负载，反而使延迟恶化。）（§3.2.7）它转而依靠副本和监控来避开缓慢的服务器。
</Callout>

### 对每个客户端加以隔离

共享服务必须防止一个客户端拖慢其他客户端。§3.2.6 列出了四种限制：

- CPU：每个 RPC 以 "generic *cpu-seconds*"（通用 *CPU 秒*）计算成本；每个客户端有一个全局 CPU 上限，"its RPCs will be throttled if it exceeds the limit *and* there is no spare capacity in the overall system"（如果它超出上限*并且*整个系统没有空闲容量，它的 RPC 将被限流）。
- 未完成的 RPC：每台服务器限制其总数，以及每个客户端的数量。
- Spanner："the maximum number of concurrent reads per *(object, client)* and per client on each Spanner server"（每台 Spanner 服务器上按 *(对象, 客户端)* 和按客户端的最大并发读取数）。
- 锁表："different lock table keys for requests from different clients"（来自不同客户端的请求使用不同的锁表键），这样 Spanner 对一个客户端的限流不会阻塞另一个客户端。

**元组数据库。** "We store relation tuples of each namespace in a separate database, where each row is identified by primary key *(shard ID, object ID, relation, user, commit timestamp)*."（我们把每个命名空间的关系元组存储在单独的数据库中，每一行由主键 *(分片 ID, 对象 ID, 关系, 用户, 提交时间戳)* 标识。）（§3.1.1）由于提交时间戳是键的一部分，旧版本保留在各自的行上，"so that we can evaluate checks and reads at any timestamp within the garbage collection window"（使我们能够在垃圾回收窗口内的任意时间戳上评估检查和读取）。贯穿示例中的元组在 `doc` 和 `group` 数据库中会是这样：

| 数据库 | 分片 ID | 对象 ID | 关系 | 用户 | 提交时间戳 |
| --- | --- | --- | --- | --- | --- |
| `doc` | *s*(readme) | `readme` | `owner` | `user:anne` | *t*₁ |
| `doc` | *s*(readme) | `readme` | `parent` | `folder:A#...` | *t*₂ |
| `doc` | *s*(readme) | `readme` | `viewer` | `group:eng#member` | *t*₃ |
| `group` | *s*(eng) | `eng` | `member` | `user:beto` | *t*₄ |

同一对象的行排在一起；论文说这种键顺序 "allows us to look up all relation tuples for a given object ID or *(object ID, relation)* pair"（使我们能够查找给定对象 ID 或 *(对象 ID, 关系)* 对的所有关系元组）。"Usually the shard ID is determined solely by the object ID"（通常分片 ID 仅由对象 ID 决定）；对于成员非常多的组，它可以 "computed from both object ID and user"（由对象 ID 和用户共同计算得出）（§3.1.1）。论文没有给出分片函数，因此上面的 *s*(…) 只是占位符，用户列的确切编码也没有描述。

**变更日志。** 所有命名空间共用一个数据库，键为 *(变更日志分片 ID, 时间戳, 唯一更新 ID)*，"where a changelog shard is randomly selected for each write"（其中每次写入随机选择一个变更日志分片）（§3.1.2）。

**命名空间配置。** 一个数据库，包含两张表：配置表 "keyed by namespace IDs"（以命名空间 ID 为键），以及 "a changelog of config updates"（配置更新的变更日志），后者 "keyed by commit timestamps"（以提交时间戳为键）。服务器在启动时加载所有配置，然后持续跟随该变更日志（§3.1.3）。

**复制。** "Replicas exist in dozens of locations around the world, with multiple replicas per region. The 5 voting replicas are in eastern and central United States, in 3 different metropolitan areas to isolate failures but within 25 milliseconds of each other so that Paxos transactions commit quickly."（副本分布在全球数十个地点，每个区域有多个副本。5 个投票副本位于美国东部和中部，分布在 3 个不同的大都市区以隔离故障，但彼此之间的距离在 25 毫秒以内，从而使 Paxos 事务能够快速提交。）（§3.1.4）Spanner 本身见 [Corbett 等人（OSDI '12）](https://www.usenix.org/system/files/conference/osdi12/osdi12-final-16.pdf)，即论文的参考文献 [15]。

## 运行数据

论文 §4 报告了以下数字。按 API 统计的峰值和延迟来自 2018 年 12 月的 7 天期间（§4、§4.2）；其他数字论文没有对应到明确的时间段。每个单元格均按原文引用。

| 项目 | 论文原文 | § |
| --- | --- | --- |

| 命名空间 | "more than 1,500 namespaces defined by hundreds of client applications"（由数百个客户端应用定义的 1,500 多个命名空间） | 4 |
| 元组 | "more than 2 trillion relation tuples that occupy close to 100 terabytes"（超过 2 万亿条关系元组，占用近 100 TB） | 4 |
| 复制 | "fully replicated in more than 30 locations around the world"（在全球 30 多个地点完整复制） | 4 |

| 服务器 | "more than 10,000 servers organized in several dozen clusters around the world"（超过 10,000 台服务器，组织成分布在全球的几十个集群） | 4 |

| 缓存查找 | "approximately 200 million lookups per second at peak, 150 million from checks and 50 million from reads"（峰值时每秒约 2 亿次查找，其中 1.5 亿次来自检查，5000 万次来自读取） | 4.4 |
