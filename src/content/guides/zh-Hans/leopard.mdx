Zanzibar 通常通过从对象到用户、一次一个查找地沿着元组前进来回答 Check。对于大多数数据，这很快。对于嵌套了许多层的组则不然，Zanzibar 把这些检查交给 Leopard，一个预先计算嵌套关系的索引。

## 嵌套为何慢

扩展贯穿示例。`group:eng` 现在位于 `group:product` 之中，`group:product` 又位于 `group:all` 之中，而 readme 共享给了整个 `group:all`。要得知 Beto 能查看 readme，需要多少次查找？

图背后的元组是：

```text
doc:readme#viewer@group:all#member
group:all#member@group:product#member
group:product#member@group:eng#member
group:eng#member@user:beto
```

注意，第 *n* 步要等第 *n* − 1 步返回后才能开始。论文称之为指针追逐，并说它 "can be expensive when indirect ACLs or groups are deep or wide"（当间接 ACL 或组很深或很宽时代价可能很高）（§3.2.3）。宽也同样有害：如果 `group:all` 有一百个子组，第 2 步就会分出一百个分支。因此："Recursive pointer chasing during check evaluation has difficulty maintaining low latency with groups that are deeply nested or have a large number of child groups. For selected namespaces that exhibit such structure, Zanzibar handles checks using Leopard, a specialized index that supports efficient set computation."（对于深度嵌套或拥有大量子组的组，检查评估过程中的递归指针追逐难以保持低延迟。对于呈现此类结构的选定命名空间，Zanzibar 使用 Leopard 来处理检查。Leopard 是一种支持高效集合计算的专用索引。）（§3.2.4）

## 两种集合

Leopard 存储 "a collection of named sets using `(T, s, e)` tuples, where *T* is an enum representing the set type and *s* and *e* are 64-bit integers representing the set ID and the element ID"（一组以 `(T, s, e)` 元组表示的具名集合，其中 *T* 是表示集合类型的枚举，*s* 和 *e* 是表示集合 ID 和元素 ID 的 64 位整数）（§3.2.4）。组成员关系使用两种集合类型：

- `GROUP2GROUP(s)`：作为祖先组 *s* 的 "*directly or indirectly*"（*直接或间接*）子组的那些组。
- `MEMBER2GROUP(s)`：用户 *s* 作为 "*direct*"（*直接*）成员所在的那些组。

## 成员关系即非空交集

"To evaluate whether user *U* is a member of group *G*, we check whether"（为评估用户 *U* 是否是组 *G* 的成员，我们检查是否满足）（§3.2.4）

```text
(MEMBER2GROUP(U) ∩ GROUP2GROUP(G)) ≠ ∅
```

也就是说：用户被直接加入的组中，是否有任何一个也位于 *G* 之下？对于 Beto 和 Anne 相对于 `group:all`，这会得到什么？

## 在有序列表上求交

求交有多便宜？"Index tuples are stored as ordered lists of integers in a structure such as a skip list, thus allowing for efficient union and intersections among sets. For example, evaluating the intersection between two sets, *A* and *B*, requires only O(min(|A|, |B|)) skip-list seeks."（索引元组以有序整数列表的形式存储在跳表之类的结构中，从而支持集合之间高效的并集和交集运算。例如，求两个集合 *A* 和 *B* 的交集只需 O(min(|A|, |B|)) 次跳表查找。）（§3.2.4）

## 三个部分

"The Leopard system consists of three discrete parts: a serving system capable of consistent and low-latency operations across sets; an offline, periodic index building system; and an online real-time layer capable of continuously updating the serving system as tuple changes occur."（Leopard 系统由三个独立部分组成：一个能够在集合之上进行一致、低延迟操作的服务系统；一个离线的周期性索引构建系统；以及一个在线实时层，能够在元组发生变化时持续更新服务系统。）（§3.2.4）它们如何连接？

- **离线索引构建器。** 它 "generates index shards from a snapshot of Zanzibar relation tuples and configs, and replicates the shards globally. It respects userset rewrite rules and recursively expands edges in an ACL graph to form Leopard index tuples."（根据 Zanzibar 关系元组和配置的快照生成索引分片，并在全球范围内复制这些分片。它遵循用户集重写规则，递归地展开 ACL 图中的边，以形成 Leopard 索引元组。）服务器 "swap old shards with new ones when they become available"（在新分片可用时用其替换旧分片）。
- **增量层。** 仅靠离线索引 "cannot do so at a fresh and consistent snapshot"（无法在新鲜且一致的快照上做到这一点），因此服务器维护 "an incremental layer that indexes all updates since the offline snapshot"（一个增量层，对自离线快照以来的所有更新进行索引），每个更新是一个 `(T, s, e, t, d)` 元组，"where *t* is the timestamp of the update and *d* is a deletion marker"（其中 *t* 是更新的时间戳，*d* 是删除标记）。"Updates with timestamps less than or equal to the query timestamp are merged on top of the offline index during query processing."（在查询处理过程中，时间戳小于或等于查询时间戳的更新会被合并到离线索引之上。）
- **馈送。** "the Leopard incremental indexer calls Zanzibar’s Watch API to receive a temporally ordered stream of Zanzibar tuple modifications and transforms the updates into a temporally ordered stream of Leopard tuple additions, updates, and deletions."（Leopard 增量索引器调用 Zanzibar 的 Watch API，接收按时间排序的 Zanzibar 元组修改流，并把这些更新转换为按时间排序的 Leopard 元组添加、更新和删除流。）

此列表中的所有引文均出自 §3.2.4。由于更新带有时间戳，并且只合并到查询时间戳为止，Leopard 的答案可以反映与 Check 其余部分相同的快照；论文所陈述的增量层的目的是 "To support consistent ACL evaluation"（为了支持一致的 ACL 评估）。

数量等于一侧的祖先数乘以另一侧的后代数，因此它随深度和宽度同时增长。为了计算它，"Generating updates for the GROUP2GROUP tuples requires the incremental indexer to maintain group-to-group membership for denormalizing the effects of a relation tuple update to potentially multiple index updates."（为 GROUP2GROUP 元组生成更新，要求增量索引器维护组到组的成员关系，以便把一次关系元组更新的影响反规范化为可能多次的索引更新。）在 Google 的规模下："In practice, a single Zanzibar tuple addition or deletion may yield potentially tens of thousands of discrete Leopard tuple events."（实际上，单个 Zanzibar 元组的添加或删除可能产生多达数万个离散的 Leopard 元组事件。）（§3.2.4）

删除比图中更微妙：只有当没有其他路径仍然连接两个组时，才能移除一个索引元组。论文没有描述索引器如何判断这一点。

这也是 Leopard 是例外的原因。在其他地方，"Zanzibar avoids storage denormalization and relies only on normalized data (except for the cases described in §3.2.4)"（Zanzibar 避免存储反规范化，只依赖规范化数据，§3.2.4 中描述的情况除外）（§3.2.5），而 Leopard 只用于 "that exhibit such structure"（呈现此类结构的）选定命名空间（§3.2.4）。

## 生产环境中

§4.4 给出了 7 天内的数据："The Leopard index is performing 1.56M QPS at the median, or 2.22M QPS at the 99th percentile"（Leopard 索引的中位数为 156 万 QPS，第 99 百分位为 222 万 QPS），以及 "Leopard servers respond in fewer than 150 μsec at the median, or under 1 msec at the 99th percentile."（Leopard 服务器的响应时间中位数不到 150 微秒，第 99 百分位不到 1 毫秒。）增量层 "writes roughly 500 index updates per second at the median, and approximately 1.5K updates per second at the 99th percentile."（中位数约每秒写入 500 次索引更新，第 99 百分位约每秒 1,500 次。）对 Leopard 的调用与对 Spanner 的调用一样会进行对冲（§3.2.7）。
