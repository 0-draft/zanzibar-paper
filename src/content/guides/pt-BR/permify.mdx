O Permify é um serviço de autorização escrito em Go. Sua documentação o chama de "an open-source authorization service for creating fine-grained and scalable authorization systems" (um serviço de autorização de código aberto para criar sistemas de autorização granulares e escaláveis), "inspired by Google's consistent, global authorization system, Google Zanzibar" (inspirado no sistema de autorização global e consistente do Google, o Google Zanzibar) ([documentação do Permify](https://fusionauth.io/permify-docs)). Você descreve os tipos de entidade e suas relações no Permify Schema, escreve os relacionamentos como tuplas e pergunta a um servidor, por gRPC ou HTTP, se um sujeito tem uma permissão.

A aquisição do Permify pela FusionAuth foi anunciada em 2025-11-20 ([anúncio do Permify](https://permify.co/post/fusionauth-acquires-permify/), [anúncio da FusionAuth](https://fusionauth.io/blog/fusionauth-acquires-permify)). A FusionAuth agora chama o produto de "FusionAuth FGA by Permify" ([publicação de suporte da FusionAuth](https://fusionauth.io/blog/how-to-get-support-for-fusionauth-fga-permify)), e a documentação fica em [fusionauth.io/permify-docs](https://fusionauth.io/permify-docs). A publicação do Permify afirma que "The core Permify project remains open source and will continue to live on GitHub." (O projeto central do Permify continua de código aberto e seguirá no GitHub.)

## O artigo e o Permify lado a lado

Cada linha nomeia um conceito do artigo e o que o Permify documenta de mais próximo. Onde o Permify não tem nada comparável, a célula diz isso.

| No artigo | No Permify |
| --- | --- |
| Configuração de namespace (§2.3) | Um bloco `entity` no Permify Schema, com `relation`, `permission` (ou seu sinônimo `action`), `attribute` e `rule` ([modelagem](https://fusionauth.io/permify-docs/getting-started/modeling)) |
| Tupla de relação `object#relation@user` (§2.1) | Tupla relacional `entity#relation@subject`, por exemplo `doc:readme#owner@user:anne` ([armazenamento de dados](https://fusionauth.io/permify-docs/getting-started/sync-data)) |
| `_this` | As tuplas armazenadas de uma `relation`; uma permissão as inclui ao nomear a relação |
| `computed_userset` | Nomear outra relação ou permissão da mesma entidade, como `edit` dentro de `view = viewer or edit` |
| `tuple_to_userset` | Travessia com ponto por meio de uma relação, como `parent.view` |
| União, interseção, exclusão | `or`, `and`, `not` |
| Zookie (§2.2, §2.4) | Snap token, o campo `snap_token` ([snap tokens](https://fusionauth.io/permify-docs/operations/snap-tokens)) |
| Check (§2.4.4) | `Permission.Check`, além de `BulkCheck` ([service.proto](https://github.com/Permify/permify/blob/master/proto/base/v1/service.proto)) |
| Read (§2.4.1) | `Data.ReadRelationships`, além de `ReadAttributes` |
| Write (§2.4.2) | `Data.Write`, `WriteRelationships`, `Delete`, `DeleteRelationships` |
| Watch (§2.4.3) | `Watch.Watch`, um stream do servidor ([operações de Watch](https://fusionauth.io/permify-docs/operations/watch)) |
| Expand (§2.4.5) | `Permission.Expand` |
| Leopard (§3.2.4) | Nenhum equivalente documentado |
| Spanner (§3.1) | PostgreSQL, ou um mecanismo em memória (o padrão da configuração) ([configuração](https://fusionauth.io/permify-docs/setting-up/configuration)) |

O Permify também tem chamadas de consulta que o artigo não descreve: `LookupEntity`, `LookupSubject` e `SubjectPermission`.

## O exemplo recorrente no Permify Schema

A Figura 1 do artigo dá aos documentos três relações concêntricas: donos são editores, editores são visualizadores, e os visualizadores da pasta pai são visualizadores do documento (§2.3.1). Eis esse modelo com os tipos do exemplo recorrente, no Permify Schema.

```text
entity user {}

entity group {
    relation member @user
}

entity folder {
    relation viewer @user @group#member

    permission view = viewer
}

entity doc {
    relation parent @folder
    relation owner @user
    relation editor @user @group#member
    relation viewer @user @group#member

    permission edit = owner or editor
    permission view = viewer or edit or parent.view
}
```

`@group#member` permite que uma relação contenha um userset: “todos que são membros deste grupo”. `parent.view` segue a relação `parent` até a pasta e avalia ali a permissão `view` da pasta; a documentação afirma que "The same traversal rule applies to both `relation.userset` and `relation.permission`" (a mesma regra de travessia se aplica tanto a `relation.userset` quanto a `relation.permission`) ([modelagem](https://fusionauth.io/permify-docs/getting-started/modeling)).

O exemplo recorrente tem cinco tuplas:

```text
doc:readme#owner@user:anne
group:eng#member@user:beto
doc:readme#viewer@group:eng#member

```

## Arquitetura

Como os servidores do Permify dividem o trabalho, e onde ficam as tuplas?

As peças, cada uma segundo a documentação:

- Os servidores escutam, por padrão, na porta HTTP 3476 e na porta gRPC 3478 ([configuração](https://fusionauth.io/permify-docs/setting-up/configuration)). A seção do banco de dados aceita URIs separadas de `writer` e `reader`.
- Cada pod mantém um cache [Ristretto](https://github.com/dgraph-io/ristretto) local ao processo com resultados de verificações; "there is no shared cache layer" (não há camada de cache compartilhada) ([cache](https://fusionauth.io/permify-docs/operations/cache)).
- Com `distributed.enabled`, os pods mapeiam cada requisição, por hash, em um anel de hashing consistente, de modo que "subsequent API calls with the same hash will retrieve the response from the instance 2, regardless of which instance that API called from" (chamadas de API subsequentes com o mesmo hash obterão a resposta da instância 2, independentemente da instância em que a API foi chamada). Um circuit breaker interrompe as chamadas ao banco de dados enquanto ele está indisponível.
- O PostgreSQL armazena as tuplas com MVCC: o Permify cria "a separate database snapshot for each write and delete operation" (um snapshot de banco de dados separado para cada operação de escrita e de exclusão), e um coletor de lixo opcional apaga as versões antigas.
- Cada stream de Watch "opens a long-lived connection with a continuous polling loop against the database" (abre uma conexão de longa duração com um laço contínuo de consulta ao banco de dados) ([operações de Watch](https://fusionauth.io/permify-docs/operations/watch)).

## Consistência

O snap token do Permify desempenha o papel do zookie. Um Write o retorna; o cliente o armazena junto com o recurso e o envia de volta como `snap_token` em verificações posteriores. A documentação o descreve como "a token that consists of an encoded timestamp" (um token que consiste em um timestamp codificado), comparado nas verificações de acesso "to ensure that the snapshot of the access control is at least as fresh as the resource timestamp" (para garantir que o snapshot do controle de acesso seja pelo menos tão atual quanto o timestamp do recurso) ([snap tokens](https://fusionauth.io/permify-docs/operations/snap-tokens)). Essa é a garantia do artigo para uma verificação que carrega um zookie: "a consistent snapshot no earlier than" (um snapshot consistente não anterior a) o zookie fornecido (§2.4.4).

Observe o comportamento sem token. O artigo permite que o Zanzibar "choose a reasonably recent snapshot, possibly offering a lower-latency response" (escolha um snapshot razoavelmente recente, possivelmente oferecendo uma resposta de menor latência) (§2.4.1). O Permify, por sua vez, lê o ID da transação mais recente em sua tabela `transactions` e avalia nesse snapshot; o resultado é armazenado em cache sob uma chave que contém esse ID ([snap tokens](https://fusionauth.io/permify-docs/operations/snap-tokens)). A chave de cache é `check_{tenant_id}_{schema_version}:{snapshot_token}:{check_request}` ([cache](https://fusionauth.io/permify-docs/operations/cache)), de modo que uma nova escrita produz novas chaves em vez de invalidar as antigas.

## Diferenças em relação ao artigo

- **Atributos e regras.** O Permify Schema acrescenta `attribute` e `rule` para verificações baseadas em atributos, como `permission view = check_ip_range(ip_range) or admin` ([modelagem](https://fusionauth.io/permify-docs/getting-started/modeling)). As reescritas do Zanzibar operam apenas sobre tuplas (§2.3.1).
- **Tuplas contextuais.** Relações "dynamically added to permission request operations" (adicionadas dinamicamente às operações de requisição de permissão) são avaliadas junto com as armazenadas e nunca são escritas ([tuplas contextuais](https://fusionauth.io/permify-docs/operations/contextual-tuples)).
- **Tenants.** Um serviço `Tenancy` cria, lista e apaga tenants ([service.proto](https://github.com/Permify/permify/blob/master/proto/base/v1/service.proto)); o artigo não tem o conceito de tenant.
- **Armazenamento.** PostgreSQL com snapshots MVCC, em vez do Spanner, cujo mecanismo TrueTime atribui um timestamp a cada escrita de ACL (§2.2, §3.1). O cache distribuído funciona "across availability zones (within an AWS region)" (entre zonas de disponibilidade, dentro de uma região da AWS) ([cache](https://fusionauth.io/permify-docs/operations/cache)).
- **Sem índice desnormalizado.** O artigo responde a verificações de grupos profundamente aninhados com o Leopard (§3.2.4). O Permify documenta cache de resultados e hashing consistente, não um índice de conjuntos.
- **Consultas.** `LookupEntity` e `LookupSubject` respondem a perguntas do tipo “quais recursos” e “quais sujeitos”, que a API do artigo não cobre.
