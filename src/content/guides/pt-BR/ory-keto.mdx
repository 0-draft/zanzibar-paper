O Ory Keto é um servidor de permissões escrito em Go pela Ory Corp. Seu README o chama de "an open source implementation of 'Zanzibar: Google's Consistent, Global Authorization System'" (uma implementação de código aberto de “Zanzibar: Google's Consistent, Global Authorization System”) ([README](https://github.com/ory/keto)). A Ory também o opera como serviço gerenciado: "Ory Permissions is powered by the open source Ory Keto" (o Ory Permissions é movido pelo Ory Keto de código aberto) na Ory Network (mesmo README).

O Keto não começou como um sistema Zanzibar. O projeto do Zanzibar chegou na v0.6.0-alpha.1, em 2021-04-07; as notas de versão dizem que o Keto anterior foi movido para um branch `legacy-0.5` e que "the architectures are vastly different" (as arquiteturas são muito diferentes) ([notas de versão](https://github.com/ory/keto/releases/tag/v0.6.0-alpha.1)). As reescritas de userset, escritas na Ory Permission Language, vieram na v0.10.0-alpha.0, em 2022-09-27 ([notas de versão](https://github.com/ory/keto/releases/tag/v0.10.0-alpha.0)).

## O artigo e o Keto lado a lado

| No artigo | No Ory Keto |
| --- | --- |
| Configuração de namespace (§2.3) | Uma `class` que `implements Namespace` na Ory Permission Language (OPL), um subconjunto de TypeScript ([referência da OPL](https://www.ory.com/docs/keto/reference/ory-permission-language)) |
| Tupla de relação `object#relation@user` (§2.1) | `namespace:object#relation@subject`, por exemplo `Group:eng#members@User:beto` ([tuplas de relação](https://www.ory.com/docs/keto/concepts/relation-tuples), [parser](https://github.com/ory/keto/blob/master/ketoapi/enc_string.go)) |
| `_this` | `this.related.viewers.includes(ctx.subject)` |
| `computed_userset` | `this.permits.edit(ctx)`: "A permission can call another permission defined on the same namespace" (uma permissão pode chamar outra permissão definida no mesmo namespace) |
| `tuple_to_userset` | `this.related.parents.traverse((p) => p.permits.view(ctx))` |
| União, interseção, exclusão | `\|\|`, `&&`, `!` |
| Zookie (§2.2, §2.4) | Existem campos `snaptoken` na API, mas cada um é "not implemented yet and has no effect" (ainda não implementado e sem efeito) ([check_service.proto](https://github.com/ory/keto/blob/master/proto/ory/keto/relation_tuples/v1alpha2/check_service.proto)) |
| Check (§2.4.4) | `CheckService.Check`, `BatchCheck` |
| Read (§2.4.1) | `ReadService.ListRelationTuples` ([read_service.proto](https://github.com/ory/keto/blob/master/proto/ory/keto/relation_tuples/v1alpha2/read_service.proto)) |
| Write (§2.4.2) | `WriteService.TransactRelationTuples`, `DeleteRelationTuples` ([write_service.proto](https://github.com/ory/keto/blob/master/proto/ory/keto/relation_tuples/v1alpha2/write_service.proto)) |
| Watch (§2.4.3) | Nenhum na API |
| Expand (§2.4.5) | `ExpandService.Expand` ([expand_service.proto](https://github.com/ory/keto/blob/master/proto/ory/keto/relation_tuples/v1alpha2/expand_service.proto)) |
| Leopard (§3.2.4) | Nenhum equivalente documentado |
| Spanner (§3.1) | PostgreSQL, MySQL ou CockroachDB; SQLite apenas para desenvolvimento ([guia de produção](https://www.ory.com/docs/keto/guides/production)) |

## O exemplo em curso em OPL

A Figura 1 do artigo torna os donos editores, os editores visualizadores, e os visualizadores da pasta pai visualizadores do documento (§2.3.1). Em OPL, cada namespace é uma classe: `related` declara as relações e os tipos de sujeito que elas aceitam, e `permits` contém funções que retornam verdadeiro ou falso para `ctx.subject`.

```ts
import { Namespace, SubjectSet, Context } from "@ory/keto-namespace-types"

class User implements Namespace {}

class Group implements Namespace {
  related: {
    members: User[]
  }
}

class Folder implements Namespace {
  related: {
    viewers: (User | SubjectSet<Group, "members">)[]
  }

  permits = {
    view: (ctx: Context): boolean => this.related.viewers.includes(ctx.subject),
  }
}

class Doc implements Namespace {
  related: {
    parents: Folder[]
    owners: User[]
    editors: (User | SubjectSet<Group, "members">)[]
    viewers: (User | SubjectSet<Group, "members">)[]
  }

  permits = {
    edit: (ctx: Context): boolean =>
      this.related.owners.includes(ctx.subject) ||
      this.related.editors.includes(ctx.subject),

    view: (ctx: Context): boolean =>
      this.related.viewers.includes(ctx.subject) ||
      this.permits.edit(ctx) ||
      this.related.parents.traverse((p) => p.permits.view(ctx)),
  }
}
```

`SubjectSet<Group, "members">` é o tipo da OPL para “os membros de um grupo”, o userset do artigo. As relações são sempre arrays porque "an object can have many subjects" (um objeto pode ter muitos sujeitos) ([referência da OPL](https://www.ory.com/docs/keto/reference/ory-permission-language)).

As cinco tuplas do exemplo em curso, na forma textual do Keto. Um sujeito escrito como `User:anne` é um subject set com relação vazia; as tuplas de exemplo dos mantenedores escrevem os usuários dessa forma ([tuples.json](https://github.com/ory/keto/blob/master/contrib/rewrites-example/relation-tuples/tuples.json)).

```text
Doc:readme#owners@User:anne
Group:eng#members@User:beto
Doc:readme#viewers@Group:eng#members
Doc:readme#parents@Folder:A
Folder:A#viewers@User:chen
```

- Cada contêiner serve uma Read API (porta padrão 4466), uma Write API (4467) e uma API de sintaxe da OPL (4469), cada uma por HTTP e gRPC ([schema de configuração](https://github.com/ory/keto/blob/master/embedx/config.schema.json)).
- "A good practice is to not expose the Write API at all to the public internet" (uma boa prática é não expor de forma alguma a Write API à internet pública), e "The Read API should also be protected" (a Read API também deve ser protegida) ([guia de produção](https://www.ory.com/docs/keto/guides/production)).
- Escalabilidade: "There are no additional requirements for scaling when self-hosting Ory Keto, just spin up another container!" (não há requisitos adicionais para escalar ao hospedar o Ory Keto por conta própria; basta subir outro contêiner!) (mesmo guia). Os contêineres compartilham o banco de dados.

## Consistência

O zookie do artigo permite que um cliente peça uma verificação "at a consistent snapshot no earlier than the given zookie" (em um snapshot consistente não anterior ao zookie fornecido) (§2.4.4). A API protobuf do Keto carrega a mesma ideia nos nomes de seus campos: `snaptoken` em Check, Expand e ListRelationTuples, `snaptokens` em TransactRelationTuples, e uma flag `latest` para uma verificação de alteração de conteúdo. Cada um desses campos está documentado como "not implemented yet and has no effect" (ainda não implementado e sem efeito) ([check_service.proto](https://github.com/ory/keto/blob/master/proto/ory/keto/relation_tuples/v1alpha2/check_service.proto)).

## Diferenças em relação ao artigo

- **Sem zookies.** Os campos existem; o comportamento não (ver acima).
- **Sem Watch.** A API v1alpha2 tem os serviços Check, Expand, Read, Write, Namespaces e Version, e um serviço separado de sintaxe da OPL (`opl/v1alpha1`), mas nenhum stream de alterações ([diretório proto](https://github.com/ory/keto/tree/master/proto/ory/keto)). O Watch do artigo alimenta índices secundários e o Leopard (§2.4.3, §3.2.4).
- **Sem Leopard.** Nenhum índice de conjuntos desnormalizado está documentado.
- **Uma sintaxe de linguagem de programação.** A OPL é um subconjunto de TypeScript para que "users can get context help from their IDE" (os usuários possam obter ajuda contextual de sua IDE) ([especificação da OPL](https://github.com/ory/keto/blob/master/docs/ory_permission_language_spec.md)). A Figura 1 do artigo escreve uma configuração em uma sintaxe textual no estilo de protocol buffers (§2.3.1); o artigo não nomeia o formato.
- **Armazenamento em SQL.** Um único banco de dados SQL compartilhado em vez do Spanner (§3.1).
- **Profundidade do Check.** As requisições de Check carregam um `max_depth`, "The maximum depth to search for a relation" (a profundidade máxima da busca por uma relação) ([check_service.proto](https://github.com/ory/keto/blob/master/proto/ory/keto/relation_tuples/v1alpha2/check_service.proto)).
