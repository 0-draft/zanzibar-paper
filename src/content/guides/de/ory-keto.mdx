Ory Keto ist ein in Go geschriebener Berechtigungsserver von Ory Corp. Sein README nennt ihn "an open source implementation of 'Zanzibar: Google's Consistent, Global Authorization System'" (eine Open-Source-Implementierung von „Zanzibar: Google's Consistent, Global Authorization System“) ([README](https://github.com/ory/keto)). Ory betreibt ihn auch als verwalteten Dienst: "Ory Permissions is powered by the open source Ory Keto" (Ory Permissions basiert auf dem Open-Source-Projekt Ory Keto) im Ory Network (dasselbe README).

Keto begann nicht als Zanzibar-System. Das Zanzibar-Design kam mit v0.6.0-alpha.1 am 2021-04-07; die Release Notes sagen, dass das frühere Keto in einen Branch `legacy-0.5` verschoben wurde und dass "the architectures are vastly different" (die Architekturen sich grundlegend unterscheiden) ([Release Notes](https://github.com/ory/keto/releases/tag/v0.6.0-alpha.1)). Userset-Umschreibungen, geschrieben in der Ory Permission Language, folgten mit v0.10.0-alpha.0 am 2022-09-27 ([Release Notes](https://github.com/ory/keto/releases/tag/v0.10.0-alpha.0)).

## Das durchgehende Beispiel in OPL

Abbildung 1 des Papers macht Eigentümer zu Bearbeitern, Bearbeiter zu Betrachtern und Betrachter des übergeordneten Ordners zu Betrachtern des Dokuments (§2.3.1). In OPL ist jeder Namespace eine Klasse: `related` deklariert die Relationen und die Subjekttypen, die sie akzeptieren, und `permits` enthält Funktionen, die für `ctx.subject` true oder false zurückgeben.

```ts
import { Namespace, SubjectSet, Context } from "@ory/keto-namespace-types"

class User implements Namespace {}

class Group implements Namespace {
  related: {
    members: User[]
  }
}

class Folder implements Namespace {
  related: {
    viewers: (User | SubjectSet<Group, "members">)[]
  }

  permits = {
    view: (ctx: Context): boolean => this.related.viewers.includes(ctx.subject),
  }
}

class Doc implements Namespace {
  related: {
    parents: Folder[]
    owners: User[]
    editors: (User | SubjectSet<Group, "members">)[]
    viewers: (User | SubjectSet<Group, "members">)[]
  }

  permits = {
    edit: (ctx: Context): boolean =>
      this.related.owners.includes(ctx.subject) ||
      this.related.editors.includes(ctx.subject),

    view: (ctx: Context): boolean =>
      this.related.viewers.includes(ctx.subject) ||
      this.permits.edit(ctx) ||
      this.related.parents.traverse((p) => p.permits.view(ctx)),
  }
}
```

`SubjectSet<Group, "members">` ist der OPL-Typ für „die Mitglieder einer Gruppe“, das Userset des Papers. Relationen sind immer Arrays, weil "an object can have many subjects" (ein Objekt viele Subjekte haben kann) ([OPL-Referenz](https://www.ory.com/docs/keto/reference/ory-permission-language)).

<Callout title="Gegen die Dokumentation geprüft, nicht ausgeführt">
Diese Konfiguration folgt der dokumentierten Syntax mit Stand 2026-11-13: der [OPL-Referenz](https://www.ory.com/docs/keto/reference/ory-permission-language), der [OPL-Spezifikation](https://github.com/ory/keto/blob/master/docs/ory_permission_language_spec.md) im Repository und der Beispieldatei [namespaces.keto.ts](https://github.com/ory/keto/blob/master/contrib/rewrites-example/namespaces.keto.ts) der Maintainer. Sie wurde nicht in Keto geladen.
</Callout>

Die fünf Tupel des durchgehenden Beispiels in der Textform von Keto. Ein als `User:anne` geschriebenes Subjekt ist ein Subject Set mit leerer Relation; die Beispieltupel der Maintainer schreiben Benutzer auf diese Weise ([tuples.json](https://github.com/ory/keto/blob/master/contrib/rewrites-example/relation-tuples/tuples.json)).

```text
Doc:readme#owners@User:anne
Group:eng#members@User:beto
Doc:readme#viewers@Group:eng#members
Doc:readme#parents@Folder:A
Folder:A#viewers@User:chen
```

- Jeder Container bedient eine Read-API (Standardport 4466), eine Write-API (4467) und eine OPL-Syntax-API (4469), jeweils über HTTP und gRPC ([Konfigurationsschema](https://github.com/ory/keto/blob/master/embedx/config.schema.json)).
- "A good practice is to not expose the Write API at all to the public internet" (Gute Praxis ist, die Write-API überhaupt nicht ins öffentliche Internet zu stellen), und "The Read API should also be protected" (Auch die Read-API sollte geschützt werden) ([Produktionsleitfaden](https://www.ory.com/docs/keto/guides/production)).
- Skalierung: "There are no additional requirements for scaling when self-hosting Ory Keto, just spin up another container!" (Beim Selbsthosten von Ory Keto gibt es keine zusätzlichen Anforderungen für die Skalierung, starten Sie einfach einen weiteren Container!) (derselbe Leitfaden). Die Container teilen die Datenbank.

## Konsistenz

Der zookie des Papers erlaubt es einem Client, eine Prüfung "at a consistent snapshot no earlier than the given zookie" (§2.4.4) (auf einem konsistenten Snapshot, der nicht früher liegt als der angegebene zookie) anzufordern. Die Protobuf-API von Keto trägt dieselbe Idee in ihren Feldnamen: `snaptoken` bei Check, Expand und ListRelationTuples, `snaptokens` bei TransactRelationTuples und ein Flag `latest` für eine Content-Change-Prüfung. Jedes dieser Felder ist als "not implemented yet and has no effect" (noch nicht implementiert und ohne Wirkung) dokumentiert ([check_service.proto](https://github.com/ory/keto/blob/master/proto/ory/keto/relation_tuples/v1alpha2/check_service.proto)).

## Unterschiede zum Paper

- **Keine zookies.** Die Felder existieren; das Verhalten nicht (siehe oben).
- **Kein Watch.** Die v1alpha2-API hat die Dienste Check, Expand, Read, Write, Namespaces und Version sowie einen separaten OPL-Syntax-Dienst (`opl/v1alpha1`), aber keinen Änderungsstream ([Proto-Verzeichnis](https://github.com/ory/keto/tree/master/proto/ory/keto)). Watch speist im Paper sekundäre Indizes und Leopard (§2.4.3, §3.2.4).
- **Kein Leopard.** Ein denormalisierter Mengenindex ist nicht dokumentiert.
- **Eine Programmiersprachen-Syntax.** OPL ist eine Teilmenge von TypeScript, damit "users can get context help from their IDE" (Benutzer kontextbezogene Hilfe von ihrer IDE erhalten können) ([OPL-Spezifikation](https://github.com/ory/keto/blob/master/docs/ory_permission_language_spec.md)). Abbildung 1 des Papers schreibt eine Konfiguration in einer Textsyntax im Stil von Protocol Buffers (§2.3.1); das Paper benennt das Format nicht.
- **SQL-Speicher.** Eine gemeinsame SQL-Datenbank statt Spanner (§3.1).
- **Prüftiefe.** Check-Anfragen tragen ein `max_depth`, "The maximum depth to search for a relation" (die maximale Tiefe, bis zu der nach einer Relation gesucht wird) ([check_service.proto](https://github.com/ory/keto/blob/master/proto/ory/keto/relation_tuples/v1alpha2/check_service.proto)).
