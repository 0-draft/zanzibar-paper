SpiceDB ist eine Open-Source-Datenbank, die Beziehungen speichert und Berechtigungsabfragen darüber beantwortet, im Stil von Zanzibar. Sie ist in Go geschrieben, unter Apache-2.0 lizenziert und wird von AuthZed, Inc. gepflegt ([Repository](https://github.com/authzed/spicedb)). Ihr erstes GitHub-Release, v1.0.0, ist auf den 2021-09-30 datiert. AuthZed verkauft darum herum auch verwaltete und kommerzielle Dienste; diese werden unten als solche benannt. Die meisten Quellen auf dieser Seite sind die eigene Dokumentation und der Blog von AuthZed.

## Begriffe des Papers und Begriffe von SpiceDB

| Im Paper | In SpiceDB |
| --- | --- |
| Namespace-Konfiguration (§2.3) | Eine `definition` im Schema ([Schema-Dokumentation](https://authzed.com/docs/spicedb/concepts/schema)) |
| Relationstupel `object#relation@user` (§2.1) | Relationship `resource#relation@subject`, z. B. `document:readme#editor@user:emilia` ([Relationships](https://authzed.com/docs/spicedb/concepts/relationships)) |
| `_this` (§2.3.1) | Eine `relation` mit ihren erlaubten Subjekttypen; die dafür gespeicherten Relationships |
| `computed_userset` | Eine andere Relation oder Berechtigung innerhalb eines `permission`-Ausdrucks nennen |
| `tuple_to_userset` | Der Pfeil `parent->view` (Alias `parent.any(view)`) |
| `union` / `intersection` / `exclusion` | `+` / `&` / `-` |
| zookie (§2.4) | ZedToken ([Konsistenz](https://authzed.com/docs/spicedb/concepts/consistency)) |
| Check (§2.4.4) | `CheckPermission`, `CheckBulkPermissions` |
| Read (§2.4.1) | `ReadRelationships` |
| Write (§2.4.2) | `WriteRelationships`, `DeleteRelationships` |
| Watch (§2.4.3) | `Watch` |
| Expand (§2.4.5) | `ExpandPermissionTree` |
| Nicht in der API des Papers | `LookupResources`, `LookupSubjects`, `ImportBulkRelationships`, `ExportBulkRelationships` |
| Leopard (§3.2.4) | AuthZed Materialize, ein kommerzieller Dienst für Kunden von AuthZed Dedicated ([Dokumentation](https://authzed.com/docs/materialize/getting-started/overview)) |
| Spanner (§3) | CockroachDB, Cloud Spanner, PostgreSQL, MySQL, memdb ([Datastores](https://authzed.com/docs/spicedb/concepts/datastores)) |

Die API-Namen stammen aus den Protokolldateien von AuthZed: [`permission_service.proto`](https://github.com/authzed/api/blob/main/authzed/api/v1/permission_service.proto) und [`watch_service.proto`](https://github.com/authzed/api/blob/main/authzed/api/v1/watch_service.proto).

## Das durchgehende Beispiel als Schema

Abbildung 1 des Papers macht Eigentümer zu Bearbeitern, Bearbeiter zu Betrachtern und Betrachter des übergeordneten Ordners zu Betrachtern des Dokuments (§2.3.1). In SpiceDB werden gespeicherte Relationen und berechnete Berechtigungen getrennt deklariert: `relation`-Zeilen sagen, wer in einer Relationship geschrieben werden darf, `permission`-Zeilen sagen, wie der Zugriff berechnet wird.

```text
definition user {}

definition group {
    relation member: user
}

definition folder {
    relation viewer: user | group#member
    permission view = viewer
}

definition doc {
    relation parent: folder
    relation owner: user
    relation editor: user | group#member
    relation viewer: user | group#member

    permission edit = owner + editor
    permission view = viewer + edit + parent->view
}
```

<Callout kind="note" title="Nicht durch einen Validator geschickt">

Dieses Schema verwendet nur Konstrukte, die mit Stand 2026-11-13 auf der [Seite zur Schemasprache](https://authzed.com/docs/spicedb/concepts/schema) von SpiceDB gezeigt werden: `definition`, `relation` mit `user | group#member`, `permission` mit `+` und `->`. Es wurde nicht durch `zed` oder den SpiceDB-Playground geschickt.

</Callout>

Die Relationships für Anne, Beto und Chen:

```text
doc:readme#owner@user:anne
doc:readme#parent@folder:A
group:eng#member@user:beto
doc:readme#viewer@group:eng#member
folder:A#viewer@user:chen
```

Keine Relationship erwähnt `view` oder `edit`: Beides sind Berechtigungen, die zur Prüfzeit aus dem Schema berechnet werden, so wie die Umschreibregeln des Papers berechnet statt gespeichert werden (§2.3.1).

## Architektur

Wie beantwortet eine SpiceDB-Installation eine Prüfung? AuthZed beschreibt SpiceDB als "fundamentally a gRPC service" (im Kern einen gRPC-Dienst) mit einem optionalen HTTP-Gateway ([Architekturbeitrag, 2021-11-17](https://authzed.com/blog/spicedb-architecture)). Ein Knoten zerlegt eine Anfrage in kleinere Fragen und leitet sie an andere Knoten weiter, ein Vorgang, den SpiceDB Dispatch nennt; jeder Knoten hält "an in-memory cache of permissions queries it has resolved in the past" (einen In-Memory-Cache der Berechtigungsabfragen, die er in der Vergangenheit aufgelöst hat) ([Performance-Dokumentation](https://authzed.com/docs/spicedb/ops/performance)). Ein konsistenter Hash schickt "the same (sub-)requests to the same server" (dieselben (Teil-)Anfragen an denselben Server) ([Architekturbeitrag](https://authzed.com/blog/spicedb-architecture)). Alle Knoten teilen einen Datastore. Materialize berechnet, wenn verwendet, ausgewählte Berechtigungen vorab, und SpiceDB "can dispatch sub-queries to Materialize" (kann Teilabfragen an Materialize dispatchen) ([Performance-Dokumentation](https://authzed.com/docs/spicedb/ops/performance)).

## Konsistenz: ZedTokens und zookies

AuthZed nennt das ZedToken "the SpiceDB equivalent of Google Zanzibar's Zookie concept which protects users from the New Enemy Problem" (die SpiceDB-Entsprechung des Zookie-Konzepts von Google Zanzibar, das Benutzer vor dem „New Enemy“-Problem schützt) ([Konsistenz-Dokumentation](https://authzed.com/docs/spicedb/concepts/consistency)). Schreibvorgänge geben eines zurück (`written_at`), Prüfungen ebenso (`checked_at`). Eine Anfrage kann einen von vier Modi wählen:

| Modus | Was er verlangt | Entsprechung im Paper |
| --- | --- | --- |
| `minimize_latency` | Was der Server am schnellsten beantworten kann | Kein zookie: "a reasonably recent snapshot" (ein hinreichend aktueller Snapshot) (§2.4.1) |
| `at_least_as_fresh` + ZedToken | Einen Snapshot, der nicht älter ist als das Token | Ein zookie in einer Prüfung oder einem Lesevorgang (§2.2, §2.4) |
| `at_exact_snapshot` + ZedToken | Genau den Snapshot des Tokens | Ein Lese-zookie, wiederverwendet, um "the same snapshot as a previous read" (denselben Snapshot wie ein vorheriger Lesevorgang) zu erhalten (§2.4.1) |
| `fully_consistent` | Die neuesten Daten | Keine direkte Entsprechung; die Content-Change-Prüfung des Papers wird auf dem neuesten Snapshot ausgewertet (§2.4.4) |

Bei CockroachDB warnt die Dokumentation, dass `fully_consistent` "does not guarantee read-after-write consistency" (keine Read-after-Write-Konsistenz garantiert), weil die Uhren der Knoten um bis zu `max_offset` des Clusters abweichen können; sie empfiehlt stattdessen ein ZedToken mit `at_least_as_fresh` ([Konsistenz-Dokumentation](https://authzed.com/docs/spicedb/concepts/consistency)).

`fully_consistent` ist der Standard für `WriteRelationships`, `DeleteRelationships`, `ReadSchema` und `WriteSchema`; `minimize_latency` ist der Standard für jede andere API ([Konsistenz-Dokumentation](https://authzed.com/docs/spicedb/concepts/consistency)).

Im Paper stammt der mit dem Inhalt gespeicherte zookie aus einer Content-Change-Prüfung (§2.2, §2.4.4). Die SpiceDB-Dokumentation sagt, dass bei einer Änderung einer Ressource "a new ZedToken is either returned or it should be requested by performing a check with full consistency" (ein neues ZedToken entweder zurückgegeben wird oder durch eine Prüfung mit voller Konsistenz angefordert werden sollte) ([Konsistenz-Dokumentation](https://authzed.com/docs/spicedb/concepts/consistency)); beide Wege existieren also.

Auch `Watch` verwendet ZedTokens: Eine Anfrage kann bei `optional_start_cursor` beginnen, und jede Antwort trägt `changes_through` zum Fortsetzen, was dem Heartbeat-zookie des Papers entspricht (§2.4.3) ([`watch_service.proto`](https://github.com/authzed/api/blob/main/authzed/api/v1/watch_service.proto)).

## Unterschiede zum Paper

- **Speicherung.** Das Paper speichert alles in Spanner (§3.1). SpiceDB hat austauschbare Datastores: CockroachDB ("high throughput and/or multi-region", also hoher Durchsatz und/oder mehrere Regionen), Cloud Spanner, PostgreSQL ("single-region", eine Region), MySQL ("Not recommended", nicht empfohlen) und memdb (lokale Entwicklung und Tests) ([Datastores](https://authzed.com/docs/spicedb/concepts/datastores)).
- **Relationen und Berechtigungen sind getrennt.** Das Paper hängt eine Userset-Umschreibung an eine Relation (§2.3.1). SpiceDB trennt gespeicherte `relation`s von berechneten `permission`s ([Schema](https://authzed.com/docs/spicedb/concepts/schema)).
- **Caveats.** Relationships können einen benannten CEL-Ausdruck tragen, der im Schema mit `with` angehängt wird (z. B. `relation viewer: user | user with ip_allowlist`) ([Caveats](https://authzed.com/docs/spicedb/concepts/caveats)). Das Tupel des Papers (§2.1) hat kein solches Feld.
- **Wildcards.** `relation viewer: user | user:*` erlaubt eine öffentliche Freigabe ([Schema](https://authzed.com/docs/spicedb/concepts/schema)). Die Tupelgrammatik des Papers hat eine Benutzer-ID oder ein Userset (§2.1), keine Wildcard.
- **Schnittmengen-Pfeil.** `.all()` verlangt, dass jedes verbundene Objekt die Berechtigung gewährt ([Schema](https://authzed.com/docs/spicedb/concepts/schema)). Die drei Umschreib-Blätter des Papers (§2.3.1) haben keine solche Form.
- **Standard-Veraltung.** Das Paper wählt die Standard-Veraltung adaptiv anhand von Statistiken zu Lesevorgängen außerhalb der Zone (§3.2.1) und rundet unabhängig davon Auswertungszeitstempel "to a coarse granularity, such as one or ten seconds" (auf eine grobe Granularität, etwa eine oder zehn Sekunden) auf, damit Cache-Einträge geteilt werden (§3.2.5). SpiceDB hat nur die Rundung: Es gruppiert Anfrage-Revisionen in Fenster, die durch `--datastore-revision-quantization-interval` festgelegt werden, damit Cache-Einträge wiederverwendet werden können; AuthZed nennt "the default is 5s" (der Standard ist 5 s) ([Beitrag zu Hotspot-Caching, 2023-05-10](https://authzed.com/blog/hotspot-caching-in-google-zanzibar-and-spicedb)), was `RevisionQuantization: 5 * time.Second` im [Quellcode](https://github.com/authzed/spicedb/blob/main/pkg/cmd/datastore/dsconfig/config.go) entspricht.
- **Lookup-APIs.** `LookupResources` und `LookupSubjects` beantworten Fragen nach „welchen Ressourcen“ und „welchen Subjekten“ ([`permission_service.proto`](https://github.com/authzed/api/blob/main/authzed/api/v1/permission_service.proto)). Die API des Papers hat Read, Write, Watch, Check und Expand (§2.4).
- **Leopard.** "AuthZed Materialize takes inspiration from the Leopard index component described in the Zanzibar paper" (AuthZed Materialize ist von der im Zanzibar-Paper beschriebenen Leopard-Indexkomponente inspiriert) ([Materialize-Dokumentation](https://authzed.com/docs/materialize/getting-started/overview)). Es ist Teil des kostenpflichtigen Angebots von AuthZed, nicht des Open-Source-SpiceDB: Laut Dokumentation ist seine Funktion Accelerated Queries "generally available to users of AuthZed Dedicated" (allgemein verfügbar für Benutzer von AuthZed Dedicated).
