Mehrere Open-Source-Projekte beschreiben sich als von Zanzibar inspiriert oder nach Zanzibar modelliert. Diese Seite stellt sechs von ihnen dem Paper gegenüber, ein Aspekt pro Tabelle. Die Zellen sind kurz; die Quellen für jede Zeile stehen unter der jeweiligen Tabelle. Die Fakten wurden am 2026-11-13 geprüft und stammen aus dem eigenen Repository und der Dokumentation des jeweiligen Projekts, sind also meist vom Hersteller verfasst.

Die sechs: [SpiceDB](https://github.com/authzed/spicedb) (AuthZed), [OpenFGA](https://github.com/openfga/openfga) (CNCF), [Permify](https://github.com/Permify/permify) (FusionAuth), [Ory Keto](https://github.com/ory/keto) (Ory), [Topaz](https://github.com/aserto-dev/topaz) (seine Maintainer, nachdem Aserto den Betrieb eingestellt hat) und [Warrant](https://github.com/warrant-dev/warrant) (WorkOS). Jedes hat eine eigene Seite: [SpiceDB](../spicedb/), [OpenFGA](../openfga/), [Permify](../permify/), [Ory Keto](../ory-keto/), [Topaz](../topaz/), [Warrant](../warrant/).

## Schemasprache

Das Paper nennt es eine Namespace-Konfiguration: Relationen mit Userset-Umschreibregeln (§2.3). Abbildung 1 schreibt eine in einer Textsyntax im Stil von Protocol Buffers; das Paper benennt das Format nicht.

| System | Schemasprache | Format |
| --- | --- | --- |
| Paper | Namespace-Konfiguration | Protobuf-artiger Text in Abbildung 1 (Format nicht benannt) |
| SpiceDB | Schema (`definition`, `relation`, `permission`) | Eigene Sprache |
| OpenFGA | Autorisierungsmodell (`type`, `define`) | DSL, nach JSON kompiliert |
| Permify | Permify Schema (`entity`, `relation`, `permission` / `action`, `attribute`, `rule`) | Eigene Sprache |
| Ory Keto | Ory Permission Language (OPL) | TypeScript-Teilmenge |
| Topaz | Manifest (`types`, `relations`, `permissions`) | YAML, `version: 3` |
| Warrant | Objekttypen (`inheritIf`, `rules`) | JSON |

Quellen: [SpiceDB schema](https://authzed.com/docs/spicedb/concepts/schema) · [OpenFGA configuration language](https://openfga.dev/docs/configuration-language) · [Permify modeling](https://fusionauth.io/permify-docs/getting-started/modeling) · [Ory Permission Language](https://www.ory.com/docs/keto/reference/ory-permission-language) · [Topaz manifest reference](https://www.topaz.sh/docs/directory/manifest-reference) · [Warrant `spec.go`](https://github.com/warrant-dev/warrant/blob/main/pkg/authz/objecttype/spec.go)

## Tupelsyntax

Das Paper schreibt ein Tupel als `object#relation@user`, wobei der Benutzer selbst ein Userset `object#relation` sein kann (§2.1). Die Zeilen unten zeigen Betos Gruppe als Betrachter des Readme, wo die Dokumentation eine String-Form angibt.

| System | Name | Form |
| --- | --- | --- |
| Paper | Relationstupel (relation tuple) | `doc:readme#viewer@group:eng#member` |
| SpiceDB | Relationship | `doc:readme#viewer@group:eng#member` |
| OpenFGA | Relationship tuple | Benutzer `group:eng#member`, Relation `viewer`, Objekt `doc:readme` |
| Permify | Relational tuple | `doc:readme#viewer@group:eng#member` |
| Ory Keto | Relation tuple | `Doc:readme#viewers@Group:eng#members` |
| Topaz | Relation | Felder `object_type`, `object_id`, `relation`, `subject_type`, `subject_id`, optional `subject_relation` |
| Warrant | Warrant | `[user:1] is an [editor] of [document:docA]` (Beispiel aus dem README) |

Quellen: [SpiceDB relationships](https://authzed.com/docs/spicedb/concepts/relationships) · [OpenFGA concepts](https://openfga.dev/docs/concepts) · [Permify sync data](https://fusionauth.io/permify-docs/getting-started/sync-data) · [Ory Keto relation tuples](https://www.ory.com/docs/keto/concepts/relation-tuples) · [Topaz `common.proto`](https://github.com/aserto-dev/go-directory/blob/main/proto/aserto/directory/common/v3/common.proto) · [Warrant README](https://github.com/warrant-dev/warrant)

## Umschreiboperatoren

Die Umschreibregeln des Papers kombinieren drei Blätter, `_this`, `computed_userset` und `tuple_to_userset`, mit Vereinigung, Schnittmenge und Ausschluss (§2.3.1).

| System | Vereinigung / Schnittmenge / Ausschluss | computed_userset | tuple_to_userset |
| --- | --- | --- | --- |
| Paper | `union` / `intersection` / `exclusion` | `computed_userset` | `tuple_to_userset` |
| SpiceDB | `+` / `&` / `-` | Eine Relation oder Berechtigung nennen | `parent->view` (auch `.any()`; `.all()` bildet die Schnittmenge) |
| OpenFGA | `or` / `and` / `but not` | Bloßer Relationsname | `viewer from parent` |
| Permify | `or` / `and` / `not` | Bloßer Name | Punkt: `org.admin` |
| Ory Keto | `\|\|` / `&&` / `!` | `this.permits.x(ctx)` | `.traverse(...)` |
| Topaz | `\|` / `&` / `-` | Eine Relation oder Berechtigung nennen | `parent->can_read` |
| Warrant | `anyOf` / `allOf` / `noneOf` | `inheritIf` | `ofType` + `withRelation` |

Quellen: [SpiceDB schema](https://authzed.com/docs/spicedb/concepts/schema) · [OpenFGA equivalent Zanzibar concepts](https://openfga.dev/docs/configuration-language#equivalent-zanzibar-concepts) · [Permify modeling](https://fusionauth.io/permify-docs/getting-started/modeling) · [Ory Permission Language](https://www.ory.com/docs/keto/reference/ory-permission-language) · [Topaz manifest reference](https://www.topaz.sh/docs/directory/manifest-reference) · [Warrant `spec.go`](https://github.com/warrant-dev/warrant/blob/main/pkg/authz/objecttype/spec.go)

## Konsistenztoken und -modi

Der zookie des Papers ist "an opaque byte sequence encoding a globally meaningful timestamp" (§2.4) (eine opake Bytefolge, die einen global aussagekräftigen Zeitstempel kodiert); eine Prüfung wird auf einem Snapshot ausgewertet, der nicht früher liegt als der zookie, den sie trägt (§2.2, §2.4.4).

| System | Token | Modi oder Verhalten |
| --- | --- | --- |
| Paper | zookie | Mit zookie: mindestens so aktuell; ohne: "a reasonably recent snapshot" (ein hinreichend aktueller Snapshot) (§2.4.1) |
| SpiceDB | ZedToken | `minimize_latency`, `at_least_as_fresh`, `at_exact_snapshot`, `fully_consistent` |
| OpenFGA | Keines | `MINIMIZE_LATENCY` (Standard), `HIGHER_CONSISTENCY`; Cache standardmäßig aus |
| Permify | Snap Token | Von Write zurückgegeben, an Check als `snap_token` übergeben; ohne Token die neueste Transaktion |
| Ory Keto | Feld `snaptoken` | "not implemented yet and has no effect" (noch nicht implementiert und ohne Wirkung) |
| Topaz | Keines dokumentiert | Keine Token-Felder in der Reader-API |
| Warrant | Header `Warrant-Token` | Der Open-Source-Server gibt kein Token zurück und reagiert nur auf `latest`, was den Lesevorgang an die primäre Datenbank schickt |

Quellen: [SpiceDB consistency](https://authzed.com/docs/spicedb/concepts/consistency) · [OpenFGA consistency](https://openfga.dev/docs/interacting/consistency) · [Permify snap tokens](https://fusionauth.io/permify-docs/operations/snap-tokens) · [Keto `check_service.proto`](https://github.com/ory/keto/blob/master/proto/ory/keto/relation_tuples/v1alpha2/check_service.proto) · [Topaz `reader.proto`](https://github.com/aserto-dev/go-directory/blob/main/proto/aserto/directory/reader/v3/reader.proto) · [Warrant `wookie.go`](https://github.com/warrant-dev/warrant/blob/main/pkg/wookie/wookie.go), [`sql.go`](https://github.com/warrant-dev/warrant/blob/main/pkg/database/sql.go), [`warrant/service.go`](https://github.com/warrant-dev/warrant/blob/main/pkg/authz/warrant/service.go)

Nur die beiden durchgezogenen Verbindungen erlauben es einer Anwendung zu sagen „mindestens so aktuell wie mein Schreibvorgang“, und genau das schützt im Paper vor dem „New Enemy“-Problem (§2.2).

## Watch und changelog

Watch streamt im Paper Tupeländerungen aus einem changelog, mit Heartbeat-zookies zum Fortsetzen (§2.4.3, §3).

| System | API | Form |
| --- | --- | --- |
| Paper | Watch | Stream, mit einem zookie fortsetzbar |
| SpiceDB | `Watch` | Stream, mit einem ZedToken fortsetzbar (`changes_through`) |
| OpenFGA | `ReadChanges` | Paginierter Lesevorgang mit Fortsetzungstoken (abgefragt) |
| Permify | `Watch` | Stream (`stream WatchResponse`) |
| Ory Keto | Keine | Kein Watch-Dienst in den Protokolldateien |
| Topaz | Keine | Kein Watch-Dienst in den Protokolldateien |
| Warrant | Keine | Kein Änderungs- oder Ereignis-Endpunkt im Repository |

Quellen: [SpiceDB `watch_service.proto`](https://github.com/authzed/api/blob/main/authzed/api/v1/watch_service.proto) · [OpenFGA `openfga_service.proto`](https://github.com/openfga/api/blob/main/openfga/v1/openfga_service.proto) · [Permify `service.proto`](https://github.com/Permify/permify/blob/master/proto/base/v1/service.proto) · [Keto protos](https://github.com/ory/keto/tree/master/proto/ory/keto) · [Topaz go-directory protos](https://github.com/aserto-dev/go-directory/tree/main/proto/aserto/directory) · [Warrant repository](https://github.com/warrant-dev/warrant)

## Leopard-ähnlicher Index

Leopard ist der Index des Papers für große und tief verschachtelte Gruppen, aufgebaut aus Snapshots und Watch-Aktualisierungen (§3.2.4).

| System | Vorberechneter Index | Anmerkung |
| --- | --- | --- |
| Paper | Leopard | Serving-, Offline- und inkrementeller Teil (§3.2.4) |
| SpiceDB | AuthZed Materialize | Kommerziell, für Kunden von AuthZed Dedicated; "takes inspiration from the Leopard index component" (ist von der Leopard-Indexkomponente inspiriert) |
| OpenFGA | Keiner dokumentiert | Check- und Iterator-Caches |
| Permify | Keiner dokumentiert | "process-local cache; there is no shared cache layer" (prozesslokaler Cache; es gibt keine gemeinsame Cache-Schicht) |
| Ory Keto | Keiner dokumentiert | |
| Topaz | Keiner dokumentiert | |
| Warrant | Keiner dokumentiert | |

Quellen: [AuthZed Materialize](https://authzed.com/docs/materialize/getting-started/overview) · [OpenFGA consistency (Cache-Flags)](https://openfga.dev/docs/interacting/consistency) · [Permify cache](https://fusionauth.io/permify-docs/operations/cache) · [Ory Keto docs](https://www.ory.com/docs/keto) · [Topaz architecture](https://www.topaz.sh/docs/architecture) · [Warrant repository](https://github.com/warrant-dev/warrant). „Keiner dokumentiert“ bedeutet, dass die aufgeführten Seiten keinen solchen Index beschreiben, nicht, dass einer ausgeschlossen wurde.
