Jedes Autorisierungssystem beantwortet dieselbe Art von Frage: Darf dieser Benutzer dies mit diesem Objekt tun? Das Paper formuliert es als Prüfung, "that a user has permission to carry out an operation on a digital object" (§1) (dass ein Benutzer die Berechtigung hat, eine Operation auf einem digitalen Objekt auszuführen). Die vier gängigen Modelle unterscheiden sich darin, was sie speichern und was sie berechnen, wenn die Frage eintrifft.

1971 beschrieb Butler Lampson Schutz als Matrix: Zeilen sind Domänen (in heutigen Begriffen Subjekte), Spalten sind Objekte, und jede Zelle listet den Zugriff auf, den eine Domäne auf ein Objekt hat ([Lampson, „Protection“](https://cseweb.ucsd.edu/classes/fa01/cse221/papers/lampson-protection-osr74.pdf)). Kein reales System speichert die ganze Matrix. Eine ACL speichert ihre Spalten, Rollen und Attributregeln berechnen ihre Zellen, und ein Beziehungsgraph leitet sie durch das Verfolgen von Kanten ab.

Diese Seite modelliert eine Zelle auf vier Arten. Das durchgehende Beispiel: Anne, Beto und Chen (`user:anne`, `user:beto`, `user:chen`); das Dokument `doc:readme` in `folder:A`; die Gruppe `group:eng`. Anne ist Eigentümerin des Readmes, Beto ist in eng, die Mitglieder von eng sehen das Readme, und Chen sieht Ordner A. Die Entscheidung lautet:

```text
Can user:chen view doc:readme?
```

Die erwartete Antwort ist ja, und zwar nur wegen des Ordners. Chen hat keine direkte Berechtigung auf dem Readme.

## ACL: eine Liste am Objekt

Eine Zugriffskontrollliste hängt an jedes Objekt eine Liste von Einträgen, jeder bestehend aus einem Prinzipal und einer Menge von Rechten. Multics hatte ACLs "on segments and directories" (auf Segmenten und Verzeichnissen), mit Einträgen aus "a principal identifier and a set of permissions bits" (einem Prinzipal-Bezeichner und einer Menge von Berechtigungsbits) (§5, mit Verweis auf Saltzers Paper von der SOSP '73, überarbeitet als [Saltzer 1974](https://dl.acm.org/doi/10.1145/361011.361067)). Spätere Systeme erlaubten es einem Eintrag, eine Gruppe zu nennen, wie es POSIX-ACLs tun (§5).

Die Prüfung selbst ist ein Nachschlagen: die Liste des Readmes nach Chen durchsuchen. Beachten Sie, wo der Ordner geblieben ist. Vererbung ist nicht Teil des ACL-Modells, also muss der Eintrag auf das Readme kopiert werden, entweder beim Anlegen des Dokuments (VMS "supports ACL inheritance for files created within a directory tree", §5, also: unterstützt ACL-Vererbung für Dateien, die innerhalb eines Verzeichnisbaums angelegt werden) oder durch die Anwendung. Einmal kopiert, weiß der Eintrag nicht mehr, woher er stammt.

## RBAC: Benutzer, Rollen, Berechtigungen

Rollenbasierte Zugriffskontrolle legt eine Schicht zwischen Benutzer und Berechtigungen. In der Formulierung des NIST: "RBAC controls all access through roles assigned to users. Each role assigns a collection of permissions to users" (RBAC steuert jeden Zugriff über Rollen, die Benutzern zugewiesen sind. Jede Rolle weist Benutzern eine Sammlung von Berechtigungen zu) ([Kuhn, Coyne und Weil 2010](https://csrc.nist.gov/files/pubs/journal/2010/06/adding-attributes-to-rolebased-access-control/final/docs/kuhn-coyne-weil-10.pdf)). Ferraiolo und Kuhn schlugen es 1992 vor, und ein vereinheitlichtes NIST-Modell wurde 2004 zu ANSI INCITS 359-2004 ([NIST-RBAC-Projekt](https://csrc.nist.gov/projects/role-based-access-control)).

Rollen sind global, also braucht eine Berechtigung auf einem Dokument eine Rolle, die dieses Dokument nennt. Aus dem durchgehenden Beispiel werden drei Rollen:

| Benutzer | Rolle | Berechtigungen, die die Rolle gewährt |
| --- | --- | --- |
| `user:anne` | `readme_owner` | `doc:readme` bearbeiten, `doc:readme` sehen |
| `user:beto` | `eng` | `doc:readme` sehen |
| `user:chen` | `folderA_viewer` | `folder:A` sehen, `doc:readme` sehen (und jedes andere Dokument in Ordner A) |

Der Ordner überlebt nur als Name. `folderA_viewer` ist mit `folder:A` auf keine Weise verbunden, die das System versteht; jemand muss dafür sorgen, dass ihre Berechtigungsmenge „allem in Ordner A“ entspricht. Rollen pro Objekt wie `readme_owner` sind das Muster, das zur Rollenexplosion führt, die in der Tabelle unten besprochen wird.

## ABAC: ein Prädikat über Attribute

Attributbasierte Zugriffskontrolle speichert überhaupt keine Berechtigungen. NIST SP 800-162 definiert sie als Methodik, bei der die Autorisierung "is determined by evaluating attributes associated with the subject, object, requested operations, and, in some cases, environment against policy, rules, or relationships" ([NIST SP 800-162](https://csrc.nist.gov/pubs/sp/800/162/upd2/final)) (bestimmt wird, indem Attribute des Subjekts, des Objekts, der angeforderten Operationen und in manchen Fällen der Umgebung gegen Richtlinien, Regeln oder Beziehungen ausgewertet werden). Die Entscheidung ist eine Funktion von Attributen, ausgewertet zum Zeitpunkt der Anfrage.

Hier sind die drei Berechtigungen des durchgehenden Beispiels als Regeln, in der Syntax von [Cedar](https://docs.cedarpolicy.com/policies/syntax-policy.html), einer Richtliniensprache, die AWS 2023 als Open Source veröffentlicht hat:

```text
// Anne: the owner may view
permit (principal, action == Action::"view", resource)
when { resource.owner == principal };

// Beto: anyone whose team is listed on the document
permit (principal, action == Action::"view", resource)
when { resource.viewerTeams.contains(principal.team) };

// Chen: anyone listed as a viewer of the document's folder
permit (principal, action == Action::"view", resource)
when { resource.folder.viewers.contains(principal) };
```

<Callout kind="warn" title="Zur Veranschaulichung">

Diese drei Richtlinien folgen der dokumentierten Syntax von Cedar, wurden aber nicht durch den Cedar-Validator geschickt. Die Attributnamen (`owner`, `viewerTeams`, `team`, `folder`, `viewers`) sind eine Erfindung dieser Seite.

</Callout>

## ReBAC: ein Graph von Beziehungen

Beziehungsbasierte Zugriffskontrolle entscheidet anhand der Beziehungen zwischen dem Anfragenden und der Ressource. Fong schreibt Carrie Gates die Prägung des Begriffs zu (ihr Workshop-Paper von 2007 wurde für diese Seite nicht geprüft), und das Modell von Philip Fong aus dem Jahr 2011 stützt Entscheidungen "on the relationship between the resource owner and the resource accessor" (auf die Beziehung zwischen dem Eigentümer der Ressource und demjenigen, der auf sie zugreift) ([Fong 2011](https://pages.cpsc.ucalgary.ca/~pwlfong/Pub/codaspy2011.pdf)). Fong betont, dass sich binäre Relationen verketten lassen, etwa zu Freunden von Freunden, während eine Rolle ein einstelliges Prädikat ist, das über boolesche Kombinationen hinaus wenig bietet.

Zanzibar speichert jede Beziehung als Relationstupel, `object#relation@user` (§2.1), und eine Namespace-Konfiguration sagt, wie sich Relationen kombinieren. Abbildung 1 des Papers kodiert genau dieses Beispiel: Eigentümer sind Bearbeiter, Bearbeiter sind Betrachter, und "viewers of the parent folder are also viewers of the document" (Betrachter des übergeordneten Ordners sind auch Betrachter des Dokuments). Das Paper verwendet das Wort ReBAC nicht.

## Dasselbe Beispiel, Zelle für Zelle

| | ACL | RBAC | ABAC | ReBAC (Zanzibar) |
| --- | --- | --- | --- | --- |
| Was gespeichert wird | Die Liste des Readmes: Anne (owner), `group:eng` (view), Chen (view, von Ordner A kopiert) | Drei Rollenzuweisungen und die Berechtigungsmengen von drei Rollen | Drei Regeln, dazu Attribute an Benutzern, dem Readme und Ordner A | Fünf Tupel (owner, eng-Mitglied, eng-Betrachter, parent, Ordner-Betrachter) und eine Namespace-Konfiguration |
| Wer das Readme sehen kann | Die Liste lesen und `group:eng` expandieren: Anne, Beto, Chen | Jeder mit einer Rolle, die „view `doc:readme`“ gewährt: Anne, Beto, Chen | Nirgends gespeichert: die Regeln für jeden Benutzer auswerten. Anne, Beto, Chen | `doc:readme#viewer` expandieren (§2.4.5): Anne, Beto, Chen |
| Beto verlässt eng | Beto aus der Gruppe entfernen; die Liste des Readmes bleibt unberührt | Betos Zuweisung zu `eng` entfernen | `user:beto.team` ändern | Ein Tupel löschen, `group:eng#member@user:beto` |
| Das Readme wandert von Ordner A nach Ordner B | Die von A kopierten Einträge entfernen und die von B hineinkopieren, auf dem Readme und auf allem anderen, das mitgewandert ist | „view `doc:readme`“ aus `folderA_viewer` herausnehmen und einer Rolle `folderB_viewer` hinzufügen | `doc:readme.folder` ändern; die Regeln bleiben gleich | Ein `parent`-Tupel ersetzen: `doc:readme#parent@folder:A#...` wird zu `@folder:B#...` |
| Was schwierig ist | Vererbung und Gruppen sind Zusätze; „was kann Chen sehen?“ heißt, die Liste jedes Objekts zu durchsuchen | Rollenexplosion: "thousands of separate roles" (Tausende separater Rollen), und n boolesche Bedingungen können 2ⁿ Rollen erfordern ([Kuhn et al.](https://csrc.nist.gov/files/pubs/journal/2010/06/adding-attributes-to-rolebased-access-control/final/docs/kuhn-coyne-weil-10.pdf)); Rollen pro Objekt wie `readme_owner` verschlimmern das | Auditierung: ABAC "is easy to set up, but analyzing or changing user permissions can be problematic" (ist leicht einzurichten, aber Benutzerberechtigungen zu analysieren oder zu ändern kann problematisch sein) ([Kuhn et al.](https://csrc.nist.gov/files/pubs/journal/2010/06/adding-attributes-to-rolebased-access-control/final/docs/kuhn-coyne-weil-10.pdf)). „Attribute Sprawl“ ist eine in der Branche gängige Bezeichnung für dasselbe Problem, kein NIST-Begriff | Graphtraversierung: "Recursive pointer chasing … has difficulty maintaining low latency with groups that are deeply nested or have a large number of child groups" (§3.2.4) (Rekursive Zeigerverfolgung … hat Mühe, bei tief verschachtelten Gruppen oder Gruppen mit sehr vielen Untergruppen eine niedrige Latenz zu halten). SpiceDB begrenzt die Tiefe standardmäßig auf [50 Schritte](https://authzed.com/docs/spicedb/modeling/recursion-and-max-depth), OpenFGAs `resolveNodeLimit` auf [25](https://openfga.dev/docs/getting-started/setup-openfga/configuration) |

Beachten Sie die beiden mittleren Zeilen. Dass Beto eng verlässt, ist in jedem Modell eine Änderung, weil jedes Modell hier eine Form von Gruppe hat. Beim Verschieben des Ordners trennen sich die Wege: ACL und RBAC haben die Bedeutung des Ordners in die Berechtigungen des Readmes kopiert und müssen diese daher neu schreiben; ABAC und ReBAC haben den Ordner als Daten behalten, also ändert sich ein Wert. ReBAC hält außerdem „wer kann sehen?“ aus gespeicherten Daten beantwortbar, was die reine Regelvariante von ABAC nicht kann.

## Wo Zanzibar steht

Zanzibar ist ein ReBAC-System: Relationstupel sind die Kanten, und Userset-Umschreibregeln (§2.3.1) sagen, wie sich Kanten kombinieren. Sein Datenmodell unterstützt "permissions, users, groups, and inheritance" (Berechtigungen, Benutzer, Gruppen und Vererbung), wie man sie in Multics, UNIX, POSIX-ACLs und VMS findet (§5), und es behandelt eine Gruppe als ein weiteres Objekt, was "allows us to unify the concepts of ACLs and groups" (§2.1) (es uns erlaubt, die Konzepte von ACLs und Gruppen zu vereinheitlichen).

RBAC passt obendrauf. Das Paper sagt, Rollen "are similar to Zanzibar relations" (ähneln Zanzibar-Relationen) und "A number of Zanzibar clients have implemented RBAC policies on top of Zanzibar’s namespace configuration language" (§5) (Eine Reihe von Zanzibar-Clients hat RBAC-Richtlinien auf Grundlage der Namespace-Konfigurationssprache von Zanzibar implementiert). Es sagt nicht, wie; eine Möglichkeit ist, eine Rolle zu einem Objekt zu machen, dessen Relation `member` ein Userset ist.

Die Rolle hat dieselbe Form wie `group:eng`: ein Userset. In Zanzibar ist die zweite `viewer`-Kante unnötig, weil die parent-Regel Betrachtern des Ordners bereits das Readme gibt; die Rolle muss nur Betrachter des Ordners sein.

ABAC ist der Teil, den das Paper nicht abdeckt. Bedingungen an die Anfrage, etwa Tageszeit oder Netzwerk, sind keine Relationen zwischen gespeicherten Objekten. Mehrere Systeme im Zanzibar-Stil fügen sie hinzu: SpiceDB hat Caveats, in CEL geschriebene Bedingungen ([SpiceDB-Schema-Dokumentation](https://authzed.com/docs/spicedb/concepts/schema)), OpenFGA hat [Conditions](https://openfga.dev/docs/modeling/conditions), und das Schema von Permify hat `attribute` und `rule` ([Permify-Dokumentation](https://fusionauth.io/permify-docs/getting-started/modeling)). Cedar geht den umgekehrten Weg: eine Attributsprache mit `in` für die Zugehörigkeit zu Hierarchien ([Cedar-Syntax](https://docs.cedarpolicy.com/policies/syntax-policy.html)).

<Callout kind="note" title="Reale Systeme mischen Modelle">

Nur wenige produktive Systeme folgen einem einzigen Modell. Cloud IAM von Google, das Benutzern Rollen zuweist, "is built as a layer on top of Zanzibar’s ACL storage and evaluation system" (§5) (ist als Schicht auf dem ACL-Speicher- und Auswertungssystem von Zanzibar gebaut). Eine Kombination, die die obigen Systeme im Zanzibar-Stil unterstützen, ist ein Beziehungsgraph für Freigaben und Hierarchien, Rollen als benannte Relationen darin und einige Attributbedingungen für den Kontext.
