Permify ist ein in Go geschriebener Autorisierungsdienst. Seine Dokumentation nennt ihn "an open-source authorization service for creating fine-grained and scalable authorization systems" (einen Open-Source-Autorisierungsdienst zum Aufbau feingranularer und skalierbarer Autorisierungssysteme), "inspired by Google's consistent, global authorization system, Google Zanzibar" (inspiriert von Googles konsistentem, globalem Autorisierungssystem, Google Zanzibar) ([Permify-Dokumentation](https://fusionauth.io/permify-docs)). Man beschreibt Entitätstypen und ihre Relationen im Permify Schema, schreibt Beziehungen als Tupel und fragt einen Server über gRPC oder HTTP, ob ein Subjekt eine Berechtigung hat.

Die Übernahme von Permify durch FusionAuth wurde am 2025-11-20 angekündigt ([Ankündigung von Permify](https://permify.co/post/fusionauth-acquires-permify/), [Ankündigung von FusionAuth](https://fusionauth.io/blog/fusionauth-acquires-permify)). FusionAuth nennt das Produkt inzwischen "FusionAuth FGA by Permify" ([Support-Beitrag von FusionAuth](https://fusionauth.io/blog/how-to-get-support-for-fusionauth-fga-permify)), und die Dokumentation liegt unter [fusionauth.io/permify-docs](https://fusionauth.io/permify-docs). Der Beitrag von Permify sagt: "The core Permify project remains open source and will continue to live on GitHub." (Das Kernprojekt Permify bleibt Open Source und wird weiter auf GitHub leben.)

## Paper und Permify nebeneinander

Jede Zeile nennt ein Konzept aus dem Paper und das Nächstliegende, das Permify dokumentiert. Wo Permify nichts Vergleichbares hat, sagt die Zelle das.

| Im Paper | In Permify |
| --- | --- |
| Namespace-Konfiguration (§2.3) | Ein `entity`-Block im Permify Schema, mit `relation`, `permission` (oder dem Synonym `action`), `attribute` und `rule` ([Modellierung](https://fusionauth.io/permify-docs/getting-started/modeling)) |
| Relationstupel `object#relation@user` (§2.1) | Relational Tuple `entity#relation@subject`, zum Beispiel `doc:readme#owner@user:anne` ([Daten speichern](https://fusionauth.io/permify-docs/getting-started/sync-data)) |
| `_this` | Die gespeicherten Tupel einer `relation`; eine Berechtigung schließt sie ein, indem sie die Relation nennt |
| `computed_userset` | Eine andere Relation oder Berechtigung derselben Entität nennen, wie `edit` in `view = viewer or edit` |
| `tuple_to_userset` | Punkt-Traversierung über eine Relation, wie `parent.view` |
| Vereinigung, Schnittmenge, Ausschluss | `or`, `and`, `not` |
| zookie (§2.2, §2.4) | Snap Token, das Feld `snap_token` ([Snap Tokens](https://fusionauth.io/permify-docs/operations/snap-tokens)) |
| Check (§2.4.4) | `Permission.Check`, dazu `BulkCheck` ([service.proto](https://github.com/Permify/permify/blob/master/proto/base/v1/service.proto)) |
| Read (§2.4.1) | `Data.ReadRelationships`, dazu `ReadAttributes` |
| Write (§2.4.2) | `Data.Write`, `WriteRelationships`, `Delete`, `DeleteRelationships` |
| Watch (§2.4.3) | `Watch.Watch`, ein Server-Stream ([Watch-Operationen](https://fusionauth.io/permify-docs/operations/watch)) |
| Expand (§2.4.5) | `Permission.Expand` |
| Leopard (§3.2.4) | Keine Entsprechung dokumentiert |
| Spanner (§3.1) | PostgreSQL oder eine In-Memory-Engine (der Konfigurationsstandard) ([Konfiguration](https://fusionauth.io/permify-docs/setting-up/configuration)) |

Permify hat außerdem Lookup-Aufrufe, die das Paper nicht beschreibt: `LookupEntity`, `LookupSubject` und `SubjectPermission`.

## Das durchgehende Beispiel im Permify Schema

Abbildung 1 des Papers gibt Dokumenten drei konzentrische Relationen: Eigentümer sind Bearbeiter, Bearbeiter sind Betrachter, und Betrachter des übergeordneten Ordners sind Betrachter des Dokuments (§2.3.1). Hier ist dieses Modell mit den Typen des durchgehenden Beispiels im Permify Schema.

```text
entity user {}

entity group {
    relation member @user
}

entity folder {
    relation viewer @user @group#member

    permission view = viewer
}

entity doc {
    relation parent @folder
    relation owner @user
    relation editor @user @group#member
    relation viewer @user @group#member

    permission edit = owner or editor
    permission view = viewer or edit or parent.view
}
```

`@group#member` lässt eine Relation ein Userset aufnehmen: „jeder, der Mitglied dieser Gruppe ist“. `parent.view` folgt der Relation `parent` zum Ordner und wertet dort die Berechtigung `view` des Ordners aus; die Dokumentation sagt: "The same traversal rule applies to both `relation.userset` and `relation.permission`" (Dieselbe Traversierungsregel gilt sowohl für `relation.userset` als auch für `relation.permission`) ([Modellierung](https://fusionauth.io/permify-docs/getting-started/modeling)).

<Callout title="Gegen die Dokumentation geprüft, nicht ausgeführt">
Dieses Schema folgt der dokumentierten Syntax mit Stand 2026-11-13: der [Modellierungsseite](https://fusionauth.io/permify-docs/getting-started/modeling) und der Beispieldatei [google-docs-simplified.yaml](https://github.com/Permify/permify/blob/master/assets/example-shapes/google-docs-simplified.yaml) der Maintainer. Es wurde nicht durch den Validator von Permify geschickt.
</Callout>

Das durchgehende Beispiel besteht aus fünf Tupeln:

```text
doc:readme#owner@user:anne
group:eng#member@user:beto
doc:readme#viewer@group:eng#member
doc:readme#parent@folder:A
folder:A#viewer@user:chen
```

## Architektur

Wie teilen sich Permify-Server die Arbeit, und wo liegen die Tupel?

Die Teile, jeweils aus der Dokumentation:

- Server lauschen standardmäßig auf HTTP-Port 3476 und gRPC-Port 3478 ([Konfiguration](https://fusionauth.io/permify-docs/setting-up/configuration)). Der Datenbankabschnitt akzeptiert getrennte URIs für `writer` und `reader`.
- Jeder Pod hält einen prozesslokalen [Ristretto](https://github.com/dgraph-io/ristretto)-Cache von Prüfergebnissen; "there is no shared cache layer" (es gibt keine gemeinsame Cache-Schicht) ([Cache](https://fusionauth.io/permify-docs/operations/cache)).
- Mit `distributed.enabled` hashen die Pods jede Anfrage auf einen Ring mit konsistentem Hashing, sodass "subsequent API calls with the same hash will retrieve the response from the instance 2, regardless of which instance that API called from" (nachfolgende API-Aufrufe mit demselben Hash die Antwort von Instanz 2 erhalten, unabhängig davon, von welcher Instanz die API aufgerufen wurde). Ein Circuit Breaker stoppt Aufrufe an die Datenbank, solange diese ausgefallen ist.
- PostgreSQL speichert Tupel mit MVCC: Permify erzeugt "a separate database snapshot for each write and delete operation" (einen separaten Datenbank-Snapshot für jede Schreib- und Löschoperation), und ein optionaler Garbage Collector löscht alte Versionen.
- Jeder Watch-Stream "opens a long-lived connection with a continuous polling loop against the database" (öffnet eine langlebige Verbindung mit einer fortlaufenden Abfrageschleife gegen die Datenbank) ([Watch-Operationen](https://fusionauth.io/permify-docs/operations/watch)).

## Konsistenz

Das Snap Token von Permify übernimmt die Rolle des zookie. Ein Write gibt es zurück; der Client speichert es mit der Ressource und sendet es bei späteren Prüfungen als `snap_token` zurück. Die Dokumentation beschreibt es als "a token that consists of an encoded timestamp" (ein Token, das aus einem kodierten Zeitstempel besteht), das bei Zugriffsprüfungen verglichen wird, "to ensure that the snapshot of the access control is at least as fresh as the resource timestamp" (um sicherzustellen, dass der Snapshot der Zugriffskontrolle mindestens so aktuell ist wie der Zeitstempel der Ressource) ([Snap Tokens](https://fusionauth.io/permify-docs/operations/snap-tokens)). Das ist die Garantie des Papers für eine Prüfung, die einen zookie trägt: "a consistent snapshot no earlier than" (ein konsistenter Snapshot, der nicht früher liegt als) der angegebene zookie (§2.4.4).

Beachten Sie das Verhalten ohne Token. Das Paper lässt Zanzibar "choose a reasonably recent snapshot, possibly offering a lower-latency response" (§2.4.1) (einen hinreichend aktuellen Snapshot wählen und so möglicherweise eine Antwort mit geringerer Latenz bieten). Permify liest stattdessen die ID der neuesten Transaktion aus seiner Tabelle `transactions` und wertet auf diesem Snapshot aus; das Ergebnis wird unter einem Schlüssel gecacht, der diese ID enthält ([Snap Tokens](https://fusionauth.io/permify-docs/operations/snap-tokens)). Der Cache-Schlüssel ist `check_{tenant_id}_{schema_version}:{snapshot_token}:{check_request}` ([Cache](https://fusionauth.io/permify-docs/operations/cache)), sodass ein neuer Schreibvorgang neue Schlüssel erzeugt, statt alte zu invalidieren.

## Unterschiede zum Paper

- **Attribute und Regeln.** Das Permify Schema fügt `attribute` und `rule` für attributbasierte Prüfungen hinzu, etwa `permission view = check_ip_range(ip_range) or admin` ([Modellierung](https://fusionauth.io/permify-docs/getting-started/modeling)). Die Umschreibungen von Zanzibar arbeiten nur auf Tupeln (§2.3.1).
- **Kontextuelle Tupel.** Relationen, die "dynamically added to permission request operations" (dynamisch zu Berechtigungsanfragen hinzugefügt) werden, werden mit den gespeicherten ausgewertet und nie geschrieben ([kontextuelle Tupel](https://fusionauth.io/permify-docs/operations/contextual-tuples)).
- **Mandanten.** Ein Dienst `Tenancy` legt Mandanten an, listet sie auf und löscht sie ([service.proto](https://github.com/Permify/permify/blob/master/proto/base/v1/service.proto)); das Paper hat kein Mandantenkonzept.
- **Speicherung.** PostgreSQL mit MVCC-Snapshots statt Spanner, dessen TrueTime-Mechanismus jeden ACL-Schreibvorgang mit einem Zeitstempel versieht (§2.2, §3.1). Der verteilte Cache funktioniert "across availability zones (within an AWS region)" (über Availability Zones hinweg (innerhalb einer AWS-Region)) ([Cache](https://fusionauth.io/permify-docs/operations/cache)).
- **Kein denormalisierter Index.** Das Paper beantwortet Prüfungen tief verschachtelter Gruppen mit Leopard (§3.2.4). Permify dokumentiert Ergebnis-Caching und konsistentes Hashing, keinen Mengenindex.
- **Lookups.** `LookupEntity` und `LookupSubject` beantworten Fragen nach „welchen Ressourcen“ und „welchen Subjekten“, die die API des Papers nicht abdeckt.
