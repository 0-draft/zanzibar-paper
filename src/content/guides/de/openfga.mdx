OpenFGA ist eine Open-Source-Autorisierungs-Engine. Ihre Dokumentation sagt, dass die JSON-Form ihrer Modellsprache, diejenige, die die API akzeptiert, "closely tracks the language in the Zanzibar paper" (sich eng an die Sprache im Zanzibar-Paper anlehnt); die DSL fügt syntaktischen Zucker hinzu und wird in dieses JSON kompiliert ([Konfigurationssprache](https://openfga.dev/docs/configuration-language)). Der CNCF-Beitrag zur Aufnahme als Incubating-Projekt sagt, sie "was developed by a group of Okta employees, and is the foundation for the Auth0 FGA commercial offering" (wurde von einer Gruppe von Okta-Mitarbeitern entwickelt und ist die Grundlage des kommerziellen Angebots Auth0 FGA) ([CNCF, 2025-11-11](https://www.cncf.io/blog/2025/11/11/openfga-becomes-a-cncf-incubating-project/)). Sie ist in Go geschrieben und unter Apache-2.0 lizenziert ([Repository](https://github.com/openfga/openfga)). Der verwaltete Dienst von Auth0 beschreibt sich als "based on OpenFGA, an open-source project owned by the Cloud Native Computing Foundation" (basierend auf OpenFGA, einem Open-Source-Projekt im Besitz der Cloud Native Computing Foundation) ([Auth0-FGA-Dokumentation](https://docs.fga.dev/fga)).

## Begriffe des Papers und Begriffe von OpenFGA

Die Dokumentation von OpenFGA enthält eine eigene Tabelle der "Equivalent Zanzibar Concepts" (entsprechenden Zanzibar-Konzepte) ([Konfigurationssprache](https://openfga.dev/docs/configuration-language#equivalent-zanzibar-concepts)); diese hier erweitert sie um die API und den Speicher.

| Im Paper | In OpenFGA |
| --- | --- |
| Namespace-Konfiguration (§2.3) | Ein `type` in einem Autorisierungsmodell, geschrieben in der DSL oder in JSON ([Konfigurationssprache](https://openfga.dev/docs/configuration-language)) |
| Relationstupel `object#relation@user` (§2.1) | Relationship Tuple mit `user`, `relation`, `object`, z. B. `user:anne`, `owner`, `doc:readme`; ein Userset wird `group:eng#member` geschrieben |
| `_this` (§2.3.1) | Eine direkte Typbeschränkung wie `[user, group#member]` (`this` in JSON) |
| `computed_userset` | Ein bloßer Relationsname, z. B. `or owner` |
| `tuple_to_userset` | `viewer from parent` (`tupleToUserset` in JSON) |
| `union` / `intersection` / `exclusion` | `or` / `and` / `but not` (`union` / `intersection` / `difference` in JSON) |
| zookie (§2.4) | Keiner; eine Abfrage wählt `MINIMIZE_LATENCY` oder `HIGHER_CONSISTENCY` ([Konsistenz](https://openfga.dev/docs/interacting/consistency)) |
| Check (§2.4.4) | `Check`, `BatchCheck` |
| Read (§2.4.1) | `Read` |
| Write (§2.4.2) | `Write` |
| Watch (§2.4.3) | `ReadChanges`, ein paginierter Listen-Lesevorgang mit Fortsetzungstoken ([Tupeländerungen](https://openfga.dev/docs/interacting/read-tuple-changes)) |
| Expand (§2.4.5) | `Expand` |
| Nicht in der API des Papers | `ListObjects`, `StreamedListObjects`, `ListUsers`; Stores; Modellversionen (`WriteAuthorizationModel`, `ReadAuthorizationModel(s)`) |
| Leopard (§3.2.4) | Keine Entsprechung in der hier zitierten Dokumentation |
| Spanner (§3) | `memory` (Standard), `postgres`, `mysql`, `sqlite` ([OpenFGA konfigurieren](https://openfga.dev/docs/getting-started/setup-openfga/configure-openfga)) |

Die API-Namen stammen aus [`openfga_service.proto`](https://github.com/openfga/api/blob/main/openfga/v1/openfga_service.proto).

## Das durchgehende Beispiel als Modell

Abbildung 1 des Papers macht Eigentümer zu Bearbeitern, Bearbeiter zu Betrachtern und Betrachter des übergeordneten Ordners zu Betrachtern des Dokuments (§2.3.1). In der DSL von OpenFGA stehen dieselben Regeln in einer Zeile pro Relation:

```text
model
  schema 1.1

type user

type group
  relations
    define member: [user]

type folder
  relations
    define viewer: [user, group#member]

type doc
  relations
    define parent: [folder]
    define owner: [user]
    define editor: [user, group#member] or owner
    define viewer: [user, group#member] or editor or viewer from parent
```

<Callout kind="note" title="Nicht durch einen Validator geschickt">

Dieses Modell verwendet nur Konstrukte, die mit Stand 2026-11-13 auf der [Seite zur Konfigurationssprache](https://openfga.dev/docs/configuration-language) von OpenFGA und im Google-Drive-Beispiel der Maintainer ([`model.fga`](https://github.com/openfga/sample-stores/blob/main/stores/gdrive/model.fga)) vorkommen: `model`, `schema 1.1`, `type`, `relations`, `define`, Typbeschränkungen mit `group#member`, `or` und `from`. Es wurde nicht durch die OpenFGA-CLI oder den Playground geschickt.

</Callout>

Die Tupel für Anne, Beto und Chen:

| user | relation | object |
| --- | --- | --- |
| `user:anne` | `owner` | `doc:readme` |
| `folder:A` | `parent` | `doc:readme` |
| `user:beto` | `member` | `group:eng` |
| `group:eng#member` | `viewer` | `doc:readme` |
| `user:chen` | `viewer` | `folder:A` |

Welche dieser Tupel durchläuft eine Prüfung auf `viewer` am Readme für jede Person?

Das Modell, nicht ein Tupel, trägt „Eigentümer sind Bearbeiter“ und „Bearbeiter sind Betrachter“: Das ist der Punkt des Papers, dass Beziehungen zwischen Relationen in die Konfiguration gehören, nicht in ein Tupel pro Objekt (§2.3.1).

## Architektur

Woraus besteht eine OpenFGA-Installation? Die Dokumentation beschreibt Server auf einem SQL-Datenspeicher. Jeder Server kann In-Memory-Caches für Check halten, und der Produktionsleitfaden rät zu "a small pool of servers with high capacity (memory and CPU cores) instead of a big pool of servers, to increase cache hit ratios" (einem kleinen Pool von Servern mit hoher Kapazität (Arbeitsspeicher und CPU-Kerne) statt eines großen Pools, um die Cache-Trefferquote zu erhöhen) ([Betrieb in Produktion](https://openfga.dev/docs/best-practices/running-in-production)). Für PostgreSQL kann ein sekundärer Datenspeicher (Read Replica) konfiguriert werden; Lesevorgänge mit `HIGHER_CONSISTENCY` gehen an den primären ([OpenFGA konfigurieren](https://openfga.dev/docs/getting-started/setup-openfga/configure-openfga)). Konsumenten von Änderungen rufen `ReadChanges` auf und behalten das Fortsetzungstoken ([Tupeländerungen](https://openfga.dev/docs/interacting/read-tuple-changes)).

Zum Vergleich Abbildung 2 des Papers (§3): `aclservers` fächern Arbeit untereinander auf, `watchservers` liefern einen Stream, und Leopard hält einen denormalisierten Index. Die hier zitierte OpenFGA-Dokumentation beschreibt keines der drei; Server antworten aus dem Datenspeicher und ihren eigenen Caches.

## Konsistenz ohne zookies

OpenFGA hat keinen zookie. Die Dokumentation sagt das unter "Future work" (zukünftige Arbeit): Das Paper "has a feature called `Zookies`" (hat eine Funktion namens `Zookies`), und OpenFGA "is considering a similar feature in future releases" (erwägt eine ähnliche Funktion in zukünftigen Releases) ([Konsistenz](https://openfga.dev/docs/interacting/consistency)). Stattdessen nehmen Read und die Abfrage-APIs einen von zwei Werten:

| Modus | Verhalten ([Konsistenz-Dokumentation](https://openfga.dev/docs/interacting/consistency)) | Entsprechung im Paper |
| --- | --- | --- |
| `MINIMIZE_LATENCY` (Standard) | "will serve queries from the cache when possible" (bedient Abfragen nach Möglichkeit aus dem Cache) | Eine Anfrage ohne zookie: "a reasonably recent snapshot" (ein hinreichend aktueller Snapshot) (§2.4.1) |
| `HIGHER_CONSISTENCY` | "will skip the cache and query the database directly" (umgeht den Cache und fragt die Datenbank direkt ab) | Keine genaue Entsprechung; am nächsten kommt die Auswertung auf dem neuesten Snapshot |

Caching ist "disabled by default" (standardmäßig deaktiviert), und dann gilt: "all queries will have strong consistency regardless of the consistency mode specified" (alle Abfragen haben starke Konsistenz, unabhängig vom angegebenen Konsistenzmodus) ([Konsistenz](https://openfga.dev/docs/interacting/consistency)). Der Modus spielt erst eine Rolle, wenn ein Cache eingeschaltet ist.

Die Dokumentation schlägt vor, pro Anfrage zu entscheiden: Speichert die Anwendung, wann eine Ressource zuletzt geändert wurde, kann sie diesen Zeitpunkt mit der Cache-TTL vergleichen, um zwischen den beiden Modi zu wählen ([Konsistenz](https://openfga.dev/docs/interacting/consistency)). Dieser Zeitstempel übernimmt einen Teil der Rolle eines zookie, gehalten von der Anwendung. Außerdem gibt es Flags zur Cache-Invalidierung (`cache-controller-enabled`), die auf kürzliche Schreibvorgänge in den Store prüfen.

## Unterschiede zum Paper

- **Kein zookie.** Es wird kein Konsistenztoken zurückgegeben oder angenommen; zwei Modi plus ein standardmäßig ausgeschalteter Cache ersetzen es ([Konsistenz](https://openfga.dev/docs/interacting/consistency)). Das Konsistenzmodell des Papers beruht auf zookies (§2.2).
- **Änderungen werden per Polling abgefragt.** `ReadChanges` gibt eine Seite von Tupeländerungen "sorted by ascending time" (aufsteigend nach Zeit sortiert) mit einem Fortsetzungstoken zurück ([`openfga_service.proto`](https://github.com/openfga/api/blob/main/openfga/v1/openfga_service.proto)). Watch ist im Paper ein Stream mit Heartbeat-zookies (§2.4.3).
- **Speicherung.** Das Paper verwendet Spanner (§3.1). OpenFGA bietet `memory` (Standard, "Data is lost between server restarts", also: Daten gehen zwischen Serverneustarts verloren), PostgreSQL (mit optionaler Read Replica), MySQL und SQLite ([OpenFGA konfigurieren](https://openfga.dev/docs/getting-started/setup-openfga/configure-openfga)).
- **Conditions.** Eine Typbeschränkung wie `[user with non_expired_grant]` lässt ein Tupel nur zählen, wenn eine CEL-Bedingung gilt ([Conditions](https://openfga.dev/docs/modeling/conditions)). Das Tupel des Papers (§2.1) hat keine Bedingung.
- **Kontextuelle Tupel.** Tupel, die mit einer einzelnen Check-, ListObjects-, ListUsers- oder Expand-Anfrage gesendet und "not persisted in the datastore" (nicht im Datenspeicher persistiert) werden ([Konzepte](https://openfga.dev/docs/concepts), [kontextuelle Tupel](https://openfga.dev/docs/interacting/contextual-tuples)).
- **Wildcards.** `[user, user:*]` erlaubt eine öffentliche Freigabe ([Konfigurationssprache](https://openfga.dev/docs/configuration-language)); die Tupelgrammatik des Papers hat keine Wildcard (§2.1).
- **Stores und Modellversionen.** Ein Store enthält "one or more versions of an authorization model" (eine oder mehrere Versionen eines Autorisierungsmodells) und seine Tupel; "Store data cannot be shared across stores" (Store-Daten können nicht zwischen Stores geteilt werden) ([Konzepte](https://openfga.dev/docs/concepts)). Im Paper werden Konfigurationen in einer Tabelle mit der Namespace-ID als Schlüssel gespeichert, neben einem Changelog der Konfigurationsänderungen, und jede Anfrage wird zu einem Konfigurations-Snapshot-Zeitstempel ausgewertet (§3.1.3, §3.2.2). Eine Prüfung in OpenFGA kann die Modellversion nennen, die sie verwendet.
- **Kein Leopard.** Die hier zitierte Dokumentation beschreibt Check-Caches und Iterator-Caches, keinen vorberechneten Mengenindex wie Leopard (§3.2.4).
- **Listen-APIs.** `ListObjects`, `StreamedListObjects` und `ListUsers` liegen außerhalb der API des Papers (§2.4).
