Ory Keto est un serveur de permissions écrit en Go par Ory Corp. Son README le présente comme « an open source implementation of 'Zanzibar: Google's Consistent, Global Authorization System' » (une implémentation open source de « Zanzibar : le système d’autorisation global et cohérent de Google ») ([README](https://github.com/ory/keto)). Ory l’exploite également comme service géré : « Ory Permissions is powered by the open source Ory Keto » (Ory Permissions repose sur Ory Keto, open source) sur l’Ory Network (même README).

Keto n’a pas commencé comme un système de type Zanzibar. La conception Zanzibar est arrivée avec la v0.6.0-alpha.1 le 2021-04-07 ; les notes de version indiquent que l’ancien Keto a été déplacé dans une branche `legacy-0.5` et que « the architectures are vastly different » (les architectures sont très différentes) ([notes de version](https://github.com/ory/keto/releases/tag/v0.6.0-alpha.1)). Les réécritures de userset, écrites dans l’Ory Permission Language, ont suivi avec la v0.10.0-alpha.0 le 2022-09-27 ([notes de version](https://github.com/ory/keto/releases/tag/v0.10.0-alpha.0)).

## L’article et Keto côte à côte

| Dans l’article | Dans Ory Keto |

## L’exemple suivi en OPL

La figure 1 de l’article fait des propriétaires des éditeurs, des éditeurs des lecteurs, et des lecteurs du dossier parent des lecteurs du document (§2.3.1). En OPL, chaque espace de noms est une classe : `related` déclare les relations et les types de sujets qu’elles acceptent, et `permits` contient des fonctions qui renvoient vrai ou faux pour `ctx.subject`.

```ts
import { Namespace, SubjectSet, Context } from "@ory/keto-namespace-types"

class User implements Namespace {}

class Group implements Namespace {
  related: {
    members: User[]
  }
}

class Folder implements Namespace {
  related: {
    viewers: (User | SubjectSet<Group, "members">)[]
  }

  permits = {
    view: (ctx: Context): boolean => this.related.viewers.includes(ctx.subject),
  }
}

class Doc implements Namespace {
  related: {
    parents: Folder[]
    owners: User[]
    editors: (User | SubjectSet<Group, "members">)[]
    viewers: (User | SubjectSet<Group, "members">)[]
  }

  permits = {
    edit: (ctx: Context): boolean =>
      this.related.owners.includes(ctx.subject) ||
      this.related.editors.includes(ctx.subject),

    view: (ctx: Context): boolean =>
      this.related.viewers.includes(ctx.subject) ||
      this.permits.edit(ctx) ||
      this.related.parents.traverse((p) => p.permits.view(ctx)),
  }
}
```

`SubjectSet<Group, "members">` est le type OPL pour « les membres d’un groupe », le userset de l’article. Les relations sont toujours des tableaux, car « an object can have many subjects » (un objet peut avoir de nombreux sujets) ([OPL reference](https://www.ory.com/docs/keto/reference/ory-permission-language)).

Les cinq tuples de l’exemple suivi, dans la forme textuelle de Keto. Un sujet écrit `User:anne` est un ensemble de sujets (subject set) dont la relation est vide ; les tuples d’exemple des mainteneurs écrivent les utilisateurs de cette façon ([tuples.json](https://github.com/ory/keto/blob/master/contrib/rewrites-example/relation-tuples/tuples.json)).

```text
Doc:readme#owners@User:anne
Group:eng#members@User:beto
Doc:readme#viewers@Group:eng#members
Doc:readme#parents@Folder:A
Folder:A#viewers@User:chen
```

On remarque que seules les flèches sont stockées. Chaque étape qui fait d’un propriétaire un lecteur, ou d’un lecteur du dossier un lecteur du document, se trouve dans les fonctions `permits` et s’exécute au moment de la vérification.

- Chaque conteneur sert une Read API (port par défaut 4466), une Write API (4467) et une API de syntaxe OPL (4469), chacune en HTTP et en gRPC ([config schema](https://github.com/ory/keto/blob/master/embedx/config.schema.json)).
- « A good practice is to not expose the Write API at all to the public internet » (une bonne pratique consiste à ne pas exposer du tout la Write API sur l’internet public), et « The Read API should also be protected » (la Read API doit également être protégée) ([production guide](https://www.ory.com/docs/keto/guides/production)).
- Passage à l’échelle : « There are no additional requirements for scaling when self-hosting Ory Keto, just spin up another container! » (il n’y a pas d’exigence supplémentaire pour passer à l’échelle lorsqu’on héberge soi-même Ory Keto : il suffit de lancer un autre conteneur !) (même guide). Les conteneurs partagent la base de données.

## Cohérence

Le zookie de l’article permet à un client de demander une vérification « at a consistent snapshot no earlier than the given zookie » (sur un instantané cohérent qui n’est pas antérieur au zookie donné) (§2.4.4). L’API protobuf de Keto reprend la même idée dans ses noms de champs : `snaptoken` sur Check, Expand et ListRelationTuples, `snaptokens` sur TransactRelationTuples, et un indicateur `latest` pour une vérification de modification de contenu. Chacun de ces champs est documenté comme « not implemented yet and has no effect » (pas encore implémenté et sans effet) ([check_service.proto](https://github.com/ory/keto/blob/master/proto/ory/keto/relation_tuples/v1alpha2/check_service.proto)).

## Différences avec l’article

- **Pas de zookies.** Les champs existent ; le comportement, non (voir ci-dessus).
- **Pas de Watch.** L’API v1alpha2 comporte les services Check, Expand, Read, Write, Namespaces et Version, ainsi qu’un service de syntaxe OPL distinct (`opl/v1alpha1`), mais aucun flux de modifications ([répertoire proto](https://github.com/ory/keto/tree/master/proto/ory/keto)). Le Watch de l’article alimente des index secondaires et Leopard (§2.4.3, §3.2.4).
- **Pas de Leopard.** Aucun index d’ensembles dénormalisé n’est documenté.
- **Une syntaxe de langage de programmation.** OPL est un sous-ensemble de TypeScript afin que « users can get context help from their IDE » (les utilisateurs puissent obtenir une aide contextuelle de leur IDE) ([spécification OPL](https://github.com/ory/keto/blob/master/docs/ory_permission_language_spec.md)). La figure 1 de l’article écrit une configuration dans une syntaxe textuelle de type protocol buffer (§2.3.1) ; l’article ne nomme pas le format.
- **Stockage SQL.** Une base de données SQL partagée plutôt que Spanner (§3.1).
- **Profondeur des vérifications.** Les requêtes Check portent un `max_depth`, « The maximum depth to search for a relation » (la profondeur maximale de recherche d’une relation) ([check_service.proto](https://github.com/ory/keto/blob/master/proto/ory/keto/relation_tuples/v1alpha2/check_service.proto)).
