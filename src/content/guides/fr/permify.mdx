Permify est un service d’autorisation écrit en Go. Sa documentation le présente comme « an open-source authorization service for creating fine-grained and scalable authorization systems » (un service d’autorisation open source permettant de créer des systèmes d’autorisation fins et capables de passer à l’échelle), « inspired by Google's consistent, global authorization system, Google Zanzibar » (inspiré du système d’autorisation global et cohérent de Google, Google Zanzibar) ([Permify docs](https://fusionauth.io/permify-docs)). Vous décrivez les types d’entités et leurs relations dans le Permify Schema, vous écrivez les relations sous forme de tuples, et vous demandez à un serveur, via gRPC ou HTTP, si un sujet dispose d’une permission.

L’acquisition de Permify par FusionAuth a été annoncée le 2025-11-20 ([annonce de Permify](https://permify.co/post/fusionauth-acquires-permify/), [annonce de FusionAuth](https://fusionauth.io/blog/fusionauth-acquires-permify)). FusionAuth nomme désormais le produit « FusionAuth FGA by Permify » ([billet de support de FusionAuth](https://fusionauth.io/blog/how-to-get-support-for-fusionauth-fga-permify)), et la documentation se trouve à [fusionauth.io/permify-docs](https://fusionauth.io/permify-docs). Le billet de Permify affirme que « The core Permify project remains open source and will continue to live on GitHub. » (le projet Permify de base reste open source et continuera d’être hébergé sur GitHub).

## L’article et Permify côte à côte

Chaque ligne nomme un concept de l’article et l’élément le plus proche que documente Permify. Lorsque Permify n’a rien de comparable, la cellule le précise.

| Dans l’article | Dans Permify |
| --- | --- |
| Configuration d’espace de noms (§2.3) | Un bloc `entity` dans le Permify Schema, avec `relation`, `permission` (ou son synonyme `action`), `attribute` et `rule` ([modeling](https://fusionauth.io/permify-docs/getting-started/modeling)) |
| Tuple de relation `object#relation@user` (§2.1) | Relational tuple `entity#relation@subject`, par exemple `doc:readme#owner@user:anne` ([storing data](https://fusionauth.io/permify-docs/getting-started/sync-data)) |
| `_this` | Les tuples stockés d’une `relation` ; une permission les inclut en nommant la relation |
| `computed_userset` | Nommer une autre relation ou permission de la même entité, comme `edit` dans `view = viewer or edit` |
| `tuple_to_userset` | Parcours par point à travers une relation, comme `parent.view` |
| Union, intersection, exclusion | `or`, `and`, `not` |
| Zookie (§2.2, §2.4) | Snap token, le champ `snap_token` ([snap tokens](https://fusionauth.io/permify-docs/operations/snap-tokens)) |
| Check (§2.4.4) | `Permission.Check`, plus `BulkCheck` ([service.proto](https://github.com/Permify/permify/blob/master/proto/base/v1/service.proto)) |
| Read (§2.4.1) | `Data.ReadRelationships`, plus `ReadAttributes` |
| Write (§2.4.2) | `Data.Write`, `WriteRelationships`, `Delete`, `DeleteRelationships` |
| Watch (§2.4.3) | `Watch.Watch`, un flux côté serveur ([Watch operations](https://fusionauth.io/permify-docs/operations/watch)) |
| Expand (§2.4.5) | `Permission.Expand` |
| Leopard (§3.2.4) | Aucun équivalent documenté |
| Spanner (§3.1) | PostgreSQL, ou un moteur en mémoire (la valeur par défaut de la configuration) ([configuration](https://fusionauth.io/permify-docs/setting-up/configuration)) |

Permify propose aussi des appels de recherche que l’article ne décrit pas : `LookupEntity`, `LookupSubject` et `SubjectPermission`.

## L’exemple suivi en Permify Schema

La figure 1 de l’article dote les documents de trois relations concentriques : les propriétaires sont éditeurs, les éditeurs sont lecteurs, et les lecteurs du dossier parent sont lecteurs du document (§2.3.1). Voici ce modèle avec les types de l’exemple suivi, en Permify Schema.

```text
entity user {}

entity group {
    relation member @user
}

entity folder {
    relation viewer @user @group#member

    permission view = viewer
}

entity doc {
    relation parent @folder
    relation owner @user
    relation editor @user @group#member
    relation viewer @user @group#member

    permission edit = owner or editor
    permission view = viewer or edit or parent.view
}
```

`@group#member` permet à une relation de contenir un userset : « tous ceux qui sont membres de ce groupe ». `parent.view` suit la relation `parent` jusqu’au dossier et y évalue la permission `view` du dossier ; la documentation indique que « The same traversal rule applies to both `relation.userset` and `relation.permission` » (la même règle de parcours s’applique à `relation.userset` et à `relation.permission`) ([modeling](https://fusionauth.io/permify-docs/getting-started/modeling)).

L’exemple suivi se compose de cinq tuples :

```text
doc:readme#owner@user:anne
group:eng#member@user:beto
doc:readme#viewer@group:eng#member
doc:readme#parent@folder:A
folder:A#viewer@user:chen
```

## Architecture

Comment les serveurs Permify se partagent-ils le travail, et où résident les tuples ?

Les éléments, chacun d’après la documentation :

- Les serveurs écoutent par défaut sur le port HTTP 3476 et le port gRPC 3478 ([configuration](https://fusionauth.io/permify-docs/setting-up/configuration)). La section base de données accepte des URI `writer` et `reader` distinctes.
- Chaque pod conserve un cache [Ristretto](https://github.com/dgraph-io/ristretto) local au processus pour les résultats de vérification ; « there is no shared cache layer » (il n’y a pas de couche de cache partagée) ([cache](https://fusionauth.io/permify-docs/operations/cache)).
- Avec `distributed.enabled`, les pods hachent chaque requête sur un anneau de hachage cohérent, de sorte que « subsequent API calls with the same hash will retrieve the response from the instance 2, regardless of which instance that API called from » (les appels d’API ultérieurs ayant le même hachage obtiendront la réponse de l’instance 2, quelle que soit l’instance depuis laquelle l’API a été appelée). Un disjoncteur (circuit breaker) interrompt les appels à la base de données lorsqu’elle est indisponible.
- PostgreSQL stocke les tuples avec MVCC : Permify crée « a separate database snapshot for each write and delete operation » (un instantané distinct de la base de données pour chaque opération d’écriture et de suppression), et un ramasse-miettes facultatif supprime les anciennes versions.
- Chaque flux Watch « opens a long-lived connection with a continuous polling loop against the database » (ouvre une connexion de longue durée avec une boucle d’interrogation continue de la base de données) ([Watch operations](https://fusionauth.io/permify-docs/operations/watch)).

## Cohérence

Le snap token de Permify joue le rôle du zookie. Une écriture le renvoie ; le client le stocke avec la ressource et le renvoie sous la forme `snap_token` dans les vérifications ultérieures. La documentation le décrit comme « a token that consists of an encoded timestamp » (un jeton constitué d’un horodatage encodé), comparé lors des vérifications d’accès « to ensure that the snapshot of the access control is at least as fresh as the resource timestamp » (pour garantir que l’instantané du contrôle d’accès est au moins aussi frais que l’horodatage de la ressource) ([snap tokens](https://fusionauth.io/permify-docs/operations/snap-tokens)). C’est la garantie de l’article pour une vérification portant un zookie : « a consistent snapshot no earlier than » (un instantané cohérent qui n’est pas antérieur au) zookie donné (§2.4.4).

Comment une vérification effectuée après une modification de partage voit-elle cette modification ?

On remarque le comportement en l’absence de jeton. L’article laisse Zanzibar « choose a reasonably recent snapshot, possibly offering a lower-latency response » (choisir un instantané raisonnablement récent, offrant éventuellement une réponse de plus faible latence) (§2.4.1). Permify lit plutôt l’identifiant de la dernière transaction dans sa table `transactions` et évalue sur cet instantané ; le résultat est mis en cache sous une clé qui contient cet identifiant ([snap tokens](https://fusionauth.io/permify-docs/operations/snap-tokens)). La clé de cache est `check_{tenant_id}_{schema_version}:{snapshot_token}:{check_request}` ([cache](https://fusionauth.io/permify-docs/operations/cache)), de sorte qu’une nouvelle écriture produit de nouvelles clés au lieu d’invalider les anciennes.

## Différences avec l’article

- **Attributs et règles.** Le Permify Schema ajoute `attribute` et `rule` pour des vérifications fondées sur des attributs, comme `permission view = check_ip_range(ip_range) or admin` ([modeling](https://fusionauth.io/permify-docs/getting-started/modeling)). Les réécritures de Zanzibar ne portent que sur des tuples (§2.3.1).
- **Tuples contextuels.** Des relations « dynamically added to permission request operations » (ajoutées dynamiquement aux opérations de requête de permission) sont évaluées avec les relations stockées et ne sont jamais écrites ([contextual tuples](https://fusionauth.io/permify-docs/operations/contextual-tuples)).
- **Locataires.** Un service `Tenancy` crée, liste et supprime des locataires (tenants) ([service.proto](https://github.com/Permify/permify/blob/master/proto/base/v1/service.proto)) ; l’article ne connaît pas de notion de locataire.
- **Stockage.** PostgreSQL avec des instantanés MVCC, au lieu de Spanner, dont le mécanisme TrueTime horodate chaque écriture d’ACL (§2.2, §3.1). Le cache distribué fonctionne « across availability zones (within an AWS region) » (entre zones de disponibilité (au sein d’une région AWS)) ([cache](https://fusionauth.io/permify-docs/operations/cache)).
- **Pas d’index dénormalisé.** L’article répond aux vérifications sur des groupes profondément imbriqués avec Leopard (§3.2.4). Permify documente la mise en cache des résultats et le hachage cohérent, et non un index d’ensembles.
- **Recherches.** `LookupEntity` et `LookupSubject` répondent aux questions « quelles ressources » et « quels sujets », que l’API de l’article ne couvre pas.
