SpiceDB est une base de données open source qui stocke des relations et répond à des requêtes de permission portant sur celles-ci, dans le style de Zanzibar. Elle est écrite en Go, distribuée sous licence Apache-2.0 et maintenue par AuthZed, Inc. ([dépôt](https://github.com/authzed/spicedb)). Sa première version GitHub, v1.0.0, est datée du 2021-09-30. AuthZed vend également des services gérés et commerciaux qui s’articulent autour d’elle ; ils sont désignés comme tels ci-dessous. La plupart des sources de cette page sont la documentation et le blog d’AuthZed.

## Termes de l’article et termes de SpiceDB

| Dans l’article | Dans SpiceDB |
| --- | --- |
| Configuration d’espace de noms (§2.3) | Une `definition` dans le schéma ([schema docs](https://authzed.com/docs/spicedb/concepts/schema)) |
| Tuple de relation `object#relation@user` (§2.1) | Relationship `resource#relation@subject`, p. ex. `document:readme#editor@user:emilia` ([relationships](https://authzed.com/docs/spicedb/concepts/relationships)) |
| `_this` (§2.3.1) | Une `relation` avec ses types de sujets autorisés ; les relations stockées pour celle-ci |
| `computed_userset` | Nommer une autre relation ou permission dans une expression `permission` |
| `tuple_to_userset` | La flèche `parent->view` (alias `parent.any(view)`) |
| `union` / `intersection` / `exclusion` | `+` / `&` / `-` |
| Zookie (§2.4) | ZedToken ([consistency](https://authzed.com/docs/spicedb/concepts/consistency)) |
| Check (§2.4.4) | `CheckPermission`, `CheckBulkPermissions` |
| Read (§2.4.1) | `ReadRelationships` |
| Write (§2.4.2) | `WriteRelationships`, `DeleteRelationships` |
| Watch (§2.4.3) | `Watch` |
| Expand (§2.4.5) | `ExpandPermissionTree` |
| Absent de l’API de l’article | `LookupResources`, `LookupSubjects`, `ImportBulkRelationships`, `ExportBulkRelationships` |
| Leopard (§3.2.4) | AuthZed Materialize, un service commercial pour les clients d’AuthZed Dedicated ([docs](https://authzed.com/docs/materialize/getting-started/overview)) |
| Spanner (§3) | CockroachDB, Cloud Spanner, PostgreSQL, MySQL, memdb ([datastores](https://authzed.com/docs/spicedb/concepts/datastores)) |

Les noms d’API proviennent des fichiers de protocole d’AuthZed : [`permission_service.proto`](https://github.com/authzed/api/blob/main/authzed/api/v1/permission_service.proto) et [`watch_service.proto`](https://github.com/authzed/api/blob/main/authzed/api/v1/watch_service.proto).

## L’exemple suivi sous forme de schéma

La figure 1 de l’article fait des propriétaires des éditeurs, des éditeurs des lecteurs, et des lecteurs du dossier parent des lecteurs du document (§2.3.1). Dans SpiceDB, les relations stockées et les permissions calculées sont déclarées séparément : les lignes `relation` indiquent qui peut être écrit dans une relation, les lignes `permission` indiquent comment l’accès est calculé.

```text
definition user {}

definition group {
    relation member: user
}

definition folder {
    relation viewer: user | group#member
    permission view = viewer
}

definition doc {
    relation parent: folder
    relation owner: user
    relation editor: user | group#member
    relation viewer: user | group#member

    permission edit = owner + editor
    permission view = viewer + edit + parent->view
}
```

<Callout kind="note" title="Non soumis à un validateur">

Ce schéma n’utilise que des constructions présentées sur la [page du langage de schéma](https://authzed.com/docs/spicedb/concepts/schema) de SpiceDB au 2026-11-13 : `definition`, `relation` avec `user | group#member`, `permission` avec `+` et `->`. Il n’a été soumis ni à `zed` ni au SpiceDB Playground.

</Callout>

Les relations pour Anne, Beto et Chen :

```text
doc:readme#owner@user:anne
doc:readme#parent@folder:A
group:eng#member@user:beto
doc:readme#viewer@group:eng#member
folder:A#viewer@user:chen
```

On remarque qu’aucune relation ne mentionne `view` ni `edit` : ce sont deux permissions, calculées au moment de la vérification à partir du schéma, de même que les règles de réécriture de l’article sont calculées et non stockées (§2.3.1).

## Architecture

Comment un déploiement SpiceDB répond-il à une vérification ? AuthZed décrit SpiceDB comme « fundamentally a gRPC service » (fondamentalement un service gRPC) doté d’une passerelle HTTP facultative ([billet sur l’architecture, 2021-11-17](https://authzed.com/blog/spicedb-architecture)). Un nœud décompose une requête en questions plus petites et les transmet à d’autres nœuds, un processus qu’il appelle dispatch ; chaque nœud conserve « an in-memory cache of permissions queries it has resolved in the past » (un cache en mémoire des requêtes de permission qu’il a résolues par le passé) ([performance docs](https://authzed.com/docs/spicedb/ops/performance)). Un hachage cohérent envoie « the same (sub-)requests to the same server » (les mêmes (sous-)requêtes au même serveur) ([billet sur l’architecture](https://authzed.com/blog/spicedb-architecture)). Tous les nœuds partagent une même base de données. Materialize, s’il est utilisé, précalcule des permissions choisies, et SpiceDB « can dispatch sub-queries to Materialize » (peut transmettre des sous-requêtes à Materialize) ([performance docs](https://authzed.com/docs/spicedb/ops/performance)).

## Cohérence : ZedTokens et zookies

AuthZed présente le ZedToken comme « the SpiceDB equivalent of Google Zanzibar's Zookie concept which protects users from the New Enemy Problem » (l’équivalent dans SpiceDB du concept de zookie de Google Zanzibar, qui protège les utilisateurs du problème du « nouvel ennemi ») ([consistency docs](https://authzed.com/docs/spicedb/concepts/consistency)). Les écritures en renvoient un (`written_at`), de même que les vérifications (`checked_at`). Une requête peut choisir l’un de quatre modes :

| Mode | Ce qu’il demande | Équivalent dans l’article |
| --- | --- | --- |
| `minimize_latency` | Ce à quoi le serveur peut répondre le plus vite | Pas de zookie : « a reasonably recent snapshot » (un instantané raisonnablement récent) (§2.4.1) |
| `at_least_as_fresh` + ZedToken | Un instantané qui n’est pas plus ancien que le jeton | Un zookie dans une vérification ou une lecture (§2.2, §2.4) |
| `at_exact_snapshot` + ZedToken | Exactement l’instantané du jeton | Un zookie de lecture réutilisé pour obtenir « the same snapshot as a previous read » (le même instantané qu’une lecture précédente) (§2.4.1) |
| `fully_consistent` | Les données les plus récentes | Pas d’équivalent direct ; la vérification de modification de contenu de l’article est évaluée au dernier instantané (§2.4.4) |

Sur CockroachDB, la documentation avertit que `fully_consistent` « does not guarantee read-after-write consistency » (ne garantit pas la cohérence lecture après écriture), car les horloges des nœuds peuvent différer jusqu’au `max_offset` du cluster ; elle recommande plutôt un ZedToken avec `at_least_as_fresh` ([consistency docs](https://authzed.com/docs/spicedb/concepts/consistency)).

`fully_consistent` est la valeur par défaut pour `WriteRelationships`, `DeleteRelationships`, `ReadSchema` et `WriteSchema` ; `minimize_latency` est la valeur par défaut pour toutes les autres API ([consistency docs](https://authzed.com/docs/spicedb/concepts/consistency)).

Dans l’article, le zookie stocké avec le contenu provient d’une vérification de modification de contenu (§2.2, §2.4.4). La documentation de SpiceDB indique que, lorsqu’une ressource change, « a new ZedToken is either returned or it should be requested by performing a check with full consistency » (un nouveau ZedToken est soit renvoyé, soit doit être demandé en effectuant une vérification en cohérence complète) ([consistency docs](https://authzed.com/docs/spicedb/concepts/consistency)) ; les deux voies existent donc.

`Watch` utilise aussi les ZedTokens : une requête peut partir d’un `optional_start_cursor`, et chaque réponse porte un `changes_through` à partir duquel reprendre, ce qui correspond au zookie de pulsation de l’article (§2.4.3) ([`watch_service.proto`](https://github.com/authzed/api/blob/main/authzed/api/v1/watch_service.proto)).

## Différences avec l’article

- **Stockage.** L’article stocke tout dans Spanner (§3.1). SpiceDB dispose de bases de données interchangeables : CockroachDB (« high throughput and/or multi-region », haut débit et/ou multirégion), Cloud Spanner, PostgreSQL (« single-region », monorégion), MySQL (« Not recommended », déconseillé) et memdb (développement local et tests) ([datastores](https://authzed.com/docs/spicedb/concepts/datastores)).
- **Relations et permissions sont séparées.** L’article rattache une réécriture de userset à une relation (§2.3.1). SpiceDB sépare les `relation` stockées des `permission` calculées ([schema](https://authzed.com/docs/spicedb/concepts/schema)).
- **Caveats.** Les relations peuvent porter une expression CEL nommée, rattachée dans le schéma avec `with` (p. ex. `relation viewer: user | user with ip_allowlist`) ([caveats](https://authzed.com/docs/spicedb/concepts/caveats)). Le tuple de l’article (§2.1) n’a pas de tel champ.
- **Jokers.** `relation viewer: user | user:*` permet une attribution publique ([schema](https://authzed.com/docs/spicedb/concepts/schema)). La grammaire des tuples de l’article prévoit un identifiant d’utilisateur ou un userset (§2.1), sans joker.
- **Flèche d’intersection.** `.all()` exige que chaque objet lié accorde la permission ([schema](https://authzed.com/docs/spicedb/concepts/schema)). Les trois feuilles de réécriture de l’article (§2.3.1) n’ont pas de forme équivalente.
- **Obsolescence par défaut.** L’article choisit l’obsolescence par défaut de manière adaptative à partir de statistiques de lectures hors zone (§3.2.1), et arrondit séparément les horodatages d’évaluation vers le haut « to a coarse granularity, such as one or ten seconds » (à une granularité grossière, par exemple une ou dix secondes) afin que les entrées de cache soient partagées (§3.2.5). SpiceDB n’a que l’arrondi : il regroupe les révisions des requêtes dans des fenêtres fixées par `--datastore-revision-quantization-interval` afin que les entrées de cache puissent être réutilisées ; AuthZed indique « the default is 5s » (la valeur par défaut est de 5 s) ([billet sur la mise en cache des points chauds, 2023-05-10](https://authzed.com/blog/hotspot-caching-in-google-zanzibar-and-spicedb)), ce qui correspond à `RevisionQuantization: 5 * time.Second` dans le [code source](https://github.com/authzed/spicedb/blob/main/pkg/cmd/datastore/dsconfig/config.go).
- **API de recherche.** `LookupResources` et `LookupSubjects` répondent aux questions « quelles ressources » et « quels sujets » ([`permission_service.proto`](https://github.com/authzed/api/blob/main/authzed/api/v1/permission_service.proto)). L’API de l’article comporte Read, Write, Watch, Check et Expand (§2.4).
- **Leopard.** « AuthZed Materialize takes inspiration from the Leopard index component described in the Zanzibar paper » (AuthZed Materialize s’inspire du composant d’index Leopard décrit dans l’article Zanzibar) ([Materialize docs](https://authzed.com/docs/materialize/getting-started/overview)). Il fait partie de l’offre payante d’AuthZed, et non de SpiceDB open source : la documentation indique que sa fonctionnalité Accelerated Queries est « generally available to users of AuthZed Dedicated » (disponible de manière générale pour les utilisateurs d’AuthZed Dedicated).
