Zanzibar stocke les permissions sous forme de *tuples de relation* : un fait par ligne, qui se lit « cet utilisateur a cette relation avec cet objet ». Tout le reste de cette page (règles de réécriture, Check et Expand) est calculé à partir de ces lignes.

L’exemple suivi : Anne, Beto et Chen (`user:anne`, `user:beto`, `user:chen`) ; le document `doc:readme` dans `folder:A` ; le groupe `group:eng`. Anne est propriétaire du readme, Beto fait partie de eng, les membres de eng peuvent voir le readme, et Chen peut voir le dossier A.

## La grammaire

L’article (§2.1) donne la notation textuelle sous forme de quatre règles :

```text
⟨tuple⟩   ::= ⟨object⟩ ‘#’ ⟨relation⟩ ‘@’ ⟨user⟩
⟨object⟩  ::= ⟨namespace⟩ ‘:’ ⟨object_id⟩
⟨user⟩    ::= ⟨user_id⟩ | ⟨userset⟩
⟨userset⟩ ::= ⟨object⟩ ‘#’ ⟨relation⟩
```

Un tuple comporte trois parties. L’*objet* est un espace de noms suivi d’un identifiant, comme `doc:readme`. La *relation* est un nom défini par l’espace de noms, comme `owner` ou `viewer`. L’*utilisateur* est soit un identifiant d’utilisateur unique, soit un *userset*. Dans l’article, un identifiant d’utilisateur est un entier ; ce site écrit `user:anne` pour que l’exemple reste lisible.

Il dit une seule chose : Anne a la relation `owner` avec `doc:readme`. L’article énumère les clés primaires qui identifient un tuple : espace de noms, identifiant d’objet, relation et utilisateur.

## Usersets : un tuple qui pointe vers un groupe

La quatrième règle de la grammaire est la plus intéressante. Un userset est lui-même un objet suivi d’une relation : `group:eng#member` signifie « tout utilisateur qui a la relation `member` avec `group:eng` ». Lorsque l’utilisateur d’un tuple est un userset, une seule ligne accorde quelque chose à tout un ensemble d’utilisateurs, et cet ensemble est défini par d’autres lignes.

Comment un seul tuple donne-t-il à chaque membre de eng l’accès au readme ?

Aucune ligne ne mentionne Beto et le readme ensemble. Beto est lecteur parce qu’il appartient à l’ensemble vers lequel pointe le second tuple. Ajoutez un membre à eng et ce membre pourra voir le readme sans aucune modification de l’ACL du readme.

Le même mécanisme s’imbrique. Le membre d’un groupe peut être un autre userset, par exemple `group:eng#member@group:sre#member` (une sous-équipe hypothétique, qui ne fait pas partie de l’exemple suivi), et l’appartenance traverse alors autant de niveaux que les tuples en décrivent. L’article le dit en une ligne : « a ⟨*userset*⟩ allows ACLs to refer to groups and thus supports representing nested group membership » (un ⟨*userset*⟩ permet aux ACL de faire référence à des groupes et permet ainsi de représenter l’appartenance à des groupes imbriqués) (§2.1). Il en explique aussi l’intérêt : modéliser avec des tuples plutôt qu’avec des ACL par objet « allows us to unify the concepts of ACLs and groups » (nous permet d’unifier les concepts d’ACL et de groupe) (§2.1). Un groupe n’est qu’un objet dont la relation `member` est une ACL.

Le tableau 1 de l’article énumère quatre exemples de tuples. Avec les utilisateurs 10 et 11 renommés Anne et Beto, et un tuple ajouté pour Chen, ce sont :

| Tuple | Se lit |
| --- | --- |
| `doc:readme#owner@user:anne` | Anne est propriétaire du readme |
| `group:eng#member@user:beto` | Beto est membre de eng |
| `doc:readme#viewer@group:eng#member` | Les membres de eng sont lecteurs du readme |

L’arête `parent` ne dit rien de l’accès. Comme l’indique l’article, certaines relations « only define abstract relations between objects. These abstract relations may indirectly affect access control given userset rewrite rules specified in namespace configs » (ne définissent que des relations abstraites entre objets. Ces relations abstraites peuvent affecter indirectement le contrôle d’accès, compte tenu des règles de réécriture de userset spécifiées dans les configurations d’espaces de noms) (§2.1). La possibilité pour Chen de voir le readme dépend d’une telle règle, objet de la section suivante.

## Configuration des espaces de noms

Avant de stocker des tuples, un client configure un *espace de noms* tel que `doc` ou `folder` (§2.3). La configuration énumère les relations de l’espace de noms, chacune avec un nom et une *configuration de relation*, ainsi que des paramètres de stockage : réglages de fragmentation et encodage des identifiants d’objets.

Les tuples seuls ne définissent pas l’ACL effective. De nombreux clients veulent que chaque éditeur soit aussi lecteur. Stocker un tuple `viewer` supplémentaire pour chaque éditeur de chaque objet serait, selon les termes de l’article, « wasteful and make it hard to make modifications across all objects » (source de gaspillage et rendrait difficiles les modifications portant sur l’ensemble des objets) (§2.3.1). À la place, une configuration de relation peut porter une *règle de réécriture de userset* : une fonction qui prend un identifiant d’objet et renvoie un arbre d’expression de userset.

Voici la figure 1 de l’article, telle quelle :

```text
name: "doc"

relation { name: "owner" }

relation {
 name: "editor"
 userset_rewrite {
  union {
   child { _this {} }
   child { computed_userset { relation: "owner" } }
} } }

relation {
 name: "viewer"
 userset_rewrite {
  union {
   child { _this {} }
   child { computed_userset { relation: "editor" } }
   child { tuple_to_userset {
     tupleset { relation: "parent" }
     computed_userset {
       object: $TUPLE_USERSET_OBJECT  # parent folder
       relation: "viewer"
   } } }
} } }
```

> Figure 1: Simple namespace configuration with concentric relations on documents. All owners are editors, and all editors are viewers. Further, viewers of the parent folder are also viewers of the document.
>
> (Figure 1 : configuration d’espace de noms simple avec des relations concentriques sur des documents. Tous les propriétaires sont des éditeurs, et tous les éditeurs sont des lecteurs. En outre, les lecteurs du dossier parent sont également lecteurs du document.)

Les feuilles d’un arbre de réécriture sont de trois sortes (§2.3.1) :

| Feuille | Ce qu’elle renvoie | Dans la figure 1 |
| --- | --- | --- |
| `_this` | Les utilisateurs des tuples stockés pour cet objet et cette relation, y compris les usersets vers lesquels pointent ces tuples. Comportement par défaut lorsqu’une relation n’a pas de règle. | Les tuples `viewer` stockés sur `doc:readme` |
| `computed_userset` | Le userset d’une autre relation sur le même objet. | `editor` sur le même document ; pour `editor`, `owner` |
| `tuple_to_userset` | Lit un *ensemble de tuples* à partir de l’objet, puis calcule un userset à partir de chaque tuple trouvé. | Lire les tuples `parent` du document, puis prendre `viewer` sur chaque dossier parent |

Les feuilles se combinent par union, intersection et exclusion (§2.3.1). La figure 1 n’utilise que l’union. Une intersection exigerait qu’un utilisateur appartienne à chaque enfant, par exemple « les éditeurs qui font aussi partie de eng » ; une exclusion retirerait un ensemble, par exemple « les lecteurs, sauf une liste bloquée ». Ces deux exemples sont des illustrations et ne proviennent pas de l’article.

## Check comme recherche dans un graphe

Une requête Check désigne un userset ⟨*object#relation*⟩ et un utilisateur, et demande si l’utilisateur en fait partie (§2.4.4). Sans règles de réécriture, l’article écrit l’évaluation sous forme d’une formule récursive (§3.2.3) : l’utilisateur appartient à ⟨*object#relation*⟩ s’il existe un tuple ⟨*object#relation@U*⟩, ou s’il existe un tuple ⟨*object#relation@U′*⟩ où U′ est un userset auquel l’utilisateur appartient. L’article appelle cette récursion « pointer chasing » (poursuite de pointeurs). Les règles de réécriture « are also translated to boolean expressions as part of check evaluation » (sont également traduites en expressions booléennes lors de l’évaluation de la vérification) (§3.2.3), si bien que l’arbre d’expression ci-dessus devient un OU de trois branches.

La question des quatre figures suivantes : Chen peut-il voir `doc:readme` ? Chaque vue utilise le même graphe et met en évidence les arêtes que lit la branche en cours. La configuration de l’espace de noms `folder` ne figure pas dans l’article ; ces vues supposent que `folder#viewer` n’a pas de règle de réécriture et se réduit donc à `_this`.

<Callout kind="note" title="Des vues, pas une chronologie">

Les vues avancent une branche à la fois afin que chacune puisse se lire isolément. Zanzibar n’attend pas ainsi : il évalue « all leaf nodes of the boolean expression tree concurrently » (tous les nœuds feuilles de l’arbre d’expression booléenne simultanément) et annule le reste d’un sous-arbre dès qu’un nœud en décide le résultat (§3.2.3).

</Callout>

## Read et Expand

Deux appels d’API examinent les mêmes données à des niveaux différents.

**Read** (§2.4.1) renvoie uniquement les tuples stockés. Une requête désigne un ou plusieurs *ensembles de tuples* : une clé de tuple unique, ou tous les tuples d’un identifiant d’objet ou d’un userset dans un espace de noms, éventuellement restreints à une relation. L’article est explicite : « Read results only depend on contents of relation tuples and do not reflect userset rewrite rules » (les résultats de Read dépendent uniquement du contenu des tuples de relation et ne reflètent pas les règles de réécriture de userset) (§2.4.1). Lire `doc:readme` avec la relation `viewer` dans l’exemple suivi renvoie une ligne :

```text
doc:readme#viewer@group:eng#member
```

Anne est absente alors que tout propriétaire est lecteur, et Chen est absent alors qu’il peut voir le readme.

**Expand** (§2.4.5) « follows indirect references expressed through userset rewrite rules » (suit les références indirectes exprimées par les règles de réécriture de userset). Il renvoie un *arbre de userset* : les feuilles sont des identifiants d’utilisateurs ou des usersets qui pointent vers d’autres paires ⟨*object#relation*⟩, et les nœuds intermédiaires sont des unions, intersections ou exclusions.

Les deux feuilles sont en pointillés. Selon le §2.4.5, une feuille peut être un userset qui pointe ailleurs ; un client qui veut chaque individu (Beto, Chen) développe donc ces feuilles à leur tour.
