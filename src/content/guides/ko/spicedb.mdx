SpiceDB는 Zanzibar 방식으로 관계를 저장하고 그에 대한 권한 쿼리에 답하는 오픈 소스 데이터베이스다. Go로 작성되었고, Apache-2.0 라이선스이며, AuthZed, Inc.가 유지 관리한다([저장소](https://github.com/authzed/spicedb)). 첫 GitHub 릴리스 v1.0.0의 날짜는 2021-09-30이다. AuthZed는 그 주변의 관리형 서비스와 상용 서비스도 판매하며, 아래에서는 그런 것을 그렇다고 밝혀 둔다. 이 페이지의 출처 대부분은 AuthZed 자신의 문서와 블로그다.

## 논문의 용어와 SpiceDB의 용어

| 논문 | SpiceDB |
| --- | --- |
| 네임스페이스 설정 (§2.3) | 스키마 안의 `definition`([스키마 문서](https://authzed.com/docs/spicedb/concepts/schema)) |
| 관계 튜플 `object#relation@user` (§2.1) | 관계(relationship) `resource#relation@subject`. 예: `document:readme#editor@user:emilia`([relationships](https://authzed.com/docs/spicedb/concepts/relationships)) |
| `_this` (§2.3.1) | 허용되는 주체 타입을 가진 `relation`, 그리고 그에 대해 저장된 관계 |
| `computed_userset` | `permission` 표현식 안에서 다른 관계나 권한의 이름을 쓰는 것 |
| `tuple_to_userset` | 화살표 `parent->view`(별칭 `parent.any(view)`) |
| `union` / `intersection` / `exclusion` | `+` / `&` / `-` |
| zookie (§2.4) | ZedToken([consistency](https://authzed.com/docs/spicedb/concepts/consistency)) |
| Check (§2.4.4) | `CheckPermission`, `CheckBulkPermissions` |
| Read (§2.4.1) | `ReadRelationships` |
| Write (§2.4.2) | `WriteRelationships`, `DeleteRelationships` |
| Watch (§2.4.3) | `Watch` |
| Expand (§2.4.5) | `ExpandPermissionTree` |
| 논문의 API에 없음 | `LookupResources`, `LookupSubjects`, `ImportBulkRelationships`, `ExportBulkRelationships` |
| Leopard (§3.2.4) | AuthZed Materialize. AuthZed Dedicated 고객을 위한 상용 서비스([문서](https://authzed.com/docs/materialize/getting-started/overview)) |
| Spanner (§3) | CockroachDB, Cloud Spanner, PostgreSQL, MySQL, memdb([datastores](https://authzed.com/docs/spicedb/concepts/datastores)) |

API 이름은 AuthZed의 프로토콜 파일 [`permission_service.proto`](https://github.com/authzed/api/blob/main/authzed/api/v1/permission_service.proto)와 [`watch_service.proto`](https://github.com/authzed/api/blob/main/authzed/api/v1/watch_service.proto)에서 가져왔다.

## 스키마로 쓴 예제

논문의 그림 1은 소유자를 편집자로, 편집자를 열람자로, 상위 폴더의 열람자를 문서의 열람자로 만든다(§2.3.1). SpiceDB에서는 저장되는 관계와 계산되는 권한을 따로 선언한다. `relation` 줄은 관계에 누구를 쓸 수 있는지를, `permission` 줄은 접근이 어떻게 계산되는지를 말한다.

```text
definition user {}

definition group {
    relation member: user
}

definition folder {
    relation viewer: user | group#member
    permission view = viewer
}

definition doc {
    relation parent: folder
    relation owner: user
    relation editor: user | group#member
    relation viewer: user | group#member

    permission edit = owner + editor
    permission view = viewer + edit + parent->view
}
```

<Callout kind="note" title="검증기로 실행하지 않음">

이 스키마는 2026-11-13 기준으로 SpiceDB의 [스키마 언어 페이지](https://authzed.com/docs/spicedb/concepts/schema)에 나오는 구문만 사용한다. `definition`, `user | group#member`를 가진 `relation`, `+`와 `->`를 가진 `permission`이다. `zed`나 SpiceDB Playground로 실행하지는 않았다.

</Callout>

Anne, Beto, Chen의 관계:

```text
doc:readme#owner@user:anne
doc:readme#parent@folder:A
group:eng#member@user:beto
doc:readme#viewer@group:eng#member
folder:A#viewer@user:chen
```

각 사람을 readme에 대한 `view`로 이끄는 저장된 관계는 무엇인가?

## 아키텍처

SpiceDB 배포 하나는 검사에 어떻게 답하는가? AuthZed는 SpiceDB를 선택적인 HTTP 게이트웨이를 가진 "fundamentally a gRPC service"(근본적으로 gRPC 서비스)로 설명한다([아키텍처 글, 2021-11-17](https://authzed.com/blog/spicedb-architecture)). 노드는 요청을 더 작은 질문들로 나누어 다른 노드에 포워딩하며, 이 과정을 디스패치라고 부른다. 각 노드는 "an in-memory cache of permissions queries it has resolved in the past"(과거에 해결한 권한 쿼리의 인메모리 캐시)를 유지한다([performance 문서](https://authzed.com/docs/spicedb/ops/performance)). 일관된 해시가 "the same (sub-)requests to the same server"(같은 (하위) 요청을 같은 서버로) 보낸다([아키텍처 글](https://authzed.com/blog/spicedb-architecture)). 모든 노드는 데이터 저장소 하나를 공유한다. Materialize를 쓰는 경우, 선택한 권한을 미리 계산하며, SpiceDB는 "can dispatch sub-queries to Materialize"(하위 쿼리를 Materialize로 디스패치할 수 있다)([performance 문서](https://authzed.com/docs/spicedb/ops/performance)).

## 일관성: ZedToken과 zookie

AuthZed는 ZedToken을 "the SpiceDB equivalent of Google Zanzibar's Zookie concept which protects users from the New Enemy Problem"(사용자를 New Enemy 문제로부터 보호하는 Google Zanzibar의 Zookie 개념에 해당하는 SpiceDB의 것)이라고 부른다([consistency 문서](https://authzed.com/docs/spicedb/concepts/consistency)). 쓰기는 ZedToken을 반환하고(`written_at`), 검사도 반환한다(`checked_at`). 요청은 네 가지 모드 중 하나를 고를 수 있다.

| 모드 | 요청하는 것 | 논문의 대응 |
| --- | --- | --- |
| `minimize_latency` | 서버가 가장 빨리 답할 수 있는 것 | zookie 없음: "a reasonably recent snapshot"(적당히 최근의 스냅샷)(§2.4.1) |
| `at_least_as_fresh` + ZedToken | 토큰보다 오래되지 않은 스냅샷 | 검사나 읽기의 zookie(§2.2, §2.4) |
| `at_exact_snapshot` + ZedToken | 정확히 토큰의 스냅샷 | "the same snapshot as a previous read"(이전 읽기와 같은 스냅샷)를 얻기 위해 재사용하는 읽기 zookie(§2.4.1) |
| `fully_consistent` | 최신 데이터 | 직접적인 대응은 없음. 논문의 content-change 검사는 최신 스냅샷에서 평가된다(§2.4.4) |

CockroachDB에서 문서는 `fully_consistent`가 "does not guarantee read-after-write consistency"(쓰기 후 읽기 일관성을 보장하지 않는다)라고 경고한다. 노드 시계가 클러스터의 `max_offset`까지 차이 날 수 있기 때문이다. 대신 `at_least_as_fresh`와 ZedToken을 권한다([consistency 문서](https://authzed.com/docs/spicedb/concepts/consistency)).

`fully_consistent`는 `WriteRelationships`, `DeleteRelationships`, `ReadSchema`, `WriteSchema`의 기본값이고, `minimize_latency`는 그 밖의 모든 API의 기본값이다([consistency 문서](https://authzed.com/docs/spicedb/concepts/consistency)).

논문에서 콘텐츠와 함께 저장되는 zookie는 content-change 검사에서 온다(§2.2, §2.4.4). `Watch`도 ZedToken을 쓴다. 요청은 `optional_start_cursor`에서 시작할 수 있고, 각 응답은 재개 지점인 `changes_through`를 담는다. 이는 논문의 하트비트 zookie(§2.4.3)에 해당한다([`watch_service.proto`](https://github.com/authzed/api/blob/main/authzed/api/v1/watch_service.proto)).

## 논문과의 차이

- **저장소.** 논문은 모든 것을 Spanner에 저장한다(§3.1). SpiceDB는 데이터 저장소를 교체할 수 있다. CockroachDB("high throughput and/or multi-region", 높은 처리량 그리고/또는 다중 리전), Cloud Spanner, PostgreSQL("single-region", 단일 리전), MySQL("Not recommended", 권장하지 않음), memdb(로컬 개발과 테스트)([datastores](https://authzed.com/docs/spicedb/concepts/datastores)).
- **관계와 권한이 분리되어 있다.** 논문은 유저셋 재작성을 관계에 붙인다(§2.3.1). SpiceDB는 저장되는 `relation`과 계산되는 `permission`을 나눈다([schema](https://authzed.com/docs/spicedb/concepts/schema)).
- **caveat.** 관계는 이름 붙은 CEL 표현식을 가질 수 있으며, 스키마에서 `with`로 붙인다(예: `relation viewer: user | user with ip_allowlist`)([caveats](https://authzed.com/docs/spicedb/concepts/caveats)). 논문의 튜플(§2.1)에는 그런 필드가 없다.
- **와일드카드.** `relation viewer: user | user:*`는 공개 부여를 허용한다([schema](https://authzed.com/docs/spicedb/concepts/schema)). 논문의 튜플 문법에는 사용자 ID나 유저셋이 있을 뿐 와일드카드는 없다(§2.1).
- **교집합 화살표.** `.all()`은 관계된 모든 객체가 권한을 부여할 것을 요구한다([schema](https://authzed.com/docs/spicedb/concepts/schema)). 논문의 세 가지 재작성 리프(§2.3.1)에는 그런 형태가 없다.
- **기본 오래된 정도.** 논문은 존 밖 읽기 통계로부터 기본 오래된 정도를 적응적으로 고르고(§3.2.1), 이와 별도로 캐시 항목을 공유하도록 평가 타임스탬프를 "to a coarse granularity, such as one or ten seconds"(1초나 10초 같은 거친 단위로) 올림한다(§3.2.5). SpiceDB에는 올림만 있다. 캐시 항목을 재사용할 수 있도록 `--datastore-revision-quantization-interval`이 정하는 구간으로 요청 리비전을 묶는다. AuthZed는 "the default is 5s"(기본값은 5초)라고 하며([핫스팟 캐싱 글, 2023-05-10](https://authzed.com/blog/hotspot-caching-in-google-zanzibar-and-spicedb)), 이는 [소스](https://github.com/authzed/spicedb/blob/main/pkg/cmd/datastore/dsconfig/config.go)의 `RevisionQuantization: 5 * time.Second`와 일치한다.
- **조회 API.** `LookupResources`와 `LookupSubjects`는 "어떤 리소스"와 "어떤 주체" 질문에 답한다([`permission_service.proto`](https://github.com/authzed/api/blob/main/authzed/api/v1/permission_service.proto)). 논문의 API에는 Read, Write, Watch, Check, Expand가 있다(§2.4).
- **Leopard.** "AuthZed Materialize takes inspiration from the Leopard index component described in the Zanzibar paper"(AuthZed Materialize는 Zanzibar 논문에 기술된 Leopard 인덱스 구성 요소에서 영감을 얻었다)([Materialize 문서](https://authzed.com/docs/materialize/getting-started/overview)). 이는 오픈 소스 SpiceDB가 아니라 AuthZed 유료 제품의 일부다. 문서는 그 Accelerated Queries 기능이 "generally available to users of AuthZed Dedicated"(AuthZed Dedicated 사용자에게 정식 제공된다)라고 말한다.
