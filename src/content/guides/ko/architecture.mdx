Zanzibar는 Spanner 데이터베이스 집합 앞에 놓인 서버 집합이다. 이 페이지는 구성 요소에 이름을 붙이고, Check 요청 하나가 그것들을 거쳐 가는 과정을 따라간 다음, 데이터가 디스크에 어떻게 배치되는지 살펴본다. 끝에 나오는 수치는 논문이 2018년 프로덕션에 대해 보고한 것이다.

## 구성 요소

어떤 상자들이 있고, 그 사이에서 데이터는 어느 방향으로 흐르는가? 논문은 그림 2로 답한다. 아래 그림은 그 색(클라이언트는 파랑, 서버는 노랑, Spanner 데이터베이스는 초록)을 유지하고 세부를 생략했다.

클라이언트가 두 종류의 서버와 통신한다는 점에 주목하라. `aclservers`는 네 가지 요청 유형에 답하고, `watchservers`는 변경을 스트리밍하기만 한다. 논문의 표현으로 `aclservers`는 "are organized in clusters and respond to Check, Read, Expand, and Write requests"(클러스터로 구성되며 Check, Read, Expand, Write 요청에 응답한다), `watchservers`는 "tail the changelog and serve a stream of namespace changes to clients in near real time"(변경 로그를 추적하여 네임스페이스 변경 스트림을 거의 실시간으로 클라이언트에 제공한다)(§3). Leopard는 크고 깊게 중첩된 그룹을 위한 인덱스이며 [별도 페이지](../leopard/)가 있다.

오프라인 파이프라인은 "dumps of the relation tuples in each namespace at a known snapshot timestamp"(알려진 스냅샷 타임스탬프에서 각 네임스페이스의 관계 튜플 덤프)를 만들고, "tuple versions older than a threshold configured per namespace"(네임스페이스별로 설정된 임계값보다 오래된 튜플 버전)를 가비지 컬렉션한다(§3).

## Check 하나를 단계별로

따라갈 요청은 이것이다. Beto는 readme의 열람자인가? 예제에서 readme의 열람자에는 `group:eng`의 멤버가 포함되고 Beto는 그중 하나이므로 답은 예다. Zanzibar는 두 객체 `doc:readme`와 `group:eng`를 읽어서 이를 알아내야 한다.

### 요청은 아무 서버에나 도착하고, 그 서버가 팬아웃한다

어느 서버가 일을 하는가? 어느 서버든 요청을 받을 수 있고, 그다음 일은 객체별로 분산된다.

서버 A는 어느 객체도 담당할 필요가 없었다. 논문은 정확히 이 형태를 기술한다. "Requests arrive at any server in a cluster and that server fans out the work to other servers in the cluster as necessary. Those servers may in turn contact other servers to compute intermediate results. The initial server gathers the final result and returns it to the client."(요청은 클러스터 내 임의의 서버에 도착하고, 그 서버는 필요에 따라 클러스터 내 다른 서버로 작업을 팬아웃한다. 그 서버들은 다시 중간 결과를 계산하기 위해 다른 서버에 연락할 수 있다. 처음 요청을 받은 서버가 최종 결과를 모아 클라이언트에 반환한다.)(§3)

### 일관된 해싱이 상대 서버를 고른다

A는 readme에 대해 B에게 물어야 한다는 것을 어떻게 알았는가? 클러스터의 서버들은 하나의 분산 캐시를 이룬다. "Cache entries are distributed across Zanzibar servers with consistent hashing"(캐시 항목은 일관된 해싱으로 Zanzibar 서버들에 분산된다)(§3.2.5). 이 방식은 논문이 [20]으로 인용하는 [Karger et al. (STOC '97)](https://people.csail.mit.edu/karger/Papers/web.pdf)에서 왔다. 대부분의 네임스페이스에서 포워딩 키는 객체 ID로 계산된다(§3.2.5).

readme의 `viewer`와 `owner`가 같은 서버에서 만난다는 점에 주목하라. 객체를 키로 삼는 이유가 이것이다. "processing a check on ⟨*object#relation*⟩ often involves indirect ACL checks on other relations of the same object and reading relation tuples of the object. These checks and reads can be processed by the same server since they share the same forwarding key with the parent check request."(⟨*object#relation*⟩에 대한 검사를 처리하는 데에는 흔히 같은 객체의 다른 관계에 대한 간접 ACL 검사와 그 객체의 관계 튜플 읽기가 수반된다. 이러한 검사와 읽기는 상위 검사 요청과 같은 포워딩 키를 공유하므로 같은 서버에서 처리될 수 있다.)(§3.2.5) Karger et al.은 캐시가 추가되거나 제거될 때 부하 균형을 유지하는 데 필요한 최소한의 비율의 객체만 이동하도록 일관된 해싱을 설계했으며, 그래서 캐시에 잘 맞는다.

뜨거운 키에 대해 논문은 [Slicer](https://www.usenix.org/conference/osdi16/technical-sessions/presentation/adya)를 사용하여 "to help distribute hot keys to multiple servers"(핫 키를 여러 서버에 분산하는 데 도움을 받는다)라고 덧붙인다(§3.2.5).

호출자들의 캐시와 피호출자의 캐시는 쌓여서 트리가 된다. "To handle hot forwarding keys, we cache results at both the caller and the callee of internal RPCs, effectively forming cache trees."(핫 포워딩 키를 처리하기 위해, 우리는 내부 RPC의 호출자와 피호출자 양쪽에서 결과를 캐시하여 사실상 캐시 트리를 형성한다.)(§3.2.5) 캐시 키에는 스냅샷 타임스탬프가 포함되며, 타임스탬프는 "rounded up to a coarse granularity, such as one or ten seconds"(1초나 10초 같은 거친 단위로 올림)되므로 최근 요청 대부분이 항목을 공유한다(§3.2.5). 프로덕션에서 검사 캐싱은 "a 10% hit rate on the delegate’s side"(위임받는 쪽에서 10% 히트율)와 위임하는 쪽에서 "a 2% hit rate"(2% 히트율)를 보였다. 논문은 이 비율이 낮아 보이지만 "they prevent 500K internal RPCs per second from creating hot spots"(초당 50만 건의 내부 RPC가 핫스팟을 만드는 것을 막는다)라고 지적한다(§4.4).

### 락 테이블이 동일한 요청을 하나로 합친다

캐시는 답을 가지고 있어야만 도움이 된다. 첫 요청이 끝나기 전에 동일한 요청이 많이 도착하면 모두 미스가 나서 모두 Spanner로 갈 것이다. 이것이 [캐시 스탬피드(cache stampede)](https://en.wikipedia.org/wiki/Cache_stampede)다(논문의 참고 문헌 [3]). C는 이를 어떻게 피하는가?

논문: "we maintain a *lock table* on each server to track outstanding reads and checks. Among requests sharing the same cache key only one request will begin processing; the rest block until the cache is populated."(우리는 처리 중인 읽기와 검사를 추적하기 위해 각 서버에 *락 테이블*을 유지한다. 같은 캐시 키를 공유하는 요청 중 하나만 처리를 시작하고, 나머지는 캐시가 채워질 때까지 대기한다.)(§3.2.5) 검사의 경우 락 테이블은 위임받는 쪽에서 "an additional 12%"(추가로 12%)를, 위임하는 쪽에서 "an additional 3%"(추가로 3%)를 절약했다(§4.4).

나중에 두 가지 개선이 더해졌다(§3.2.5). 매우 인기 있는 객체에 대해 Zanzibar는 ⟨*object#relation*⟩의 *모든* 튜플을 한꺼번에 읽어 캐시하며, 이는 "trading read bandwidth for cacheability"(읽기 대역폭을 캐시 가능성과 맞바꾸는 것)다. 그리고 취소된 하위 검사는 캐시 키를 비워 두므로, "eager cancellation when there are waiters on the corresponding lock table entry"(해당 락 테이블 항목에 대기자가 있을 때의 조기 취소)를 늦춘다.

### Spanner로 가는 읽기는 풀링된다

이번에는 한 객체의 여러 관계를 건드리는 검사를 보자. Chen은 readme의 열람자인가? 논문의 그림 1 설정에서 `viewer`는 `editor`를 포함하고, `editor`는 `owner`를 포함하며, `parent` 폴더의 열람자는 문서의 열람자다. 따라서 서버 B는 readme의 튜플 집합 네 개를 읽어야 한다.

리프는 동시에 실행된다. "we evaluate all leaf nodes of the boolean expression tree concurrently. ### 느린 Spanner 읽기는 헤징된다

헤징이란 "we send the same request to multiple servers, use whichever response comes back first, and cancel the other requests"(같은 요청을 여러 서버에 보내고, 먼저 돌아오는 응답을 사용하며, 나머지 요청은 취소하는 것)다(§3.2.7). 두 번째 요청은 기다린다. "we first send one request and defer sending hedged requests until the initial request is known to be slow"(우리는 먼저 요청 하나를 보내고, 첫 요청이 느리다고 알려질 때까지 헤지 요청의 전송을 미룬다)이며, 지연 시간은 "*N*th percentile latency based on recent measurements"(최근 측정치에 기반한 *N*번째 백분위수 지연 시간)의 추정기가 정한다(§3.2.7). 프로덕션에서 "1% of Spanner reads, or 200K reads per second, benefit from hedging"(Spanner 읽기의 1%, 즉 초당 20만 건의 읽기가 헤징의 혜택을 받는다)(§4.4).

<Callout kind="note" title="aclserver 사이에서는 하지 않는다">
Zanzibar는 자신의 내부 호출을 헤징하지 않는다. 검사마다 비용이 다르기 때문이다. "Hedging check requests would result in duplicating the most expensive workloads and, ironically, worsening latency."(검사 요청을 헤징하면 가장 비싼 작업 부하를 중복시키게 되어, 아이러니하게도 지연 시간이 악화될 것이다.)(§3.2.7) 대신 복제본과 모니터링에 의존하여 느린 서버를 피한다.
</Callout>

### 각 클라이언트는 울타리 안에 있다

공유 서비스는 한 클라이언트가 다른 클라이언트를 느리게 만드는 것을 막아야 한다. §3.2.6은 네 가지 한도를 든다.

- CPU: 각 RPC는 "generic *cpu-seconds*"(일반화된 *CPU 초*)로 비용이 매겨진다. 각 클라이언트에는 전역 CPU 한도가 있으며, "its RPCs will be throttled if it exceeds the limit *and* there is no spare capacity in the overall system."(한도를 초과하고 *동시에* 시스템 전체에 여유 용량이 없으면 그 RPC는 스로틀링된다.)
- 처리 중인 RPC: 각 서버는 전체 개수와 클라이언트별 개수를 제한한다.
- Spanner: "the maximum number of concurrent reads per *(object, client)* and per client on each Spanner server."(각 Spanner 서버에서 *(객체, 클라이언트)*별 및 클라이언트별 최대 동시 읽기 수.)
- 락 테이블: "different lock table keys for requests from different clients"(서로 다른 클라이언트의 요청에 서로 다른 락 테이블 키)를 사용하여, Spanner가 한 클라이언트를 스로틀링해도 다른 클라이언트가 막히지 않게 한다.

**튜플 데이터베이스.** "We store relation tuples of each namespace in a separate database, where each row is identified by primary key *(shard ID, object ID, relation, user, commit timestamp)*."(우리는 각 네임스페이스의 관계 튜플을 별도의 데이터베이스에 저장하며, 각 행은 기본 키 *(샤드 ID, 객체 ID, 관계, 사용자, 커밋 타임스탬프)*로 식별된다.)(§3.1.1) 커밋 타임스탬프가 키의 일부이므로 오래된 버전은 자신의 행에 남으며, "so that we can evaluate checks and reads at any timestamp within the garbage collection window"(가비지 컬렉션 기간 안의 어떤 타임스탬프에서든 검사와 읽기를 평가할 수 있다). 예제의 튜플은 `doc`과 `group` 데이터베이스에 다음과 같이 놓일 것이다.

| 데이터베이스 | 샤드 ID | 객체 ID | 관계 | 사용자 | 커밋 타임스탬프 |
| --- | --- | --- | --- | --- | --- |
| `doc` | *s*(readme) | `readme` | `owner` | `user:anne` | *t*₁ |
| `doc` | *s*(readme) | `readme` | `parent` | `folder:A#...` | *t*₂ |
| `doc` | *s*(readme) | `readme` | `viewer` | `group:eng#member` | *t*₃ |
| `group` | *s*(eng) | `eng` | `member` | `user:beto` | *t*₄ |

한 객체의 행은 함께 정렬된다. 논문은 이 키 순서가 "allows us to look up all relation tuples for a given object ID or *(object ID, relation)* pair"(주어진 객체 ID 또는 *(객체 ID, 관계)* 쌍에 대한 모든 관계 튜플을 조회할 수 있게 한다)라고 말한다. "Usually the shard ID is determined solely by the object ID"(보통 샤드 ID는 객체 ID만으로 결정된다)이며, 멤버가 매우 많은 그룹에서는 "computed from both object ID and user"(객체 ID와 사용자 양쪽으로부터 계산)될 수 있다(§3.1.1). 논문은 샤드 함수를 제시하지 않으므로 위의 *s*(…)는 자리 표시자이며, 사용자 열의 정확한 인코딩도 기술되어 있지 않다.

**변경 로그.** 모든 네임스페이스를 위한 데이터베이스 하나로, *(변경 로그 샤드 ID, 타임스탬프, 고유 갱신 ID)*를 키로 하며, "where a changelog shard is randomly selected for each write"(변경 로그 샤드는 쓰기마다 무작위로 선택된다)(§3.1.2).

**네임스페이스 설정.** 테이블 두 개를 가진 데이터베이스 하나다. "keyed by namespace IDs"(네임스페이스 ID를 키로 하는) 설정 테이블과, "keyed by commit timestamps"(커밋 타임스탬프를 키로 하는) "a changelog of config updates"(설정 갱신의 변경 로그)다. 서버는 시작할 때 모든 설정을 로드하고 이후 그 변경 로그를 따라간다(§3.1.3).

**복제.** "Replicas exist in dozens of locations around the world, with multiple replicas per region. The 5 voting replicas are in eastern and central United States, in 3 different metropolitan areas to isolate failures but within 25 milliseconds of each other so that Paxos transactions commit quickly."(복제본은 전 세계 수십 곳에 있으며, 리전마다 여러 복제본이 있다. 투표 복제본 5개는 미국 동부와 중부에 있는데, 장애를 격리하기 위해 서로 다른 3개 대도시권에 두되 Paxos 트랜잭션이 빠르게 커밋되도록 서로 25밀리초 이내에 있다.)(§3.1.4) Spanner 자체는 논문의 참고 문헌 [15]인 [Corbett et al. (OSDI '12)](https://www.usenix.org/system/files/conference/osdi12/osdi12-final-16.pdf)에 기술되어 있다.

## 운영 수치

논문의 §4는 다음 수치를 보고한다. API별 최고치와 지연 시간은 2018년 12월의 7일 기간에서 나왔다(§4, §4.2). 논문은 그 밖의 수치를 특정 기간과 연결하지 않는다. 각 칸은 원문 그대로 인용한다.
