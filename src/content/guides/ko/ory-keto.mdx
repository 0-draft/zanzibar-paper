Ory Keto는 Ory Corp가 Go로 작성한 권한 서버다. README는 이를 "an open source implementation of 'Zanzibar: Google's Consistent, Global Authorization System'"('Zanzibar: Google의 일관된 글로벌 인가 시스템'의 오픈 소스 구현)이라고 부른다([README](https://github.com/ory/keto)). Ory는 이를 관리형 서비스로도 운영한다. Ory Network에서 "Ory Permissions is powered by the open source Ory Keto"(Ory Permissions는 오픈 소스 Ory Keto로 작동한다)(같은 README).

Keto는 처음부터 Zanzibar 시스템이었던 것은 아니다. Zanzibar 설계는 2021-04-07의 v0.6.0-alpha.1에서 들어왔다. 릴리스 노트는 이전의 Keto가 `legacy-0.5` 브랜치로 옮겨 갔으며 "the architectures are vastly different"(아키텍처가 크게 다르다)라고 말한다([릴리스 노트](https://github.com/ory/keto/releases/tag/v0.6.0-alpha.1)). Ory Permission Language로 작성하는 유저셋 재작성은 2022-09-27의 v0.10.0-alpha.0에서 뒤따랐다([릴리스 노트](https://github.com/ory/keto/releases/tag/v0.10.0-alpha.0)).

## 논문과 Keto 나란히 보기

| 논문 | Ory Keto |
| --- | --- |
| 네임스페이스 설정 (§2.3) | TypeScript의 부분 집합인 Ory Permission Language(OPL)에서 `implements Namespace`하는 `class`([OPL reference](https://www.ory.com/docs/keto/reference/ory-permission-language)) |
| 관계 튜플 `object#relation@user` (§2.1) | `namespace:object#relation@subject`. 예: `Group:eng#members@User:beto`([relation tuples](https://www.ory.com/docs/keto/concepts/relation-tuples), [parser](https://github.com/ory/keto/blob/master/ketoapi/enc_string.go)) |

| `tuple_to_userset` | `this.related.parents.traverse((p) => p.permits.view(ctx))` |
| 합집합, 교집합, 차집합 | `\|\|`, `&&`, `!` |
| zookie (§2.2, §2.4) | API에 `snaptoken` 필드가 있지만, 각각 "not implemented yet and has no effect"(아직 구현되지 않았으며 효과가 없다)([check_service.proto](https://github.com/ory/keto/blob/master/proto/ory/keto/relation_tuples/v1alpha2/check_service.proto)) |
| Check (§2.4.4) | `CheckService.Check`, `BatchCheck` |
| Read (§2.4.1) | `ReadService.ListRelationTuples`([read_service.proto](https://github.com/ory/keto/blob/master/proto/ory/keto/relation_tuples/v1alpha2/read_service.proto)) |
| Write (§2.4.2) | `WriteService.TransactRelationTuples`, `DeleteRelationTuples`([write_service.proto](https://github.com/ory/keto/blob/master/proto/ory/keto/relation_tuples/v1alpha2/write_service.proto)) |
| Watch (§2.4.3) | API에 없음 |
| Expand (§2.4.5) | `ExpandService.Expand`([expand_service.proto](https://github.com/ory/keto/blob/master/proto/ory/keto/relation_tuples/v1alpha2/expand_service.proto)) |

## OPL로 쓴 예제

논문의 그림 1은 소유자를 편집자로, 편집자를 열람자로, 상위 폴더의 열람자를 문서의 열람자로 만든다(§2.3.1). OPL에서 각 네임스페이스는 클래스다. `related`는 관계와 그것이 받는 주체 타입을 선언하고, `permits`는 `ctx.subject`에 대해 참이나 거짓을 반환하는 함수를 담는다.

```ts
import { Namespace, SubjectSet, Context } from "@ory/keto-namespace-types"

class User implements Namespace {}

class Group implements Namespace {
  related: {
    members: User[]
  }
}

class Folder implements Namespace {
  related: {
    viewers: (User | SubjectSet<Group, "members">)[]
  }

  permits = {
    view: (ctx: Context): boolean => this.related.viewers.includes(ctx.subject),
  }
}

class Doc implements Namespace {
  related: {
    parents: Folder[]
    owners: User[]
    editors: (User | SubjectSet<Group, "members">)[]
    viewers: (User | SubjectSet<Group, "members">)[]
  }

  permits = {
    edit: (ctx: Context): boolean =>
      this.related.owners.includes(ctx.subject) ||
      this.related.editors.includes(ctx.subject),

    view: (ctx: Context): boolean =>
      this.related.viewers.includes(ctx.subject) ||
      this.permits.edit(ctx) ||
      this.related.parents.traverse((p) => p.permits.view(ctx)),
  }
}
```

`SubjectSet<Group, "members">`는 "그룹의 멤버", 즉 논문의 유저셋을 나타내는 OPL 타입이다. 관계는 항상 배열인데, "an object can have many subjects"(객체는 많은 주체를 가질 수 있기) 때문이다([OPL reference](https://www.ory.com/docs/keto/reference/ory-permission-language)).

다음은 예제의 튜플 다섯 개를 Keto의 텍스트 형식으로 쓴 것이다. `User:anne`처럼 쓴 주체는 관계가 비어 있는 주체 집합(subject set)이다. 메인테이너들의 샘플 튜플도 사용자를 이렇게 쓴다([tuples.json](https://github.com/ory/keto/blob/master/contrib/rewrites-example/relation-tuples/tuples.json)).

```text
Doc:readme#owners@User:anne
Group:eng#members@User:beto
Doc:readme#viewers@Group:eng#members
Doc:readme#parents@Folder:A
Folder:A#viewers@User:chen
```

어느 튜플과 어느 OPL 표현식이 각 사람의 readme 접근을 결정하는가?

- 각 컨테이너는 Read API(기본 포트 4466), Write API(4467), OPL 문법 API(4469)를 각각 HTTP와 gRPC로 제공한다([config schema](https://github.com/ory/keto/blob/master/embedx/config.schema.json)).

## 일관성

논문의 zookie는 클라이언트가 "at a consistent snapshot no earlier than the given zookie"(주어진 zookie보다 이르지 않은 일관된 스냅샷에서) 검사를 요청할 수 있게 한다(§2.4.4). Keto의 protobuf API는 필드 이름에 같은 생각을 담고 있다. Check, Expand, ListRelationTuples의 `snaptoken`, TransactRelationTuples의 `snaptokens`, 그리고 content-change 검사를 위한 `latest` 플래그다. 이 필드들은 모두 "not implemented yet and has no effect"(아직 구현되지 않았으며 효과가 없다)로 문서화되어 있다([check_service.proto](https://github.com/ory/keto/blob/master/proto/ory/keto/relation_tuples/v1alpha2/check_service.proto)).

## 논문과의 차이

- **zookie 없음.** 필드는 있지만 동작은 없다(위 참조).
- **Watch 없음.** v1alpha2 API에는 Check, Expand, Read, Write, Namespaces, Version 서비스와 별도의 OPL 문법 서비스(`opl/v1alpha1`)가 있지만 변경 스트림은 없다([proto 디렉터리](https://github.com/ory/keto/tree/master/proto/ory/keto)). 논문의 Watch는 보조 인덱스와 Leopard에 데이터를 공급한다(§2.4.3, §3.2.4).
- **Leopard 없음.** 비정규화된 집합 인덱스는 문서화되어 있지 않다.
- **프로그래밍 언어 문법.** OPL은 "users can get context help from their IDE"(사용자가 IDE에서 문맥 도움을 받을 수 있도록) TypeScript의 부분 집합이다([OPL 명세](https://github.com/ory/keto/blob/master/docs/ory_permission_language_spec.md)). 논문의 그림 1은 설정을 프로토콜 버퍼 스타일의 텍스트 문법으로 쓰며(§2.3.1), 논문은 그 형식의 이름을 밝히지 않는다.
- **SQL 저장소.** Spanner(§3.1) 대신 공유 SQL 데이터베이스 하나.
- **검사 깊이.** Check 요청은 `max_depth`, 즉 "The maximum depth to search for a relation"(관계를 탐색할 최대 깊이)을 담는다([check_service.proto](https://github.com/ory/keto/blob/master/proto/ory/keto/relation_tuples/v1alpha2/check_service.proto)).
