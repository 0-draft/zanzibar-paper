Topaz is an authorization service written in Go. It "uses the Open Policy Agent (OPA) as its decision engine, and provides a built-in directory that is inspired by the Google Zanzibar data model" ([README](https://github.com/aserto-dev/topaz)). A decision is made by a Rego policy; the policy can ask the directory whether a relation or permission holds between a subject and an object, which is the part that resembles Zanzibar. The directory data is "modeled and stored locally in an embedded database" (same README).

Topaz was built by Aserto. On 2025-04-27 Aserto announced that it was "sunsetting the Aserto SaaS control plane and will shut it down by May 31, 2025", that it would "wind down Aserto as a commercial entity", and that "we have a set of maintainers that will continue to support Topaz" ([Aserto blog](https://www.aserto.com/blog/the-final-chapter-for-aserto), vendor-authored). Releases have continued since.

## Paper and Topaz side by side

| In the paper | In Topaz |
| --- | --- |
| Namespace config (§2.3) | An object type under `types` in the manifest, a YAML file with `model: version: 3` ([manifest reference](https://www.topaz.sh/docs/directory/manifest-reference)) |
| Relation tuple `object#relation@user` (§2.1) | A relation record: `object_type`, `object_id`, `relation`, `subject_type`, `subject_id` and an optional `subject_relation` |
| `_this` | A relation's stored records; the relation lists the subject types it accepts, as `viewer: user \| group#member` |
| `computed_userset` | Naming another relation or permission of the same type inside a permission |
| `tuple_to_userset` | The arrow, as `parent->can_read` |
| Union, intersection, exclusion | `\|`, `&`, `-` |
| Zookie (§2.2, §2.4) | None documented |
| Check (§2.4.4) | Directory `Reader.Check` and `Checks`; policy decisions through `Authorizer.Is` ([reader.proto](https://github.com/aserto-dev/go-directory/blob/main/proto/aserto/directory/reader/v3/reader.proto), [authorizer.proto](https://github.com/aserto-dev/go-authorizer/blob/main/proto/aserto/authorizer/v2/authorizer.proto)) |
| Read (§2.4.1) | `Reader.GetRelation`, `GetRelations` |
| Write (§2.4.2) | `Writer.SetRelation`, `DeleteRelation` ([writer.proto](https://github.com/aserto-dev/go-directory/blob/main/proto/aserto/directory/writer/v3/writer.proto)) |
| Watch (§2.4.3) | None in the directory API |
| Expand (§2.4.5) | No Expand call; `Reader.GetGraph` ("get object relationship graph") is the closest |
| Leopard (§3.2.4) | No equivalent documented |
| Spanner (§3.1) | An embedded BoltDB file ([architecture](https://www.topaz.sh/docs/architecture)) |

## The running example as a Topaz manifest

The paper's Figure 1 makes owners editors, editors viewers, and viewers of the parent folder viewers of the document (§2.3.1). A Topaz manifest separates `relations`, which hold stored records, from `permissions`, which are computed from relations and other permissions.

```yaml
model:
  version: 3

types:
  user: {}

  group:
    relations:
      member: user

  folder:
    relations:
      viewer: user | group#member
    permissions:
      can_read: viewer

  doc:
    relations:
      parent: folder
      owner: user
      editor: user | group#member
      viewer: user | group#member
    permissions:
      can_write: owner | editor
      can_read: viewer | can_write | parent->can_read
```

`group#member` grants the relation to "everyone with the `member` relation to a specified `group`", and the arrow "allows a permission to be granted to subjects who have a specified relation or permission with another object" ([manifest reference](https://www.topaz.sh/docs/directory/manifest-reference)). Names must be lowercase and at most 64 characters.

- "The Authorizer exposes three APIs to the calling application": `authz/is`, `authz/query` and `authz/decisiontree`, each "a POST or gRPC API" ([architecture](https://www.topaz.sh/docs/architecture)).
- Policies reach the directory through OPA built-ins, including `ds.check`, `ds.check_relation` and `ds.check_permission` (same page).
- "The directory is implemented as a BoltDB instance" (same page). "Directory objects are loaded on-demand, in contrast to `data.json` files", which are loaded with the policy.
- "The authorizer captures and stores decision logs for every decision that it evaluates" (same page).
- Topaz can be deployed "as a sidecar or a microservice in your cloud" ([intro](https://www.topaz.sh/docs/intro)).

## Consistency

The paper's zookie lets a client ask for a check "at a consistent snapshot no earlier than the given zookie" (§2.4.4). Topaz documents nothing comparable: the manifest reference and architecture pages make no statement about consistency, and the directory's Reader and Writer messages carry no token or snapshot field ([reader.proto](https://github.com/aserto-dev/go-directory/blob/main/proto/aserto/directory/reader/v3/reader.proto), [writer.proto](https://github.com/aserto-dev/go-directory/blob/main/proto/aserto/directory/writer/v3/writer.proto)). A check reads the BoltDB file of the Topaz instance it runs on. How several instances share or copy data is not described on the pages checked here.

## Differences from the paper

- **Policy first.** The decision API is `Is`, which evaluates a Rego policy; the Zanzibar-style check is one input the policy can use. In the paper, Check on the userset is the decision (§2.4.4).
- **Local, embedded storage.** One BoltDB file per instance instead of Spanner replicated worldwide (§3.1).
- **No zookie, Watch or Leopard.** None is documented.
- **Wildcards.** `viewer: user | user:*` allows a relation to the subject with ID `*` ([manifest reference](https://www.topaz.sh/docs/directory/manifest-reference)).
- **Decision logs.** Every decision is logged for audit, which the paper does not describe for Zanzibar.
