SpiceDB is an open-source database that stores relationships and answers permission queries over them, in the style of Zanzibar. It is written in Go, licensed Apache-2.0 and maintained by AuthZed, Inc. ([repository](https://github.com/authzed/spicedb)). Its first GitHub release, v1.0.0, is dated 2021-09-30. AuthZed also sells managed and commercial services around it; those are named as such below. Most sources on this page are AuthZed's own documentation and blog.

## Paper terms and SpiceDB terms

| In the paper | In SpiceDB |
| --- | --- |
| Namespace config (§2.3) | A `definition` in the schema ([schema docs](https://authzed.com/docs/spicedb/concepts/schema)) |
| Relation tuple `object#relation@user` (§2.1) | Relationship `resource#relation@subject`, e.g. `document:readme#editor@user:emilia` ([relationships](https://authzed.com/docs/spicedb/concepts/relationships)) |
| `_this` (§2.3.1) | A `relation` with its allowed subject types; the stored relationships for it |
| `computed_userset` | Naming another relation or permission inside a `permission` expression |
| `tuple_to_userset` | The arrow `parent->view` (alias `parent.any(view)`) |
| `union` / `intersection` / `exclusion` | `+` / `&` / `-` |
| Zookie (§2.4) | ZedToken ([consistency](https://authzed.com/docs/spicedb/concepts/consistency)) |
| Check (§2.4.4) | `CheckPermission`, `CheckBulkPermissions` |
| Read (§2.4.1) | `ReadRelationships` |
| Write (§2.4.2) | `WriteRelationships`, `DeleteRelationships` |
| Watch (§2.4.3) | `Watch` |
| Expand (§2.4.5) | `ExpandPermissionTree` |
| Not in the paper's API | `LookupResources`, `LookupSubjects`, `ImportBulkRelationships`, `ExportBulkRelationships` |
| Leopard (§3.2.4) | AuthZed Materialize, a commercial service for AuthZed Dedicated customers ([docs](https://authzed.com/docs/materialize/getting-started/overview)) |
| Spanner (§3) | CockroachDB, Cloud Spanner, PostgreSQL, MySQL, memdb ([datastores](https://authzed.com/docs/spicedb/concepts/datastores)) |

API names come from AuthZed's protocol files: [`permission_service.proto`](https://github.com/authzed/api/blob/main/authzed/api/v1/permission_service.proto) and [`watch_service.proto`](https://github.com/authzed/api/blob/main/authzed/api/v1/watch_service.proto).

## The running example as a schema

The paper's Figure 1 makes owners editors, editors viewers, and viewers of the parent folder viewers of the document (§2.3.1). In SpiceDB, stored relations and computed permissions are declared separately: `relation` lines say who may be written in a relationship, `permission` lines say how access is computed.

```text
definition user {}

definition group {
    relation member: user
}

definition folder {
    relation viewer: user | group#member
    permission view = viewer
}

definition doc {
    relation parent: folder
    relation owner: user
    relation editor: user | group#member
    relation viewer: user | group#member

    permission edit = owner + editor
    permission view = viewer + edit + parent->view
}
```

<Callout kind="note" title="Not run through a validator">

This schema uses only constructs shown on SpiceDB's [schema language page](https://authzed.com/docs/spicedb/concepts/schema) as of 2026-11-13: `definition`, `relation` with `user | group#member`, `permission` with `+` and `->`. It has not been run through `zed` or the SpiceDB Playground.

</Callout>

The relationships for Anne, Beto and Chen:

```text
doc:readme#owner@user:anne
doc:readme#parent@folder:A
group:eng#member@user:beto
doc:readme#viewer@group:eng#member
folder:A#viewer@user:chen
```

## Architecture

How does one SpiceDB deployment answer a check? AuthZed describes SpiceDB as "fundamentally a gRPC service" with an optional HTTP gateway ([architecture post, 2021-11-17](https://authzed.com/blog/spicedb-architecture)). A node splits a request into smaller questions and forwards them to other nodes, a process it calls dispatch; each node keeps "an in-memory cache of permissions queries it has resolved in the past" ([performance docs](https://authzed.com/docs/spicedb/ops/performance)). A consistent hash sends "the same (sub-)requests to the same server" ([architecture post](https://authzed.com/blog/spicedb-architecture)). All nodes share one datastore. Materialize, if used, precomputes chosen permissions, and SpiceDB "can dispatch sub-queries to Materialize" ([performance docs](https://authzed.com/docs/spicedb/ops/performance)).

Compare the paper's Figure 2 (§3): there, `aclservers` also fan work out to other servers in the cluster, but storage is always Spanner, Watch is served by separate `watchservers` that tail a changelog, and Leopard reads offline snapshots as well as Watch. SpiceDB has no separate watch server type in the docs cited here; `Watch` is an RPC on the same service.

## Consistency: ZedTokens and zookies

AuthZed calls the ZedToken "the SpiceDB equivalent of Google Zanzibar's Zookie concept which protects users from the New Enemy Problem" ([consistency docs](https://authzed.com/docs/spicedb/concepts/consistency)). Writes return one (`written_at`), and so do checks (`checked_at`). A request can pick one of four modes:

| Mode | What it asks for | Paper analogue |
| --- | --- | --- |
| `minimize_latency` | Whatever the server can answer fastest | No zookie: "a reasonably recent snapshot" (§2.4.1) |
| `at_least_as_fresh` + ZedToken | A snapshot no older than the token | A zookie in a check or read (§2.2, §2.4) |
| `at_exact_snapshot` + ZedToken | Exactly the token's snapshot | A read zookie reused to get "the same snapshot as a previous read" (§2.4.1) |
| `fully_consistent` | The newest data | No direct analogue; the paper's content-change check is evaluated at the latest snapshot (§2.4.4) |

On CockroachDB, the docs warn that `fully_consistent` "does not guarantee read-after-write consistency", because node clocks can differ by up to the cluster's `max_offset`; they recommend a ZedToken with `at_least_as_fresh` instead ([consistency docs](https://authzed.com/docs/spicedb/concepts/consistency)).

`fully_consistent` is the default for `WriteRelationships`, `DeleteRelationships`, `ReadSchema` and `WriteSchema`; `minimize_latency` is the default for every other API ([consistency docs](https://authzed.com/docs/spicedb/concepts/consistency)).

In the paper the zookie stored with content comes from a content-change check (§2.2, §2.4.4). SpiceDB's docs say that when a resource changes, "a new ZedToken is either returned or it should be requested by performing a check with full consistency" ([consistency docs](https://authzed.com/docs/spicedb/concepts/consistency)), so both routes exist.

`Watch` also uses ZedTokens: a request may start from `optional_start_cursor`, and each response carries `changes_through` to resume from, which matches the paper's heartbeat zookie (§2.4.3) ([`watch_service.proto`](https://github.com/authzed/api/blob/main/authzed/api/v1/watch_service.proto)).

## Differences from the paper

- **Storage.** The paper stores everything in Spanner (§3.1). SpiceDB has pluggable datastores: CockroachDB ("high throughput and/or multi-region"), Cloud Spanner, PostgreSQL ("single-region"), MySQL ("Not recommended") and memdb (local development and testing) ([datastores](https://authzed.com/docs/spicedb/concepts/datastores)).
- **Relations and permissions are separate.** The paper attaches a userset rewrite to a relation (§2.3.1). SpiceDB splits stored `relation`s from computed `permission`s ([schema](https://authzed.com/docs/spicedb/concepts/schema)).
- **Caveats.** Relationships can carry a named CEL expression, attached in the schema with `with` (e.g. `relation viewer: user | user with ip_allowlist`) ([caveats](https://authzed.com/docs/spicedb/concepts/caveats)). The paper's tuple (§2.1) has no such field.
- **Wildcards.** `relation viewer: user | user:*` allows a public grant ([schema](https://authzed.com/docs/spicedb/concepts/schema)). The paper's tuple grammar has a user ID or a userset (§2.1), no wildcard.
- **Intersection arrow.** `.all()` requires every related object to grant the permission ([schema](https://authzed.com/docs/spicedb/concepts/schema)). The paper's three rewrite leaves (§2.3.1) have no such form.
- **Default staleness.** The paper picks the default staleness adaptively from out-of-zone read statistics (§3.2.1), and separately rounds evaluation timestamps up "to a coarse granularity, such as one or ten seconds" so cache entries are shared (§3.2.5). SpiceDB has only the rounding: it groups request revisions into windows set by `--datastore-revision-quantization-interval` so cache entries can be reused; AuthZed gives "the default is 5s" ([hotspot caching post, 2023-05-10](https://authzed.com/blog/hotspot-caching-in-google-zanzibar-and-spicedb)), which matches `RevisionQuantization: 5 * time.Second` in the [source](https://github.com/authzed/spicedb/blob/main/pkg/cmd/datastore/dsconfig/config.go).
- **Lookup APIs.** `LookupResources` and `LookupSubjects` answer "which resources" and "which subjects" questions ([`permission_service.proto`](https://github.com/authzed/api/blob/main/authzed/api/v1/permission_service.proto)). The paper's API has Read, Write, Watch, Check and Expand (§2.4).
- **Leopard.** "AuthZed Materialize takes inspiration from the Leopard index component described in the Zanzibar paper" ([Materialize docs](https://authzed.com/docs/materialize/getting-started/overview)). It is part of AuthZed's paid offering, not the open-source SpiceDB: the docs say its Accelerated Queries feature is "generally available to users of AuthZed Dedicated".
