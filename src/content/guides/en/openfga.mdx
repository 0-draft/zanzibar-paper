OpenFGA is an open-source authorization engine. Its docs say the JSON form of its model language, the one the API accepts, "closely tracks the language in the Zanzibar paper"; the DSL adds syntactic sugar and compiles to that JSON ([configuration language](https://openfga.dev/docs/configuration-language)). The CNCF post announcing its incubation says it "was developed by a group of Okta employees, and is the foundation for the Auth0 FGA commercial offering" ([CNCF, 2025-11-11](https://www.cncf.io/blog/2025/11/11/openfga-becomes-a-cncf-incubating-project/)). It is written in Go and licensed Apache-2.0 ([repository](https://github.com/openfga/openfga)). Auth0's managed service describes itself as "based on OpenFGA, an open-source project owned by the Cloud Native Computing Foundation" ([Auth0 FGA docs](https://docs.fga.dev/fga)).

## Paper terms and OpenFGA terms

OpenFGA's own docs include a table of "Equivalent Zanzibar Concepts" ([configuration language](https://openfga.dev/docs/configuration-language#equivalent-zanzibar-concepts)); this one extends it to the API and the storage.

| In the paper | In OpenFGA |
| --- | --- |
| Namespace config (§2.3) | A `type` in an authorization model, written in the DSL or JSON ([configuration language](https://openfga.dev/docs/configuration-language)) |
| Relation tuple `object#relation@user` (§2.1) | Relationship tuple with `user`, `relation`, `object`, e.g. `user:anne`, `owner`, `doc:readme`; a userset is written `group:eng#member` |
| `_this` (§2.3.1) | A direct type restriction such as `[user, group#member]` (`this` in JSON) |
| `computed_userset` | A bare relation name, e.g. `or owner` |
| `tuple_to_userset` | `viewer from parent` (`tupleToUserset` in JSON) |
| `union` / `intersection` / `exclusion` | `or` / `and` / `but not` (`union` / `intersection` / `difference` in JSON) |
| Zookie (§2.4) | None; a query chooses `MINIMIZE_LATENCY` or `HIGHER_CONSISTENCY` ([consistency](https://openfga.dev/docs/interacting/consistency)) |
| Check (§2.4.4) | `Check`, `BatchCheck` |
| Read (§2.4.1) | `Read` |
| Write (§2.4.2) | `Write` |
| Watch (§2.4.3) | `ReadChanges`, a paginated list read with a continuation token ([tuple changes](https://openfga.dev/docs/interacting/read-tuple-changes)) |
| Expand (§2.4.5) | `Expand` |
| Not in the paper's API | `ListObjects`, `StreamedListObjects`, `ListUsers`; stores; model versions (`WriteAuthorizationModel`, `ReadAuthorizationModel(s)`) |
| Leopard (§3.2.4) | No equivalent in the documentation cited here |
| Spanner (§3) | `memory` (the default), `postgres`, `mysql`, `sqlite` ([configure OpenFGA](https://openfga.dev/docs/getting-started/setup-openfga/configure-openfga)) |

API names come from [`openfga_service.proto`](https://github.com/openfga/api/blob/main/openfga/v1/openfga_service.proto).

## The running example as a model

The paper's Figure 1 makes owners editors, editors viewers, and viewers of the parent folder viewers of the document (§2.3.1). In OpenFGA's DSL the same rules sit on one line per relation:

```text
model
  schema 1.1

type user

type group
  relations
    define member: [user]

type folder
  relations
    define viewer: [user, group#member]

type doc
  relations
    define parent: [folder]
    define owner: [user]
    define editor: [user, group#member] or owner
    define viewer: [user, group#member] or editor or viewer from parent
```

<Callout kind="note" title="Not run through a validator">

This model uses only constructs that appear on OpenFGA's [configuration language page](https://openfga.dev/docs/configuration-language) and in the maintainers' Google Drive sample ([`model.fga`](https://github.com/openfga/sample-stores/blob/main/stores/gdrive/model.fga)) as of 2026-11-13: `model`, `schema 1.1`, `type`, `relations`, `define`, type restrictions with `group#member`, `or`, and `from`. It has not been run through the OpenFGA CLI or Playground.

</Callout>

The tuples for Anne, Beto and Chen:

| user | relation | object |

| `user:anne` | `owner` | `doc:readme` |

| `user:beto` | `member` | `group:eng` |
| `group:eng#member` | `viewer` | `doc:readme` |

Notice that the model, not a tuple, carries "owners are editors" and "editors are viewers": this is the paper's point that relationships between relations belong in the config, not in one tuple per object (§2.3.1).

## Architecture

What does an OpenFGA deployment consist of? The docs describe servers on one SQL datastore. Each server can keep in-memory caches for Check, and the production guide advises "a small pool of servers with high capacity (memory and CPU cores) instead of a big pool of servers, to increase cache hit ratios" ([running in production](https://openfga.dev/docs/best-practices/running-in-production)). For PostgreSQL a secondary (read replica) datastore can be configured; `HIGHER_CONSISTENCY` reads go to the primary ([configure OpenFGA](https://openfga.dev/docs/getting-started/setup-openfga/configure-openfga)). Consumers of changes call `ReadChanges` and keep the continuation token ([tuple changes](https://openfga.dev/docs/interacting/read-tuple-changes)).

Compare the paper's Figure 2 (§3): `aclservers` fan work out to each other, `watchservers` push a stream, and Leopard keeps a denormalized index. The OpenFGA docs cited here describe none of the three; servers answer from the datastore and their own caches.

## Consistency without zookies

OpenFGA has no zookie. Its docs say so under "Future work": the paper "has a feature called `Zookies`", and OpenFGA "is considering a similar feature in future releases" ([consistency](https://openfga.dev/docs/interacting/consistency)). Instead, Read and the query APIs take one of two values:

| Mode | Behaviour ([consistency docs](https://openfga.dev/docs/interacting/consistency)) | Paper analogue |
| --- | --- | --- |
| `MINIMIZE_LATENCY` (default) | "will serve queries from the cache when possible" | A request without a zookie: "a reasonably recent snapshot" (§2.4.1) |
| `HIGHER_CONSISTENCY` | "will skip the cache and query the database directly" | None exactly; closest is evaluating at the latest snapshot |

Caching is "disabled by default", and then "all queries will have strong consistency regardless of the consistency mode specified" ([consistency](https://openfga.dev/docs/interacting/consistency)). The mode only matters once a cache is turned on.

The docs suggest deciding per request: if the application stores when a resource was last modified, it can compare that time with the cache TTL to choose between the two modes ([consistency](https://openfga.dev/docs/interacting/consistency)). That timestamp plays part of a zookie's role, kept by the application. Cache invalidation flags (`cache-controller-enabled`) also exist and check for recent writes to the store.

## Differences from the paper

- **No zookie.** No consistency token is returned or accepted; two modes plus an off-by-default cache replace it ([consistency](https://openfga.dev/docs/interacting/consistency)). The paper's consistency model rests on zookies (§2.2).
- **Changes are polled.** `ReadChanges` returns a page of tuple changes "sorted by ascending time" with a continuation token ([`openfga_service.proto`](https://github.com/openfga/api/blob/main/openfga/v1/openfga_service.proto)). The paper's Watch is a stream with heartbeat zookies (§2.4.3).
- **Storage.** The paper uses Spanner (§3.1). OpenFGA offers `memory` (default, "Data is lost between server restarts"), PostgreSQL (with an optional read replica), MySQL and SQLite ([configure OpenFGA](https://openfga.dev/docs/getting-started/setup-openfga/configure-openfga)).
- **Conditions.** A type restriction like `[user with non_expired_grant]` makes a tuple count only when a CEL condition holds ([conditions](https://openfga.dev/docs/modeling/conditions)). The paper's tuple (§2.1) has no condition.
- **Contextual tuples.** Tuples sent with a single Check, ListObjects, ListUsers or Expand request, "not persisted in the datastore" ([concepts](https://openfga.dev/docs/concepts), [contextual tuples](https://openfga.dev/docs/interacting/contextual-tuples)).
- **Wildcards.** `[user, user:*]` allows a public grant ([configuration language](https://openfga.dev/docs/configuration-language)); the paper's tuple grammar has no wildcard (§2.1).
- **Stores and model versions.** A store holds "one or more versions of an authorization model" and its tuples; "Store data cannot be shared across stores" ([concepts](https://openfga.dev/docs/concepts)). In the paper, configs are stored in a table keyed by namespace ID, next to a changelog of config updates, and each request is evaluated at one config snapshot timestamp (§3.1.3, §3.2.2). A check in OpenFGA can name the model version it uses.
- **No Leopard.** The docs cited here describe Check caches and iterator caches, not a precomputed set index like Leopard (§3.2.4).
- **List APIs.** `ListObjects`, `StreamedListObjects` and `ListUsers` are outside the paper's API (§2.4).

## Status

As of 2026-11-13: active. Latest release v1.22.1 on 2026-10-28; first release v0.1.0 on 2022-06-10; about 6.1k GitHub stars; Apache-2.0 ([repository](https://github.com/openfga/openfga), [releases](https://github.com/openfga/openfga/releases)).

- June 2022: open sourced ([project post, 2026-01-07](https://openfga.dev/blog/incubation-announcement)).
- 2022: accepted as a CNCF Sandbox project. The sources disagree on the date: CNCF's project page says OpenFGA "was accepted to CNCF on September 14, 2022" and its announcement says September 2022; the project's own post says December 2022 ([CNCF project page](https://www.cncf.io/projects/openfga/), [CNCF](https://www.cncf.io/blog/2025/11/11/openfga-becomes-a-cncf-incubating-project/), [project post](https://openfga.dev/blog/incubation-announcement)).
- 2025-10-28: moved to the Incubating maturity level, according to the CNCF project page.
- 2025-11-11: CNCF announces that its Technical Oversight Committee "has voted to accept OpenFGA as a CNCF incubating project" ([CNCF](https://www.cncf.io/blog/2025/11/11/openfga-becomes-a-cncf-incubating-project/)).
- The managed service is Auth0 FGA ([docs](https://docs.fga.dev/fga)).
