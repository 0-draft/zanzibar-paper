規則の中には、誰が何と関係しているかを問題にしないものがある。「オフィスのネットワークからのみ」「営業時間内のみ」「1,000 未満の送金のみ」「金曜日まで」。どれもリクエストか時計についての事実に依存する。論文にはこれらを書く手段がない。論文の考え方に基づく製品はそれぞれ異なるやり方で手段を加えている。本ページでは、この欠落がなぜあるのか、3 つの製品が何を加えているのか、そしてどんなときに規則をアプリケーション側に置いたほうがよいのかを説明する。

通しの例: Anne、Beto、Chen (`user:anne`、`user:beto`、`user:chen`)、`folder:A` 内のドキュメント `doc:readme`、グループ `group:eng`。Anne は readme を所有し、Beto は eng に属し、eng のメンバーは readme を閲覧し、Chen はフォルダ A を閲覧する。本ページが前提とする関係のパターンは [モデリングのページ](../modeling/) にある。

## タプルが言えないこと

論文のタプルは 4 つの要素だけからなる。その文法は ⟨*object*⟩ ‘#’ ⟨*relation*⟩ ‘@’ ⟨*user*⟩ であり、"the primary keys required to identify a relation tuple are ⟨*namespace*⟩, ⟨*object_id*⟩, ⟨*relation*⟩, and ⟨*user*⟩" (リレーションタプルを識別するのに必要な主キーは ⟨*namespace*⟩、⟨*object_id*⟩、⟨*relation*⟩、⟨*user*⟩ である) (§2.1)。ストレージでは "each row is identified by primary key *(shard ID, object ID, relation, user, commit timestamp)*" (各行は主キー *(シャード ID、オブジェクト ID、関係、ユーザー、コミットタイムスタンプ)* で識別される) (§3.1.1)。論文はそれ以外の列を記述していない。有効期限も、条件も、ユーザーやオブジェクトの属性もない。

リクエストの側も同じく狭い。"A check request specifies a userset, represented by ⟨*object#relation*⟩, a putative user, often represented by an authentication token, and a zookie corresponding to the desired object version" (チェックリクエストは、⟨*object#relation*⟩ で表されるユーザーセット、多くの場合は認証トークンで表される推定上のユーザー、そして目的のオブジェクトバージョンに対応する zookie を指定する) (§2.4.4)。呼び出し元の IP アドレス、時刻、取引の金額のためのフィールドはない。

答えは、格納されたタプルと、zookie が選ぶスナップショットにしか依存できないことに注意したい。それが答えをキャッシュ可能かつ一貫したものにしており、同時にリクエストに対する条件を排除してもいる。

要件の一部は関係に曲げて表せる。有効期限は、時間が来たらタプルを削除するジョブで実現できるが、ジョブが走るまでアクセスが続くという代償を伴う。許可されたネットワークの集合は、アプリケーションが呼び出し元を関係付けるオブジェクトにできる。送金の上限はそうはいかない。金額は誰かが関係を持つオブジェクトではないからである。論文はこうした回避策のどれも論じていない。

## SpiceDB の caveat

SpiceDB は関係に条件を付ける。"Caveats are expressions that can return true or false, and they can be attached (by name) to relationships" (caveat は true または false を返しうる式であり、(名前で) 関係に付けられる)。"a caveat definition includes a name, one or more well-typed parameters, and a CEL expression returning a boolean value" (caveat の定義は、名前、1 つ以上の型付きパラメータ、真偽値を返す CEL 式を含む) ([caveats docs](https://authzed.com/docs/spicedb/concepts/caveats))。CEL は Google の [Common Expression Language](https://github.com/google/cel-spec) である。パラメータの型には `int`、`string`、`duration`、`timestamp`、`list<T>`、`map<T>`、そして SpiceDB 固有の `ipaddress` がある。

Chen がフォルダ A を、そしてそれを通じて readme を閲覧できるのは、オフィスのネットワークからだけだとする。caveat と、それを持ちうる関係は、caveats のページの例にならうと次のようになる。

```text
definition user {}

caveat has_valid_ip(user_ip ipaddress, allowed_range string) {
  user_ip.in_cidr(allowed_range)
}

definition folder {
    relation viewer: user | user with has_valid_ip
    permission view = viewer
}
```

*SpiceDB のスキーマ。2026-11-13 時点の文書化された構文に従っている。バリデータは実行していない。*

`user | user with has_valid_ip` により、同じ関係が caveat なしの関係と caveat 付きの関係の両方を保持できる。"to make the caveat **required**, the `user |` can be removed" (caveat を **必須** にするには `user |` を取り除けばよい) (caveats docs)。関係 `folder:A#viewer@user:chen` は、caveat 名 `has_valid_ip` とそのコンテキストの一部、ここでは `allowed_range` = `10.20.30.0/24` とともに書き込まれる。残りの `user_ip` は、各 `CheckPermission` 呼び出しの `context` フィールドで届く。両方が値を与えた場合、"the values in the Relationship take precedence over those in the CheckPermissionRequest" (Relationship の値が CheckPermissionRequest の値より優先される) (caveats docs)。

### 2 つではなく 3 つの答え

caveat 付きのチェックは、yes でも no でもない形で終わりうる。API は 3 つの結果を定義している。`PERMISSIONSHIP_NO_PERMISSION`、`PERMISSIONSHIP_HAS_PERMISSION`、そして `PERMISSIONSHIP_CONDITIONAL_PERMISSION` である。最後のものは "indicates that the subject has the requested permission on the resource, but only if a caveat condition is met. The `partial_caveat_info` field in the response should contain the missing context fields that must be provided to fully evaluate the caveat" (主体がリソースに対して要求された権限を持つが、caveat の条件が満たされる場合に限ることを示す。レスポンスの `partial_caveat_info` フィールドには、caveat を完全に評価するために与えなければならない欠けたコンテキストのフィールドが入る) ([`permission_service.proto`](https://github.com/authzed/api/blob/main/authzed/api/v1/permission_service.proto))。caveats のページはこれを "required context is missing to determine permissionship" (権限の有無を判定するのに必要なコンテキストが欠けている) と表現している。SpiceDB の内部では、ノード間でディスパッチされる部分問題も、`MEMBER` と `NOT_MEMBER` に並んで同じ第 3 の状態 `CAVEATED_MEMBER` を持つ ([`dispatch.proto`](https://github.com/authzed/spicedb/blob/main/proto/internal/dispatch/v1/dispatch.proto))。

### 期限付きの関係

有効期限は caveat のよくある用途だった。それに関する AuthZed の記事は、多くのユーザーが有効期限だけを求めていたと述べ、組み込みの形を紹介している。関係は省略可能な有効期限を持ち、スキーマは `use expiration` と `with expiration` でそれを有効にする。記事によれば、これは SpiceDB v1.40 で `--enable-experimental-relationship-expiration` の背後にある実験的機能として出荷された ([AuthZed blog, 2025-02-13](https://authzed.com/blog/the-evolution-of-expiration))。

```text
use expiration

definition folder {
    relation viewer: user | user with expiration
    permission view = viewer
}
```

*SpiceDB のスキーマ。2026-11-13 時点の文書化された構文に従っている。バリデータは実行していない。*

[expiring relationships のドキュメント](https://authzed.com/docs/spicedb/concepts/expiring-relationships) は `WriteRelationships` の `OptionalExpiresAt` (RFC 3339) で時刻を設定し、caveat よりこちらを選ぶ理由を 2 つ挙げている。caveat は "requires clients to provide the `now` timestamp" (クライアントが `now` のタイムスタンプを与える必要がある)、そして "expired caveats are not automatically garbage collected" (期限切れの caveat は自動的にはガベージコレクションされない)。期限切れの関係は期限が来た時点で数えられなくなる。ただし、期限前にキャッシュされた部分結果は、そのキャッシュの有効期間内であればまだ返されうる。その行は後でガベージコレクションによって削除される (同じページによれば、デフォルトでは 24 時間後)。このページはバージョンを一度は "v1.40"、一度は "v1.4.0" と書いており、ブログ記事は v1.40 としている。現行リリースでこの機能がまだ実験的とされているかは確認していない。

## OpenFGA の condition

OpenFGA は型制約を通じてタプルに条件を付ける。[conditions のガイド](https://openfga.dev/docs/modeling/conditions) のモデルを、通しの例の型で示す。

```text
model
  schema 1.1

type user

type group
  relations
    define member: [user]

type doc
  relations
    define viewer: [user, group#member, user with non_expired_grant]

condition non_expired_grant(current_time: timestamp, grant_time: timestamp, grant_duration: duration) {
  current_time < grant_time + grant_duration
}
```

*OpenFGA DSL。2026-11-13 時点の文書化された構文に従っている。バリデータは実行していない。*

タプル `user:chen`、`viewer`、`doc:readme` は、condition 名 `non_expired_grant` と、`grant_time` と `grant_duration` からなるコンテキストとともに書き込まれる (ガイドの例では `2023-01-01T00:00:00Z` と `10m`)。各 Check は `current_time` を渡す。ガイドの 2 つのチェックが結果を示している。`00:09:50` では allowed が `true`、`00:10:01` では `false` である。SpiceDB と同様に、格納されたコンテキストとリクエストのコンテキストは "merged together into a single evaluation context" (1 つの評価コンテキストにマージされ)、"persisted context has higher precedence than request context" (永続化されたコンテキストがリクエストのコンテキストより優先される) (conditions のガイド)。

SpiceDB との違いは 2 つある。コンテキストの欠落は第 3 の答えではなくエラーである。"If you don't provide the current_time in the context, the Check and ListObjects operations will fail" (コンテキストで current_time を与えなければ、Check と ListObjects の操作は失敗する)、メッセージは "failed to evaluate relationship condition 'non_expired_grant': context is missing parameters '[current_time]'" である ([OpenFGA blog, 2023-11-06](https://openfga.dev/blog/conditional-tuples-announcement))。そして文書化された上限がある。格納されたコンテキストは "is limited to 32KB in size" (サイズが 32KB に制限される)、サーバーは "a maximum Google CEL expression evaluation cost of 100 (by default)" (Google CEL 式の評価コストの上限 100 (デフォルト)) を課す (conditions のガイド)。同じブログ記事によれば、この機能は OpenFGA 1.4.0-rc1 からである。

### contextual tuple

OpenFGA では、リクエストが自前のタプルを持ち込むこともできる。contextual tuple は "a tuple that can be added to a Check request, and only exists within the context of that particular request" (Check リクエストに追加でき、その特定のリクエストのコンテキスト内にだけ存在するタプル) であり、"are not persisted in the store" (ストアには永続化されない) ([contextual and time-based authorization のガイド](https://openfga.dev/docs/modeling/contextual-time-based-authorization))。このガイドは、許可された IP の範囲と時間帯をオブジェクト (`ip-address-range`、`timeslot`) としてモデル化し、チェックとともに `user:anne` `user` `timeslot:12_13` を送る。支店が許可していない時間帯なら `{"allowed":false}` が返る。

通しの例に当てはめる。フォルダ A はオフィスのネットワークからしか閲覧できないとする。アプリケーションは呼び出し元のアドレスから Chen が `network:office` にいると判断し、それを contextual tuple で伝える。

```text
type network
  relations
    define user: [user]

type folder
  relations
    define allowed_network: [network]
    define viewer: [user, group#member]
    define can_view: viewer and user from allowed_network
```

*OpenFGA DSL。2026-11-13 時点の文書化された構文に従っている。バリデータは実行していない。*

どの辺が格納されていて、どの辺がこのリクエストの間だけ存在するか。

IP の照合がどこで行われたかに注意したい。呼び出しの前に、アプリケーションの中で行われている。contextual tuple が動かすのは事実をリクエストへであって、ロジックをサービスへではない。ガイドはその適用範囲も挙げている。contextual tuple は Check と ListObjects でサポートされ、"are not supported on read, expand and other endpoints" (read、expand、その他のエンドポイントではサポートされない)。また、タプルの変更から構築した検索インデックスをそれと組み合わせるのは "will not be trivial" (簡単ではない)。この記述は 2026-11-13 に取得したガイドによるもので、その後のリリースでサポートが広がっている可能性がある。

## Permify の attribute と rule

Permify は、FusionAuth による買収が 2025-11-20 に発表された ([Permify, 2025-11-20](https://permify.co/post/fusionauth-acquires-permify/)) 製品であり、関係に条件を付けるのではなく、エンティティに属性を格納する。そのスキーマには `attribute` と `rule` があり、ドキュメントは CEL について "we design our schema language based on" (スキーマ言語をそれに基づいて設計している) と述べている ([Permify ABAC docs](https://fusionauth.io/permify-docs/use-cases/abac))。Permify の [モデリングガイド](https://fusionauth.io/permify-docs/getting-started/modeling) にある例:

```text
entity organization {
    relation admin @user
    attribute ip_range string[]
    permission view = check_ip_range(ip_range) or admin
}

rule check_ip_range(ip_range string[]) {
    context.data.ip in ip_range
}
```

*Permify のスキーマ。2026-11-13 時点の文書化された例からコピーした。バリデータは実行していない。*

`ip_range` は組織に格納された属性であり、`context.data.ip` はチェックリクエストとともに届く。金額も同じ形に収まる。ABAC のページの銀行の例には `permission withdraw = check_balance(balance) and owner` がある。`context.data` に値が欠けているときに Permify のチェックが何を返すかは、引用したページには見つからず、ここでは述べない。

## Cedar は Zanzibar をどう分類しているか

Cedar はポリシー言語であり、その論文は RBAC と ABAC をネイティブにサポートするものとして Cedar を説明している。その論文 (Cutler et al., "Cedar: A New Language for Expressive, Fast, Safe, and Analyzable Authorization (Extended Version)", [arXiv:2403.04651v2](https://arxiv.org/abs/2403.04651), 2024-03-08) は関連研究 (§6) で Zanzibar を位置付けている。Zanzibar を "a highly scalable, relationship-based access control (ReBAC) system" (スケーラビリティの高い、関係ベースアクセス制御 (ReBAC) のシステム) と呼び、"Zanzibar supports RBAC and ReBAC with a natural syntax, and with policy validation" (Zanzibar は自然な構文とポリシー検証によって RBAC と ReBAC をサポートする)、"forbid-style policies are supported by expressing one relationship in terms of non-membership in some other relation" (forbid 形式のポリシーは、ある関係を別の関係への非所属によって表現することでサポートされる)、そして "it does not support ABAC, string matching, or search." (ABAC、文字列照合、検索はサポートしない。) と述べている。Cedar についてはその逆として "Cedar natively supports RBAC and ABAC, can encode ReBAC, and supports forbid policies." (Cedar は RBAC と ABAC をネイティブにサポートし、ReBAC をエンコードでき、forbid ポリシーをサポートする。) と説明している。

Cedar の論文が説明しているのは 2019 年の Zanzibar 論文である。その実験では OpenFGA を使っており、OpenFGA を "a recently developed language for specifying relationship-based access control (ReBAC) [43] policies" (関係ベースアクセス制御 (ReBAC) [43] のポリシーを記述するための、最近開発された言語) として紹介している。参考文献 43 は Zanzibar 論文である (§1)。上で見た caveat や condition は製品の拡張であり、この論文の分類には含まれない。その "forbid-style" の文は、[モデリングのページ](../modeling/#ブロックリスト-除外) にある除外のパターンである。

## 規則をアプリケーションに置くべきとき

認可サービスでの条件はただではない。この節は本ページとしての指針であり、論文やベンダーの主張ではない。

- **事実がリクエストの中にしか存在しない。** 送金の金額や呼び出し元の IP は、まずアプリケーションが知るものである。それをコンテキストとして渡すことはできるが、サービスはそれを評価するだけで、格納も一覧も監査もできない。「金額は 1,000 以下」のような規則は、関係のチェックの後でアプリケーションがチェックするほうが簡単なことが多く、認可サービスの答えをキャッシュ可能なまま保てる。
- **一覧とインデックスには格納された事実が必要である。** 論文の Expand は、クライアントが "build efficient search indices for access-controlled content" (アクセス制御されたコンテンツのための効率的な検索インデックスを構築する) ことができるように存在する (§2.4.5)。リクエストに依存する付与は前もってインデックス化できない。OpenFGA のガイドも contextual tuple についてそう述べており、SpiceDB のチェックは呼び出し元がコンテキストを与えるまで `CONDITIONAL_PERMISSION` を返しうる。
- **期限はストレージに置く。** 有効期限は付与の性質であって、リクエストの性質ではない。組み込みの有効期限 (SpiceDB) や格納されたタプルへの condition (OpenFGA) なら、期限を付与の隣に置ける。そこなら「先週の火曜日に readme を閲覧できたのは誰か」という監査からも見える。
- **頻繁に変わる属性は、タプルよりコンテキストのほうが安い。** ユーザーの位置やドキュメントの状態が変わるたびにタプルを書き込むと、変更のたびに二重書き込みが生じる。リクエストのコンテキストに対して評価される条件ならそれを避けられるが、呼び出し元が正しい値を送ると信頼するという代償を伴う。
