Zanzibar は通常、オブジェクトからユーザーへと、1 回に 1 つずつ検索しながらタプルをたどることで Check に答える。ほとんどのデータではこれで速い。しかし何段にも入れ子になったグループでは速くない。Zanzibar はそうしたチェックを、入れ子を事前計算したインデックスである Leopard に任せる。

## 入れ子が遅い理由

共通の例を拡張する。`group:eng` は `group:product` の中にあり、`group:product` は `group:all` の中にあり、readme は `group:all` 全体に共有されているとする。Beto が readme を閲覧できることを知るには、何回の検索が必要か。

図の背後にあるタプルは次のとおりである。

```text
doc:readme#viewer@group:all#member
group:all#member@group:product#member
group:product#member@group:eng#member
group:eng#member@user:beto
```

ステップ *n* はステップ *n* − 1 が返るまで始められないことに注意されたい。論文はこれをポインタ追跡と呼び、"can be expensive when indirect ACLs or groups are deep or wide" (間接 ACL やグループが深い場合や広い場合にはコストが高くなりうる) と述べている (§3.2.3)。広さも問題になる。`group:all` が 100 個の子グループを持っていれば、ステップ 2 は 100 通りに分岐する。そこで次のようになる。"Recursive pointer chasing during check evaluation has difficulty maintaining low latency with groups that are deeply nested or have a large number of child groups. For selected namespaces that exhibit such structure, Zanzibar handles checks using Leopard, a specialized index that supports efficient set computation." (チェック評価中の再帰的なポインタ追跡では、深く入れ子になったグループや多数の子グループを持つグループに対して低レイテンシを維持するのが難しい。そのような構造を示す選ばれた名前空間について、Zanzibar は効率的な集合演算をサポートする専用のインデックスである Leopard を用いてチェックを処理する。) (§3.2.4)

## 2 種類の集合

Leopard は "a collection of named sets using `(T, s, e)` tuples, where *T* is an enum representing the set type and *s* and *e* are 64-bit integers representing the set ID and the element ID" (`(T, s, e)` タプルを用いた名前付き集合の集まり。ここで *T* は集合の種類を表す列挙型、*s* と *e* は集合 ID と要素 ID を表す 64 ビット整数である) を格納する (§3.2.4)。グループのメンバーシップには 2 種類の集合を使う。

- `GROUP2GROUP(s)`：祖先グループ *s* の「*直接または間接の*」("*directly or indirectly*") サブグループであるグループ。
- `MEMBER2GROUP(s)`：ユーザー *s* が「*直接の*」("*direct*") メンバーであるグループ。

例では、これらの集合は何を保持しているか。

<Callout kind="warn" title="グループは自分自身を含むか">
論文は `GROUP2GROUP(s)` を *s* のサブグループであるグループと定義しており、*s* 自身がその集合に含まれるかどうかは述べていない。*G* の直接のメンバーが下のテストに合格するには、*G* が `GROUP2GROUP(G)` に含まれるか、別途処理される必要がある。図は前者を仮定している。これは推測であり、論文が述べていることではない。
</Callout>

## メンバーシップは空でない積集合である

"To evaluate whether user *U* is a member of group *G*, we check whether" (ユーザー *U* がグループ *G* のメンバーであるかを評価するには、次が成り立つかをチェックする) (§3.2.4)

```text
(MEMBER2GROUP(U) ∩ GROUP2GROUP(G)) ≠ ∅
```

つまり、ユーザーが直接追加されたグループのいずれかが *G* の下のどこかにもあるか、ということである。`group:all` について、Beto と Anne ではどうなるか。

## ソート済みリスト上の積集合

積集合はどれほど安いのか。"Index tuples are stored as ordered lists of integers in a structure such as a skip list, thus allowing for efficient union and intersections among sets. For example, evaluating the intersection between two sets, *A* and *B*, requires only O(min(|A|, |B|)) skip-list seeks." (インデックスタプルはスキップリストのような構造の中に整数の順序付きリストとして格納され、それにより集合間の和集合と積集合を効率的に計算できる。たとえば、2 つの集合 *A* と *B* の積集合を評価するのに必要なのは O(min(|A|, |B|)) 回のスキップリストのシークだけである。) (§3.2.4)

## 3 つの部分

"The Leopard system consists of three discrete parts: a serving system capable of consistent and low-latency operations across sets; an offline, periodic index building system; and an online real-time layer capable of continuously updating the serving system as tuple changes occur." (Leopard システムは 3 つの独立した部分から成る。集合をまたいで一貫性のある低レイテンシな操作が可能な提供システム、オフラインで定期的に動くインデックス構築システム、そしてタプルの変更に応じて提供システムを継続的に更新できるオンラインのリアルタイム層である。) (§3.2.4) これらはどうつながっているのか。

- **オフラインのインデックスビルダー。** これは "generates index shards from a snapshot of Zanzibar relation tuples and configs, and replicates the shards globally. It respects userset rewrite rules and recursively expands edges in an ACL graph to form Leopard index tuples." (Zanzibar のリレーションタプルと設定のスナップショットからインデックスのシャードを生成し、シャードをグローバルに複製する。ユーザーセット書き換えルールを尊重し、ACL グラフの辺を再帰的に展開して Leopard のインデックスタプルを形成する。) サーバーは "swap old shards with new ones when they become available" (新しいシャードが利用可能になると古いシャードと入れ替える)。
- **差分層。** オフラインのインデックスだけでは "cannot do so at a fresh and consistent snapshot" (新しく一貫したスナップショットでそれを行うことはできない) ので、サーバーは "an incremental layer that indexes all updates since the offline snapshot" (オフラインのスナップショット以降のすべての更新をインデックス化する差分層) を保持する。各更新は `(T, s, e, t, d)` タプルであり、"where *t* is the timestamp of the update and *d* is a deletion marker" (*t* は更新のタイムスタンプ、*d* は削除マーカーである)。"Updates with timestamps less than or equal to the query timestamp are merged on top of the offline index during query processing." (クエリのタイムスタンプ以下のタイムスタンプを持つ更新は、クエリ処理中にオフラインのインデックスの上に統合される。)
- **供給。** "the Leopard incremental indexer calls Zanzibar’s Watch API to receive a temporally ordered stream of Zanzibar tuple modifications and transforms the updates into a temporally ordered stream of Leopard tuple additions, updates, and deletions." (Leopard の差分インデクサーは Zanzibar の Watch API を呼び出して、時間順に並んだ Zanzibar のタプル変更のストリームを受け取り、その更新を、時間順に並んだ Leopard タプルの追加、更新、削除のストリームに変換する。)

この一覧の引用はすべて §3.2.4 からである。更新はタイムスタンプを持ち、クエリのタイムスタンプまで統合されるので、Leopard の答えは Check の他の部分と同じスナップショットを反映できる。論文が述べる差分層の目的は "To support consistent ACL evaluation" (一貫した ACL 評価をサポートするため) である。

個数は一方の側の祖先の数と他方の側の子孫の数の積なので、深さと広さの両方に応じて増える。これを計算するために、"Generating updates for the GROUP2GROUP tuples requires the incremental indexer to maintain group-to-group membership for denormalizing the effects of a relation tuple update to potentially multiple index updates." (GROUP2GROUP タプルの更新を生成するには、差分インデクサーがグループ間のメンバーシップを保持し、1 つのリレーションタプルの更新の影響を、潜在的に複数のインデックス更新へと非正規化する必要がある。) Google の規模では "In practice, a single Zanzibar tuple addition or deletion may yield potentially tens of thousands of discrete Leopard tuple events." (実際には、Zanzibar のタプルの追加や削除 1 つが、潜在的に数万の個別の Leopard タプルイベントを生むことがある。) (§3.2.4)

削除は図より微妙である。インデックスタプルを削除できるのは、2 つのグループをつなぐ他の経路が残っていない場合に限られる。インデクサーがそれをどう判断するかは、論文に書かれていない。

これは Leopard が例外である理由でもある。他の部分では "Zanzibar avoids storage denormalization and relies only on normalized data (except for the cases described in §3.2.4)" (Zanzibar はストレージの非正規化を避け、正規化されたデータのみに依存する (§3.2.4 で述べた場合を除く)) (§3.2.5)、Leopard は "that exhibit such structure" (そのような構造を示す) 選ばれた名前空間にのみ使われる (§3.2.4)。

## 本番環境での実績

§4.4 より、7 日間について。"The Leopard index is performing 1.56M QPS at the median, or 2.22M QPS at the 99th percentile" (Leopard インデックスは中央値で 1.56M QPS、99 パーセンタイルで 2.22M QPS を処理している)、そして "Leopard servers respond in fewer than 150 μsec at the median, or under 1 msec at the 99th percentile." (Leopard サーバーは中央値で 150 μs 未満、99 パーセンタイルで 1 ms 未満で応答する。) 差分層は "writes roughly 500 index updates per second at the median, and approximately 1.5K updates per second at the 99th percentile." (中央値で毎秒約 500 件、99 パーセンタイルで毎秒約 1.5K 件のインデックス更新を書き込む。) Leopard への呼び出しは、Spanner への呼び出しと同様にヘッジされる (§3.2.7)。
