Warrant は Go で書かれた認可サービスである。README は Warrant を "a relationship based access control (ReBAC) engine (inspired by Google Zanzibar)" (Google Zanzibar に着想を得た、関係ベースのアクセス制御 (ReBAC) エンジン) と説明し、ロールベースや属性ベースのルールも扱えるとしている。関係は `[user:1] is an [editor] of [document:docA]` のように書く ([README](https://github.com/warrant-dev/warrant))。格納された関係は *warrant* と呼ばれる。

WorkOS は 2024 年に Warrant を買収した。日付の 2024-04-23 は、X 上の WorkOS の投稿による ([投稿](https://x.com/WorkOS/status/1782774170146791776))。X はこのサイトの確認ツールにページを返さなかったため、日付は投稿の ID から復号したものであり、投稿の本文 ("Today, we are excited to announce the acquisition of @warrant_dev"、本日、@warrant_dev の買収を発表できることを嬉しく思う) は検索結果でしか確認できていない。WorkOS 自身のブログ記事は見つからなかった。Warrant のウェブサイトは現在 "Warrant —> Now WorkOS FGA" (Warrant は現在 WorkOS FGA) と表示しており ([warrant.dev](https://warrant.dev))、README は WorkOS FGA のドキュメントにリンクしている。

## オブジェクト型で書いた共通の例

論文の図 1 は、所有者を編集者に、編集者を閲覧者に、親フォルダの閲覧者をそのドキュメントの閲覧者にする (§2.3.1)。Warrant では各オブジェクト型がその関係を列挙する。空のオブジェクト `{}` は「直接の warrant のみ」を意味し、`inheritIf` がルールを追加する。

```json
[
  { "type": "group", "relations": { "member": {} } },
  { "type": "folder", "relations": { "viewer": {} } },
  {
    "type": "doc",
    "relations": {
      "parent": {},
      "owner": {},
      "editor": { "inheritIf": "owner" },
      "viewer": {
        "inheritIf": "anyOf",
        "rules": [
          { "inheritIf": "editor" },
          { "inheritIf": "viewer", "ofType": "folder", "withRelation": "parent" }
        ]
      }
    }
  }
]
```

`user` の項目はない。サーバーは最初のデータベースマイグレーションで組み込みの `user` オブジェクト型を作成するからである ([マイグレーション](https://github.com/warrant-dev/warrant/blob/main/migrations/datastore/postgres/000002_create_default_obj_types.up.sql))。`ofType` と `withRelation` を持つルールは、warrant `doc:readme#parent@folder:…` を探し、見つかった各フォルダについて `viewer` をチェックする。これはチェックのコード ([check/service.go](https://github.com/warrant-dev/warrant/blob/main/pkg/authz/check/service.go) の `getMatchingSubjectsBySubjectType`) のとおりである。

<Callout title="コードと照合済み、実行はしていない">
これらのオブジェクト型は、2026-11-13 時点でオープンソースのサーバーが受け付ける構造に従っている。参照したのは [spec.go](https://github.com/warrant-dev/warrant/blob/main/pkg/authz/objecttype/spec.go) の `RelationRule` 型と、[tests/v2/authz.json](https://github.com/warrant-dev/warrant/blob/main/tests/v2/authz.json) などのメンテナーによるテストフィクスチャである。Warrant サーバーには送っていない。Warrant を継続する製品である WorkOS FGA は、設定の仕方が異なる (「現状」を参照)。
</Callout>

共通の例の 5 つの warrant を、`POST /v2/warrants` のボディとして示す。

```json
{ "objectType": "doc", "objectId": "readme", "relation": "owner", "subject": { "objectType": "user", "objectId": "anne" } }
{ "objectType": "group", "objectId": "eng", "relation": "member", "subject": { "objectType": "user", "objectId": "beto" } }
{ "objectType": "doc", "objectId": "readme", "relation": "viewer", "subject": { "objectType": "group", "objectId": "eng", "relation": "member" } }
{ "objectType": "doc", "objectId": "readme", "relation": "parent", "subject": { "objectType": "folder", "objectId": "A" } }
{ "objectType": "folder", "objectId": "A", "relation": "viewer", "subject": { "objectType": "user", "objectId": "chen" } }
```

各人の readme に対する `viewer` 関係を決めるのは、どの warrant とどのルールか。

- 1 つの Go サービスが HTTP API を提供する ([router.go](https://github.com/warrant-dev/warrant/blob/main/pkg/service/router.go))。
- MySQL と PostgreSQL の設定は `dsn` と省略可能な `readerDsn` を受け取る ([config.go](https://github.com/warrant-dev/warrant/blob/main/pkg/config/config.go))。SQLite もサポートされており、"in-memory or file" (インメモリまたはファイル) で使える ([README](https://github.com/warrant-dev/warrant))。
- プールを選ぶ規則は [sql.go](https://github.com/warrant-dev/warrant/blob/main/pkg/database/sql.go) のコメントにある。呼び出しが書き込みの場合、reader がない場合、コンテキストが "contains 'latest' wookie" ('latest' の wookie を含む) 場合、またはサーバー内部のコードが writer の上書きを設定した場合は writer を使い、それ以外は reader を使う。

## 一貫性

Warrant のコードはそのトークンを *wookie* と呼ぶ ([wookie](https://github.com/warrant-dev/warrant/tree/main/pkg/wookie))。`Token` 型は ID、バージョン、タイムスタンプを保持するが、オープンソースのサーバーはそれをクライアントに一度も送らない。warrant サービスはその位置で `nil` を返し、HTTP ハンドラーはそれを無視する ([warrant/service.go](https://github.com/warrant-dev/warrant/blob/main/pkg/authz/warrant/service.go)、[warrant/handlers.go](https://github.com/warrant-dev/warrant/blob/main/pkg/authz/warrant/handlers.go))。サーバーが実際に読むのはリクエストヘッダー `Warrant-Token` であり、挙動を変える値は `latest` の 1 つだけである。

書き込み直後のチェックに対して、`Warrant-Token: latest` は何を変えるのか。

README 自身が、高スループットでの低レイテンシは "requires running Warrant as a distributed service with the use of Warrant-Tokens (also referred to as Zookies in Google Zanzibar)" (Warrant-Token (Google Zanzibar では Zookie とも呼ばれる) を用いて、Warrant を分散サービスとして動かす必要がある) と述べ、"this open source version of Warrant is only capable of handling low-to-moderate throughput" (このオープンソース版の Warrant が処理できるのは低から中程度のスループットだけである) としている ([README](https://github.com/warrant-dev/warrant)、ベンダー自身による記述)。Warrant-Token についてのリンクは、現在は WorkOS FGA の一般的な概要ページにつながっており、そこには Warrant-Token の説明はない。

論文との違いに注意してほしい。zookie は下限を定めるものであり、それによって Zanzibar は "to choose any timestamp fresher than the one encoded in a zookie" (zookie にエンコードされたものより新しい任意のタイムスタンプを選択) でき、ほとんどのチェックを "at a default staleness with already replicated data" (既に複製済みのデータを用いてデフォルトの古さで) 処理できる (§2.2)。`latest` には時点が含まれていない。読み取りをプライマリに移すだけであり、プライマリは最も新しいコピーではあるが、レプリカの利点を手放すことになる。

## 論文との違い

- **スナップショットトークンがない。** オープンソースのサーバーには、上で述べたとおりない。
- **RBAC と ABAC が組み込まれている。** ロール、権限、テナント、料金プラン、機能のための組み込みオブジェクト型と、warrant に付けるポリシー条件がある ([README](https://github.com/warrant-dev/warrant)、[マイグレーション](https://github.com/warrant-dev/warrant/blob/main/migrations/datastore/postgres/000002_create_default_obj_types.up.sql))。
- **クエリ言語。** `GET /v2/query` は、論文の Read と Expand が答えない一覧の問いに答える ([query handlers](https://github.com/warrant-dev/warrant/blob/main/pkg/authz/query/handlers.go))。
- **Watch、Expand、Leopard がない。** また Spanner (§3.1) ではなく、単一の SQL プライマリを使う。

## 現状

- オープンソース: 最初のリリースは 2023-02-23 の v0.1.0。最後のリリースは 2024-06-10 の v1.15.1。最後のコミットは 2025-12-05 の README の変更。アーカイブはされていない。スター数は約 1.3k ([releases](https://github.com/warrant-dev/warrant/releases)、GitHub API、2026-11-13)。
- 会社: WorkOS が買収し、2024-04-23 に X で発表された (上記参照。投稿そのものは読み込めなかった)。
- 製品: WorkOS FGA。現在のドキュメントは Warrant にも Zanzibar にも触れていない。FGA を WorkOS RBAC の拡張として紹介しており、"You configure resource types in the WorkOS Dashboard" (リソース型は WorkOS Dashboard で設定する)、FGA は "can be adopted incrementally, with no data migration or confusing schema DSL" (データ移行もわかりにくいスキーマ DSL もなしに、段階的に導入できる) としている ([WorkOS FGA docs](https://workos.com/docs/fga)、ベンダー自身による記述)。このページのオブジェクト型の JSON はオープンソース版の形式であり、WorkOS FGA の形式ではない。
