Zanzibar の論文は、自らの系譜を [§5 関連研究](../../#s5) で述べている。データモデルについては Multics、UNIX、POSIX ACL、VMS、Taos を、ロールについては RBAC を、RPC API の背後に 1 つの ACL ストアを置くという考え方については Amazon、Google、Microsoft の IAM システムを、同程度の規模のシステムとしては Facebook の TAO を、一貫性の問題については Lamport クロック、Spanner、Chubby、ZooKeeper を引いている。このページは同じ系譜を時系列でたどる。

## 考え方はどのように Zanzibar へつながったか

最初期のマルチユーザーシステムは、誰が何に触れてよいかを決める必要があった。1966 年、Dennis と Van Horn は各計算に *ケイパビリティ* のリストを与えた。ケイパビリティとは、オブジェクトを指し、それに対する権利を付与する、偽造できないトークンである ([Dennis and Van Horn](https://doi.org/10.1145/365230.365252))。Lampson の 1971 年のアクセス行列は、ケイパビリティとアクセス制御リストが同じ表を行ごとに格納するか列ごとに格納するかの違いにすぎないことを示した ([Lampson](https://cseweb.ucsd.edu/classes/fa01/cse221/papers/lampson-protection-osr74.pdf))。Multics は列の見方をとり、すべてのセグメントとディレクトリが ACL を持った ([Saltzer](https://dl.acm.org/doi/10.1145/361011.361067))。Zanzibar も ACL の側にあり、「このオブジェクトに誰が触れられるか」に答える。

その後、オペレーティングシステムはリストをより安価で粗いものにし、のちに再び豊かにした。論文自身がこの流れをたどっている。UNIX の初版では、ファイルのフラグが "whether owner and non-owner can read or write the file" (所有者と所有者以外がファイルを読み書きできるかどうか) を表す。第 4 版では "for owner, group, and others" (所有者、グループ、その他に対する) 読み取り・書き込み・実行のビットがある。POSIX ACL は "an arbitrary list of users and groups" (ユーザーとグループの任意のリスト) を加え、VMS は "supports ACL inheritance for files created within a directory tree" (ディレクトリツリー内に作成されたファイルに対する ACL の継承をサポートする) (§5)。権限、ユーザー、グループ、継承というこの 4 つの語が、Zanzibar のデータモデルがサポートしようとするものである。

1970 年代から、モデルはオブジェクトごとのリストから離れていった。Bell–LaPadula と Biba は、所有者ではなくシステムがラベルによって判定する。Zanzibar は任意アクセス制御であるため、これらは祖先ではなく対比の対象である。ロールベースアクセス制御 (1992 年) は、ユーザーと権限の間にロールを置いた。論文はロールが "are similar to Zanzibar relations" (Zanzibar の関係に似ている) と述べている (§5)。属性ベースの制御は NIST の 2014 年のガイド SP 800-162 で定義され、リクエスト時に属性から判定を計算する。関係ベースの制御は 2007 年に Gates が名付け、2011 年に Fong が形式化したもので、「メンバーである」や「親フォルダである」のような、合成できる関係から判定する ([Fong](https://pages.cpsc.ucalgary.ca/~pwlfong/Pub/codaspy2011.pdf))。論文は ReBAC という語を一度も使っていないが、そのリレーションタプルはまさにそのようなグラフである。

Google で新しかったのは規模と一貫性である。論文は、2019 年 7 月の時点で Zanzibar が "has been in production use for more than 5 years" (5 年以上本番で使われてきた) と述べている (§4)。したがって遅くとも 2014 年には稼働していたが、開始年を示す公開資料はない。Zanzibar は Calendar、Cloud、Drive、Maps、Photos、YouTube に使われている (§1)。論文が比較対象とする TAO は "eventual global consistency" (グローバルな結果整合性) を提供するのに対し、Zanzibar は "external consistency and snapshot reads with bounded staleness" (外部一貫性と有界な古さを伴うスナップショット読み取り) を提供し、それによって「new enemy」問題を防ぐ (§5)。Lamport クロックは、"require explicit participation of all “processes”" (すべての「プロセス」の明示的な参加を必要とする) うえに、Zanzibar のプロセスの一部は "external clients or even human users" (外部のクライアントや、人間のユーザーでさえある) ため、採用されなかった。Chubby は "high volumes of data, efficient range reads, or reads at a client-specified snapshot with bounded staleness" (大量のデータ、効率的な範囲読み取り、クライアントが指定した有界な古さのスナップショットでの読み取り) をサポートせず、ZooKeeper はノードをまたぐ外部一貫性も、有界な古さを伴うスナップショット読み取りも提供しない (§5)。保証を与えたのは Spanner とその TrueTime クロックである ([Spanner, OSDI '12](https://www.usenix.org/system/files/conference/osdi12/osdi12-final-16.pdf))。

論文の公開後、他の人々がこの設計をオープンな形で作り直した。Ory Keto は 2021 年にこの設計を中心に書き直され、SpiceDB、OpenFGA、Permify、Topaz がおよそ 18 か月以内に続いた。同じ時期に、ABAC の系譜にあるポリシーエンジンの OPA と Cedar が成熟し、2023 年に結成された OpenID Foundation の AuthZEN ワーキンググループが、アプリケーションが認可エンジンに判定を問い合わせる方法を標準化した。その Authorization API 1.0 は 2026 年 1 月に OpenID Final Specification となった。各システムの詳細はエコシステムのページにある。

## Zanzibar はどこから何を取り入れたか

論文は、何かの上に構築することと、何かに似ていることの違いに注意を払っている。Zanzibar は Spanner と Leopard の上で動いている。以前の ACL システムの機能をサポートしている。そして RBAC のロールを自らの関係に、Abadi らの "blessings" を自らのタプルに似ているとしている (§5)。

この分かれ方に注目したい。上半分のデータモデルは古い考え方の組み合わせ直しである。論文自身が主張しているのはその統一であり、タプルによるモデル化は "allows us to unify the concepts of ACLs and groups" (ACL とグループの概念を統一できる) (§2.1)。Abadi らはこれらを分けたままにしていた (§5)。下半分は Google の規模でそれを機能させたものである。"external consistency and snapshot reads with bounded staleness" (外部一貫性と有界な古さを伴うスナップショット読み取り) のための Spanner (§5) と、ポインタをたどるだけでは十分速く処理できないグループのための (§3.2.4)、"an indexing system used to optimize operations on large and deeply nested sets" (大規模で深く入れ子になった集合に対する操作を最適化するためのインデックスシステム) である Leopard (§3) である。

<Callout kind="note" title="上に載る IAM">

論文はまた、Google の Cloud IAM システムが "is built as a layer on top of Zanzibar’s ACL storage and evaluation system" (Zanzibar の ACL の格納・評価システムの上の層として構築されている) とも述べている (§5)。関係のストアの上で動くロールベースの製品である。各モデルの関係については [ACL、RBAC、ABAC、ReBAC](../access-control-models/) を参照。

</Callout>
