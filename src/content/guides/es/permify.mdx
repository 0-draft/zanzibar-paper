Permify es un servicio de autorización escrito en Go. Su documentación lo llama "an open-source authorization service for creating fine-grained and scalable authorization systems" (un servicio de autorización de código abierto para crear sistemas de autorización de grano fino y escalables), "inspired by Google's consistent, global authorization system, Google Zanzibar" (inspirado en el sistema de autorización global y consistente de Google, Google Zanzibar) ([documentación de Permify](https://fusionauth.io/permify-docs)). Los tipos de entidad y sus relaciones se describen en el Permify Schema, las relaciones se escriben como tuplas y se pregunta a un servidor, mediante gRPC o HTTP, si un sujeto tiene un permiso.

La adquisición de Permify por FusionAuth se anunció el 2025-11-20 ([anuncio de Permify](https://permify.co/post/fusionauth-acquires-permify/), [anuncio de FusionAuth](https://fusionauth.io/blog/fusionauth-acquires-permify)). FusionAuth llama ahora al producto "FusionAuth FGA by Permify" ([entrada de soporte de FusionAuth](https://fusionauth.io/blog/how-to-get-support-for-fusionauth-fga-permify)), y la documentación está en [fusionauth.io/permify-docs](https://fusionauth.io/permify-docs). La entrada de Permify afirma que "The core Permify project remains open source and will continue to live on GitHub." (El proyecto central de Permify sigue siendo de código abierto y seguirá en GitHub.)

## El artículo y Permify, uno al lado del otro

Cada fila nombra un concepto del artículo y lo más parecido que documenta Permify. Cuando Permify no tiene nada comparable, la celda lo indica.

| En el artículo | En Permify |
| --- | --- |
| Configuración del espacio de nombres (§2.3) | Un bloque `entity` en el Permify Schema, con `relation`, `permission` (o su sinónimo `action`), `attribute` y `rule` ([modeling](https://fusionauth.io/permify-docs/getting-started/modeling)) |
| Tupla de relación `object#relation@user` (§2.1) | Relational tuple `entity#relation@subject`, por ejemplo `doc:readme#owner@user:anne` ([storing data](https://fusionauth.io/permify-docs/getting-started/sync-data)) |
| `_this` | Las tuplas almacenadas de una `relation`; un permiso las incluye nombrando la relación |
| `computed_userset` | Nombrar otra relación u otro permiso de la misma entidad, como `edit` dentro de `view = viewer or edit` |
| `tuple_to_userset` | Recorrido con punto a través de una relación, como `parent.view` |
| Unión, intersección, exclusión | `or`, `and`, `not` |
| Zookie (§2.2, §2.4) | Snap token, el campo `snap_token` ([snap tokens](https://fusionauth.io/permify-docs/operations/snap-tokens)) |
| Check (§2.4.4) | `Permission.Check`, más `BulkCheck` ([service.proto](https://github.com/Permify/permify/blob/master/proto/base/v1/service.proto)) |
| Read (§2.4.1) | `Data.ReadRelationships`, más `ReadAttributes` |
| Write (§2.4.2) | `Data.Write`, `WriteRelationships`, `Delete`, `DeleteRelationships` |
| Watch (§2.4.3) | `Watch.Watch`, un flujo del servidor ([Watch operations](https://fusionauth.io/permify-docs/operations/watch)) |
| Expand (§2.4.5) | `Permission.Expand` |
| Leopard (§3.2.4) | Sin equivalente documentado |
| Spanner (§3.1) | PostgreSQL, o un motor en memoria (el predeterminado en la configuración) ([configuration](https://fusionauth.io/permify-docs/setting-up/configuration)) |

Permify tiene además llamadas de búsqueda que el artículo no describe: `LookupEntity`, `LookupSubject` y `SubjectPermission`.

## El ejemplo de referencia en Permify Schema

La Figura 1 del artículo da a los documentos tres relaciones concéntricas: los propietarios son editores, los editores son lectores y los lectores de la carpeta padre son lectores del documento (§2.3.1). Este es ese modelo con los tipos del ejemplo de referencia, en Permify Schema.

```text
entity user {}

entity group {
    relation member @user
}

entity folder {
    relation viewer @user @group#member

    permission view = viewer
}

entity doc {
    relation parent @folder
    relation owner @user
    relation editor @user @group#member
    relation viewer @user @group#member

    permission edit = owner or editor
    permission view = viewer or edit or parent.view
}
```

`@group#member` permite que una relación contenga un userset: “todos los que son miembros de este grupo”. `parent.view` sigue la relación `parent` hasta la carpeta y evalúa allí el permiso `view` de la carpeta; la documentación afirma que "The same traversal rule applies to both `relation.userset` and `relation.permission`" (la misma regla de recorrido se aplica tanto a `relation.userset` como a `relation.permission`) ([modeling](https://fusionauth.io/permify-docs/getting-started/modeling)).

<Callout title="Contrastado con la documentación, no ejecutado">
Este esquema sigue la sintaxis documentada a 2026-11-13: la [página de modelado](https://fusionauth.io/permify-docs/getting-started/modeling) y el ejemplo de los mantenedores [google-docs-simplified.yaml](https://github.com/Permify/permify/blob/master/assets/example-shapes/google-docs-simplified.yaml). No se ha pasado por el validador de Permify.
</Callout>

El ejemplo de referencia son cinco tuplas:

```text
doc:readme#owner@user:anne
group:eng#member@user:beto
doc:readme#viewer@group:eng#member
doc:readme#parent@folder:A
folder:A#viewer@user:chen
```

## Arquitectura

Las piezas, cada una según la documentación:

- Los servidores escuchan por defecto en el puerto HTTP 3476 y en el puerto gRPC 3478 ([configuration](https://fusionauth.io/permify-docs/setting-up/configuration)). La sección de base de datos acepta URI separadas de `writer` y `reader`.
- Cada pod mantiene una caché [Ristretto](https://github.com/dgraph-io/ristretto) local del proceso con los resultados de las comprobaciones; "there is no shared cache layer" (no hay capa de caché compartida) ([cache](https://fusionauth.io/permify-docs/operations/cache)).
- Con `distributed.enabled`, los pods asignan cada solicitud a un anillo de hashing consistente, de modo que "subsequent API calls with the same hash will retrieve the response from the instance 2, regardless of which instance that API called from" (las llamadas posteriores a la API con el mismo hash obtendrán la respuesta de la instancia 2, sea cual sea la instancia desde la que se llamó a la API). Un circuit breaker detiene las llamadas a la base de datos mientras está caída.
- PostgreSQL almacena las tuplas con MVCC: Permify crea "a separate database snapshot for each write and delete operation" (una instantánea de base de datos separada para cada operación de escritura y de eliminación), y un recolector de basura opcional elimina las versiones antiguas.
- Cada flujo de Watch "opens a long-lived connection with a continuous polling loop against the database" (abre una conexión de larga duración con un bucle de sondeo continuo contra la base de datos) ([Watch operations](https://fusionauth.io/permify-docs/operations/watch)).

## Consistencia

El snap token de Permify cumple el papel del zookie. Un Write lo devuelve; el cliente lo almacena con el recurso y lo devuelve como `snap_token` en las comprobaciones posteriores. La documentación lo describe como "a token that consists of an encoded timestamp" (un token que consiste en una marca de tiempo codificada), que se compara en las comprobaciones de acceso "to ensure that the snapshot of the access control is at least as fresh as the resource timestamp" (para garantizar que la instantánea del control de acceso sea al menos tan reciente como la marca de tiempo del recurso) ([snap tokens](https://fusionauth.io/permify-docs/operations/snap-tokens)). Es la garantía del artículo para una comprobación que lleva un zookie: "a consistent snapshot no earlier than" (una instantánea consistente no anterior al) zookie dado (§2.4.4).

Obsérvese el comportamiento sin token. El artículo permite a Zanzibar "choose a reasonably recent snapshot, possibly offering a lower-latency response" (elegir una instantánea razonablemente reciente, lo que posiblemente ofrezca una respuesta de menor latencia) (§2.4.1). Permify, en cambio, lee el ID de la última transacción de su tabla `transactions` y evalúa en esa instantánea; el resultado se guarda en caché con una clave que contiene ese ID ([snap tokens](https://fusionauth.io/permify-docs/operations/snap-tokens)). La clave de caché es `check_{tenant_id}_{schema_version}:{snapshot_token}:{check_request}` ([cache](https://fusionauth.io/permify-docs/operations/cache)), así que una escritura nueva produce claves nuevas en lugar de invalidar las antiguas.

## Diferencias con el artículo

- **Atributos y reglas.** El Permify Schema añade `attribute` y `rule` para comprobaciones basadas en atributos, como `permission view = check_ip_range(ip_range) or admin` ([modeling](https://fusionauth.io/permify-docs/getting-started/modeling)). Las reescrituras de Zanzibar solo operan sobre tuplas (§2.3.1).
- **Tuplas contextuales.** Las relaciones "dynamically added to permission request operations" (añadidas dinámicamente a las operaciones de solicitud de permisos) se evalúan junto con las almacenadas y nunca se escriben ([contextual tuples](https://fusionauth.io/permify-docs/operations/contextual-tuples)).
- **Inquilinos.** Un servicio `Tenancy` crea, lista y elimina inquilinos ([service.proto](https://github.com/Permify/permify/blob/master/proto/base/v1/service.proto)); el artículo no tiene el concepto de inquilino.
- **Almacenamiento.** PostgreSQL con instantáneas MVCC, en lugar de Spanner, cuyo mecanismo TrueTime asigna una marca de tiempo a cada escritura de ACL (§2.2, §3.1). La caché distribuida funciona "across availability zones (within an AWS region)" (entre zonas de disponibilidad, dentro de una región de AWS) ([cache](https://fusionauth.io/permify-docs/operations/cache)).
- **Sin índice desnormalizado.** El artículo responde a las comprobaciones de grupos profundamente anidados con Leopard (§3.2.4). Permify documenta caché de resultados y hashing consistente, no un índice de conjuntos.
- **Búsquedas.** `LookupEntity` y `LookupSubject` responden a preguntas de “qué recursos” y “qué sujetos” que la API del artículo no cubre.
