Zanzibar 以*關係元組*儲存權限：每一列是一則事實，讀作「此使用者對此物件具有此關係」。本頁其餘內容，包括改寫規則、Check 與 Expand，都是由這些列計算而來。

貫穿全站的範例：Anne、Beto 與 Chen（`user:anne`、`user:beto`、`user:chen`）；位於 `folder:A` 中的文件 `doc:readme`；群組 `group:eng`。Anne 擁有 readme，Beto 屬於 eng，eng 的成員可檢視 readme，Chen 可檢視資料夾 A。

## 文法

論文（§2.1）以四條規則給出文字表示法：

```text
⟨tuple⟩   ::= ⟨object⟩ ‘#’ ⟨relation⟩ ‘@’ ⟨user⟩
⟨object⟩  ::= ⟨namespace⟩ ‘:’ ⟨object_id⟩
⟨user⟩    ::= ⟨user_id⟩ | ⟨userset⟩
⟨userset⟩ ::= ⟨object⟩ ‘#’ ⟨relation⟩
```

元組由三個部分組成。*物件*是命名空間加上 ID，例如 `doc:readme`。*關係*是命名空間所定義的名稱，例如 `owner` 或 `viewer`。*使用者*是單一使用者 ID 或一個*使用者集合*。論文中的使用者 ID 是整數；本站寫成 `user:anne`，讓範例保持易讀。

## 使用者集合：指向群組的元組

第四條文法規則才是關鍵。使用者集合本身是一個物件加上一個關係：`group:eng#member` 的意思是「所有對 `group:eng` 具有 `member` 關係的使用者」。當元組的使用者是使用者集合時，一列就能把某項權限授予一整組使用者，而這組使用者由其他列定義。

請注意，沒有任何一列同時提到 Beto 與 readme。Beto 之所以是檢視者，是因為他屬於第二筆元組所指向的集合。在 eng 中新增一名成員，該成員就能檢視 readme，而 readme 的 ACL 不需任何變更。

同樣的手法可以巢狀使用。群組的成員可以是另一個使用者集合，例如 `group:eng#member@group:sre#member`（一個假設的子團隊，不屬於貫穿全站的範例），成員資格便會沿著元組所描述的層數一路傳遞。論文用一句話說明："a ⟨*userset*⟩ allows ACLs to refer to groups and thus supports representing nested group membership"（⟨*userset*⟩ 讓 ACL 能夠參照群組，從而支援表示巢狀的群組成員資格）（§2.1）。論文也說明了其好處：以元組而非逐物件的 ACL 來建模，"allows us to unify the concepts of ACLs and groups"（讓我們得以統一 ACL 與群組的概念）（§2.1）。群組只是一個其 `member` 關係為 ACL 的物件。

## 將表 1 畫成一張圖

論文的表 1 列出四筆元組範例。將使用者 10 與 11 改名為 Anne 與 Beto，並為 Chen 加上一筆元組後，它們如下：

| 元組 | 讀作 |
| --- | --- |
| `doc:readme#owner@user:anne` | Anne 是 readme 的擁有者 |
| `group:eng#member@user:beto` | Beto 是 eng 的成員 |
| `doc:readme#viewer@group:eng#member` | eng 的成員是 readme 的檢視者 |
| `doc:readme#parent@folder:A#...` | readme 位於資料夾 A 中 |
| `folder:A#viewer@user:chen` | Chen 是資料夾 A 的檢視者（不在表 1 中） |

第四列的 `#...` 是論文用來表示 "a relation that does not affect the semantics of the tuple"（不影響元組語意的關係）的記法（表 1 說明）：該元組指向資料夾本身，而不是其使用者構成的集合。

## 命名空間設定

客戶端在儲存元組之前，會先設定一個*命名空間*，例如 `doc` 或 `folder`（§2.3）。設定中列出該命名空間的關係，每個關係有一個名稱與一個*關係設定*，另外還有儲存參數：分片設定與物件 ID 的編碼方式。

僅憑元組並不能定義有效的 ACL。許多客戶端希望每位編輯者同時也是檢視者。為每個物件的每位編輯者額外儲存一筆 `viewer` 元組，用論文的話來說會 "wasteful and make it hard to make modifications across all objects"（既浪費，也會使跨所有物件的修改變得困難）（§2.3.1）。因此，關係設定可以帶有一條*使用者集合改寫規則*：一個以物件 ID 為輸入、傳回使用者集合運算式樹的函式。

以下是論文的圖 1，原文照錄：

```text
name: "doc"

relation { name: "owner" }

relation {
 name: "editor"
 userset_rewrite {
  union {
   child { _this {} }
   child { computed_userset { relation: "owner" } }
} } }

relation {
 name: "viewer"
 userset_rewrite {
  union {
   child { _this {} }
   child { computed_userset { relation: "editor" } }
   child { tuple_to_userset {
     tupleset { relation: "parent" }
     computed_userset {
       object: $TUPLE_USERSET_OBJECT  # parent folder
       relation: "viewer"
   } } }
} } }
```

> Figure 1: Simple namespace configuration with concentric relations on documents. All owners are editors, and all editors are viewers. Further, viewers of the parent folder are also viewers of the document.
>
> （圖 1：文件上具有同心關係的簡單命名空間設定。所有擁有者都是編輯者，所有編輯者都是檢視者。此外，上層資料夾的檢視者也是該文件的檢視者。）

改寫樹的葉節點分為三種（§2.3.1）：

| 葉節點 | 傳回什麼 | 在圖 1 中 |
| --- | --- | --- |
| `_this` | 儲存的元組中針對此物件與關係的使用者，包括這些元組所指向的使用者集合。關係沒有規則時的預設行為。 | 儲存在 `doc:readme` 上的 `viewer` 元組 |
| `computed_userset` | 同一物件上另一個關係的使用者集合。 | 同一文件上的 `editor`；對 `editor` 而言則是 `owner` |
| `tuple_to_userset` | 從物件讀取一個*元組集合*，再從找到的每一筆元組計算出一個使用者集合。 | 讀取文件的 `parent` 元組，再取每個上層資料夾的 `viewer` |

葉節點以聯集、交集與排除加以組合（§2.3.1）。圖 1 只使用聯集。交集會要求使用者屬於每一個子節點，例如「同時也屬於 eng 的編輯者」；排除則會移除一個集合，例如「封鎖清單以外的檢視者」。這兩個例子是說明用，並非出自論文。

## 將 Check 視為圖搜尋

Check 請求指定一個使用者集合 ⟨*object#relation*⟩ 與一名使用者，詢問該使用者是否屬於該集合（§2.4.4）。在沒有改寫規則的情況下，論文將評估寫成一個遞迴公式（§3.2.3）：若存在元組 ⟨*object#relation@U*⟩，或存在元組 ⟨*object#relation@U′*⟩ 且 U′ 是使用者集合而該使用者屬於 U′，則該使用者屬於 ⟨*object#relation*⟩。論文將這種遞迴稱為 "pointer chasing"（指標追蹤）。改寫規則 "are also translated to boolean expressions as part of check evaluation"（也會在檢查評估過程中轉換為布林運算式）（§3.2.3），因此上面的運算式樹會成為三個分支的 OR。

接下來四張圖要回答的問題：Chen 能否檢視 `doc:readme`？每一格都使用同一張圖，並標出目前分支所讀取的邊。`folder` 的命名空間設定不在論文中；這幾格假設 `folder#viewer` 沒有改寫規則，因此它就只是 `_this`。

## Read 與 Expand

有兩個 API 呼叫從不同的高度檢視同一份資料。

**Read**（§2.4.1）只傳回儲存的元組。請求會指定一個或多個*元組集合*：單一元組鍵，或命名空間中某個物件 ID 或使用者集合的所有元組，並可選擇性地限縮為單一關係。論文明確指出 "Read results only depend on contents of relation tuples and do not reflect userset rewrite rules"（讀取結果僅取決於關係元組的內容，不會反映使用者集合改寫規則）（§2.4.1）。在貫穿全站的範例中，以關係 `viewer` 讀取 `doc:readme` 會傳回一列：

```text
doc:readme#viewer@group:eng#member
```

雖然每位擁有者都是檢視者，結果中卻沒有 Anne；雖然 Chen 能檢視 readme，結果中也沒有他。

**Expand**（§2.4.5）"follows indirect references expressed through userset rewrite rules"（會追蹤透過使用者集合改寫規則所表達的間接參照）。它傳回一棵*使用者集合樹*：葉節點是使用者 ID 或指向其他 ⟨*object#relation*⟩ 配對的使用者集合，中間節點則是聯集、交集或排除。
