Zanzibar 通常以一次一次查找、從物件沿著元組走向使用者的方式回答 Check。對大多數資料而言這很快。但對於巢狀多層的群組則不然，Zanzibar 會把這些檢查交給 Leopard，一個預先計算巢狀關係的索引。

## 為什麼巢狀很慢

擴充貫穿全站的範例。`group:eng` 現在位於 `group:product` 之內，而 `group:product` 又位於 `group:all` 之內，readme 則分享給整個 `group:all`。要得知 Beto 能檢視 readme，需要幾次查找？

圖背後的元組如下：

```text
doc:readme#viewer@group:all#member
group:all#member@group:product#member
group:product#member@group:eng#member
group:eng#member@user:beto
```

請注意，第 *n* 步必須等第 *n* − 1 步傳回之後才能開始。論文將此稱為指標追蹤，並說它 "can be expensive when indirect ACLs or groups are deep or wide"（當間接 ACL 或群組很深或很寬時，成本可能很高）（§3.2.3）。寬也同樣有害：若 `group:all` 擁有一百個子群組，第 2 步就會分岔成一百條路。因此："Recursive pointer chasing during check evaluation has difficulty maintaining low latency with groups that are deeply nested or have a large number of child groups. For selected namespaces that exhibit such structure, Zanzibar handles checks using Leopard, a specialized index that supports efficient set computation."（檢查評估期間的遞迴指標追蹤，對於深層巢狀或擁有大量子群組的群組，難以維持低延遲。對於呈現此類結構的特定命名空間，Zanzibar 使用 Leopard 處理檢查，這是一種支援高效率集合運算的專用索引。）（§3.2.4）

## 兩種集合

Leopard 儲存 "a collection of named sets using `(T, s, e)` tuples, where *T* is an enum representing the set type and *s* and *e* are 64-bit integers representing the set ID and the element ID"（以 `(T, s, e)` 元組表示的一組具名集合，其中 *T* 是代表集合類型的列舉值，*s* 與 *e* 是代表集合 ID 與元素 ID 的 64 位元整數）（§3.2.4）。群組成員資格使用兩種集合類型：

- `GROUP2GROUP(s)`："*directly or indirectly*"（*直接或間接*）為祖先群組 *s* 之子群組的群組。
- `MEMBER2GROUP(s)`：使用者 *s* 為其"*direct*"（*直接*）成員的群組。

在這個範例中，這些集合存放了什麼？

## 成員資格即非空交集

"To evaluate whether user *U* is a member of group *G*, we check whether"（為了評估使用者 *U* 是否為群組 *G* 的成員，我們檢查）（§3.2.4）

```text
(MEMBER2GROUP(U) ∩ GROUP2GROUP(G)) ≠ ∅
```

也就是說：使用者被直接加入的群組中，是否有任何一個也位於 *G* 底下的某處？對 `group:all` 而言，Beto 與 Anne 的結果是什麼？

## 在已排序的串列上取交集

交集的成本有多低？"Index tuples are stored as ordered lists of integers in a structure such as a skip list, thus allowing for efficient union and intersections among sets. For example, evaluating the intersection between two sets, *A* and *B*, requires only O(min(|A|, |B|)) skip-list seeks."（索引元組以有序整數串列的形式，儲存在跳躍串列之類的結構中，因此集合之間的聯集與交集都很有效率。例如，計算兩個集合 *A* 與 *B* 的交集，只需要 O(min(|A|, |B|)) 次跳躍串列搜尋。）（§3.2.4）

## 三個部分

"The Leopard system consists of three discrete parts: a serving system capable of consistent and low-latency operations across sets; an offline, periodic index building system; and an online real-time layer capable of continuously updating the serving system as tuple changes occur."（Leopard 系統由三個獨立的部分組成：一個能對集合進行一致且低延遲操作的服務系統；一個離線、定期執行的索引建構系統；以及一個線上即時層，能在元組發生變更時持續更新服務系統。）（§3.2.4）它們如何連接？

- **離線索引建構器。** 它 "generates index shards from a snapshot of Zanzibar relation tuples and configs, and replicates the shards globally. It respects userset rewrite rules and recursively expands edges in an ACL graph to form Leopard index tuples."（從 Zanzibar 關係元組與設定的快照產生索引分片，並將分片複製到全球。它遵循使用者集合改寫規則，並遞迴展開 ACL 圖中的邊，以形成 Leopard 索引元組。）伺服器 "swap old shards with new ones when they become available"（在新分片可用時，以新分片替換舊分片）。
- **增量層。** 僅靠離線索引 "cannot do so at a fresh and consistent snapshot"（無法在新鮮且一致的快照上做到這一點），因此伺服器維護 "an incremental layer that indexes all updates since the offline snapshot"（一個為離線快照以來所有更新建立索引的增量層），每筆更新都是一個 `(T, s, e, t, d)` 元組，"where *t* is the timestamp of the update and *d* is a deletion marker"（其中 *t* 是更新的時間戳記，*d* 是刪除標記）。"Updates with timestamps less than or equal to the query timestamp are merged on top of the offline index during query processing."（時間戳記小於或等於查詢時間戳記的更新，會在查詢處理期間合併到離線索引之上。）
- **資料饋送。** "the Leopard incremental indexer calls Zanzibar’s Watch API to receive a temporally ordered stream of Zanzibar tuple modifications and transforms the updates into a temporally ordered stream of Leopard tuple additions, updates, and deletions."（Leopard 增量索引器呼叫 Zanzibar 的 Watch API，以接收依時間排序的 Zanzibar 元組修改串流，並將這些更新轉換為依時間排序的 Leopard 元組新增、更新與刪除串流。）

此清單中的所有引文都出自 §3.2.4。由於更新帶有時間戳記，並合併到查詢時間戳記為止，Leopard 的答案可以反映與 Check 其餘部分相同的快照；論文所陳述的增量層用途是 "To support consistent ACL evaluation"（為了支援一致的 ACL 評估）。

數量是一側的祖先數乘以另一側的後代數，因此會隨深度與寬度一起增加。為了計算它，"Generating updates for the GROUP2GROUP tuples requires the incremental indexer to maintain group-to-group membership for denormalizing the effects of a relation tuple update to potentially multiple index updates."（為 GROUP2GROUP 元組產生更新，需要增量索引器維護群組對群組的成員資格，以便將一次關係元組更新的影響反正規化為可能多次的索引更新。）在 Google 的規模下："In practice, a single Zanzibar tuple addition or deletion may yield potentially tens of thousands of discrete Leopard tuple events."（實務上，單一 Zanzibar 元組的新增或刪除，可能產生數萬個獨立的 Leopard 元組事件。）（§3.2.4）

刪除比圖中所示更微妙：只有在沒有其他路徑仍連接兩個群組時，才能移除一筆索引元組。論文並未說明索引器如何判斷這一點。

這也是 Leopard 屬於例外的原因。在其他地方，"Zanzibar avoids storage denormalization and relies only on normalized data (except for the cases described in §3.2.4)"（Zanzibar 避免儲存層的反正規化，只依賴正規化的資料（§3.2.4 所述的情況除外））（§3.2.5），而 Leopard 只用於 "that exhibit such structure"（呈現此類結構的）特定命名空間（§3.2.4）。

## 正式環境中的表現

依 §4.4，在 7 天期間內："The Leopard index is performing 1.56M QPS at the median, or 2.22M QPS at the 99th percentile"（Leopard 索引在中位數時執行 156 萬 QPS，在第 99 百分位時執行 222 萬 QPS），以及 "Leopard servers respond in fewer than 150 μsec at the median, or under 1 msec at the 99th percentile."（Leopard 伺服器在中位數時於 150 微秒內回應，在第 99 百分位時於 1 毫秒內回應。）增量層 "writes roughly 500 index updates per second at the median, and approximately 1.5K updates per second at the 99th percentile."（在中位數時每秒寫入約 500 次索引更新，在第 99 百分位時每秒約 1,500 次更新。）對 Leopard 的呼叫與對 Spanner 的呼叫一樣會進行對沖（§3.2.7）。
