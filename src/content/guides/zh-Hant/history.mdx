Zanzibar 論文在 [§5 相關研究](../../#s5)中描述了它自己的系譜。在資料模型方面，它引用 Multics、UNIX、POSIX ACL、VMS 與 Taos；在角色方面引用 RBAC；在「以 RPC API 提供單一 ACL 儲存」的概念上，引用 Amazon、Google 與 Microsoft 的 IAM 系統；引用 Facebook 的 TAO 作為規模相近的系統；並在一致性問題上引用 Lamport 時鐘、Spanner、Chubby 與 ZooKeeper。本頁依時間順序追溯這些脈絡。

## 這些概念如何通往 Zanzibar

最早的多使用者系統必須決定誰可以碰觸什麼。1966 年，Dennis 與 Van Horn 為每一個計算賦予一份*能力*（capability）清單；能力是不可偽造的權杖，指名一個物件並授予對它的權利（[Dennis and Van Horn](https://doi.org/10.1145/365230.365252)）。Lampson 1971 年的存取矩陣顯示，能力與存取控制清單是儲存同一張表的兩種方式，一種按列、一種按欄（[Lampson](https://cseweb.ucsd.edu/classes/fa01/cse221/papers/lampson-protection-osr74.pdf)）。Multics 採取了按欄的觀點：每個區段與目錄都帶有一份 ACL（[Saltzer](https://dl.acm.org/doi/10.1145/361011.361067)）。Zanzibar 也站在 ACL 這一邊：它回答的是「誰能碰觸這個物件？」。

接著，作業系統讓清單變得更便宜、更粗略，之後又再度變得更豐富。論文自己追溯了這段歷程：在 UNIX 第一版中，檔案旗標表示 "whether owner and non-owner can read or write the file"（擁有者與非擁有者能否讀取或寫入檔案）；到了第四版，則有 "for owner, group, and others"（針對擁有者、群組與其他人）的讀取、寫入與執行位元；POSIX ACL 加入了 "an arbitrary list of users and groups"（任意的使用者與群組清單）；VMS "supports ACL inheritance for files created within a directory tree"（對在目錄樹中建立的檔案支援 ACL 繼承）（§5）。權限、使用者、群組與繼承這四個詞，正是 Zanzibar 的資料模型所要支援的。

從 1970 年代起，模型開始離開逐物件的清單。Bell–LaPadula 與 Biba 讓系統而非擁有者依據標籤做決定；Zanzibar 是自主式（discretionary）的，因此它們是對照，而非祖先。以角色為基礎的存取控制（1992）在使用者與權限之間放入角色；論文說角色 "are similar to Zanzibar relations"（類似於 Zanzibar 的關係）（§5）。以屬性為基礎的控制，由 NIST 2014 年的指南 SP 800-162 定義，在請求當下由屬性計算決策。以關係為基礎的控制，由 Gates 於 2007 年命名、Fong 於 2011 年形式化，依據「是……的成員」或「是……的上層資料夾」之類可以組合的關係做決定（[Fong](https://pages.cpsc.ucalgary.ca/~pwlfong/Pub/codaspy2011.pdf)）。論文從未使用 ReBAC 這個詞，但它的關係元組正是這樣的一張圖。

在 Google 新出現的是規模與一致性。論文說，截至 2019 年 7 月論文發表時，Zanzibar "has been in production use for more than 5 years"（已在正式環境中使用超過 5 年）（§4），因此最遲在 2014 年就已在運作；沒有任何公開來源給出起始年份。它為 Calendar、Cloud、Drive、Maps、Photos 與 YouTube 提供服務（§1）。論文拿來比較的 TAO 提供 "eventual global consistency"（最終的全域一致性），而 Zanzibar 提供 "external consistency and snapshot reads with bounded staleness"（外部一致性與具有有界陳舊度的快照讀取），藉此防範「new enemy」問題（§5）。Lamport 時鐘被排除，因為它們 "require explicit participation of all “processes”"（需要所有「行程」明確參與），而 Zanzibar 的部分「行程」是 "external clients or even human users"（外部客戶端，甚至是人類使用者）。Chubby 不支援 "high volumes of data, efficient range reads, or reads at a client-specified snapshot with bounded staleness"（大量資料、高效率的範圍讀取，或在客戶端指定、具有有界陳舊度的快照上讀取），而 ZooKeeper 既不提供跨節點的外部一致性，也不提供有界陳舊度的快照讀取（§5）。Spanner 及其 TrueTime 時鐘提供了這項保證（[Spanner, OSDI '12](https://www.usenix.org/system/files/conference/osdi12/osdi12-final-16.pdf)）。

論文發表之後，其他人以開放的方式重建了這套設計。Ory Keto 於 2021 年圍繞它重寫，SpiceDB、OpenFGA、Permify 與 Topaz 則在約十八個月內陸續跟進。同一時期，ABAC 一脈的政策引擎 OPA 與 Cedar 逐漸成熟，而 2023 年成立的 OpenID Foundation AuthZEN 工作小組，將應用程式向授權引擎請求決策的方式標準化：其 Authorization API 1.0 於 2026 年 1 月成為 OpenID Final Specification。各系統的細節見生態系頁面。

## Zanzibar 從何處取得了什麼

論文謹慎地區分「建構於某物之上」與「與某物相似」。它執行在 Spanner 與 Leopard 之上；它支援早期 ACL 系統的功能；並稱 RBAC 的角色類似於它的關係，Abadi 等人的 "blessings" 類似於它的元組（§5）。

請注意其中的分野。上半部的資料模型是舊概念的重新組合；論文自己的主張在於統一：以元組建模 "allows us to unify the concepts of ACLs and groups"（讓我們得以統一 ACL 與群組的概念）（§2.1），而 Abadi 等人將兩者分開（§5）。下半部則是讓它能在 Google 的規模下運作的部分：Spanner 提供 "external consistency and snapshot reads with bounded staleness"（外部一致性與具有有界陳舊度的快照讀取）（§5），而 Leopard 是 "an indexing system used to optimize operations on large and deeply nested sets"（一套用於最佳化對大型且深層巢狀集合之操作的索引系統）（§3），用於指標追蹤無法足夠快速處理的群組（§3.2.4）。

<Callout kind="note" title="建構在其上的 IAM">

論文也指出，Google 的 Cloud IAM 系統 "is built as a layer on top of Zanzibar’s ACL storage and evaluation system"（是建構在 Zanzibar 的 ACL 儲存與評估系統之上的一層）（§5）：一個以角色為基礎、執行在關係儲存之上的產品。各模型如何互相搭配，見 [ACL、RBAC、ABAC、ReBAC](../access-control-models/)。

</Callout>
