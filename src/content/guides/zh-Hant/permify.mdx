Permify 是一套以 Go 撰寫的授權服務。其文件稱它為 "an open-source authorization service for creating fine-grained and scalable authorization systems"（一套用於建立細粒度、可擴展授權系統的開源授權服務），"inspired by Google's consistent, global authorization system, Google Zanzibar"（受到 Google 的一致性全球授權系統 Google Zanzibar 啟發）（[Permify docs](https://fusionauth.io/permify-docs)）。你在 Permify Schema 中描述實體型別及其關係，將關係寫成元組，並透過 gRPC 或 HTTP 詢問伺服器某個主體是否具有某項權限。

FusionAuth 於 2025-11-20 收購了 Permify（[Permify 公告](https://permify.co/post/fusionauth-acquires-permify/)、[FusionAuth 公告](https://fusionauth.io/blog/fusionauth-acquires-permify)）。FusionAuth 現在將產品命名為 "FusionAuth FGA by Permify"（[FusionAuth support post](https://fusionauth.io/blog/how-to-get-support-for-fusionauth-fga-permify)），文件則位於 [fusionauth.io/permify-docs](https://fusionauth.io/permify-docs)。Permify 的文章表示 "The core Permify project remains open source and will continue to live on GitHub."（Permify 核心專案仍維持開源，並將繼續存放於 GitHub。）

## 論文與 Permify 並列對照

每一列都列出一個論文中的概念，以及 Permify 所記載的最接近的對應物。Permify 沒有可比較之物時，格中會如此註明。

| 論文中 | Permify 中 |
| --- | --- |
| 命名空間設定（§2.3） | Permify Schema 中的一個 `entity` 區塊，含 `relation`、`permission`（或其同義詞 `action`）、`attribute` 與 `rule`（[modeling](https://fusionauth.io/permify-docs/getting-started/modeling)） |
| 關係元組 `object#relation@user`（§2.1） | Relational tuple `entity#relation@subject`，例如 `doc:readme#owner@user:anne`（[storing data](https://fusionauth.io/permify-docs/getting-started/sync-data)） |
| `_this` | 一個 `relation` 所儲存的元組；權限透過指名該關係將它們納入 |
| `computed_userset` | 指名同一實體的另一個關係或權限，例如 `view = viewer or edit` 中的 `edit` |
| `tuple_to_userset` | 透過某個關係的點號走訪，例如 `parent.view` |
| 聯集、交集、排除 | `or`、`and`、`not` |
| zookie（§2.2、§2.4） | Snap token，即 `snap_token` 欄位（[snap tokens](https://fusionauth.io/permify-docs/operations/snap-tokens)） |
| Check（§2.4.4） | `Permission.Check`，另有 `BulkCheck`（[service.proto](https://github.com/Permify/permify/blob/master/proto/base/v1/service.proto)） |
| Read（§2.4.1） | `Data.ReadRelationships`，另有 `ReadAttributes` |
| Write（§2.4.2） | `Data.Write`、`WriteRelationships`、`Delete`、`DeleteRelationships` |
| Watch（§2.4.3） | `Watch.Watch`，一個伺服器串流（[Watch operations](https://fusionauth.io/permify-docs/operations/watch)） |
| Expand（§2.4.5） | `Permission.Expand` |
| Leopard（§3.2.4） | 文件中未記載對應物 |
| Spanner（§3.1） | PostgreSQL，或記憶體內引擎（設定的預設值）（[configuration](https://fusionauth.io/permify-docs/setting-up/configuration)） |

Permify 還有論文未描述的查找呼叫：`LookupEntity`、`LookupSubject` 與 `SubjectPermission`。

## 以 Permify Schema 表示貫穿全站的範例

論文的圖 1 為文件定義了三個同心關係：擁有者是編輯者，編輯者是檢視者，而上層資料夾的檢視者也是文件的檢視者（§2.3.1）。以下是以 Permify Schema、並使用貫穿全站範例之型別寫成的該模型。

```text
entity user {}

entity group {
    relation member @user
}

entity folder {
    relation viewer @user @group#member

    permission view = viewer
}

entity doc {
    relation parent @folder
    relation owner @user
    relation editor @user @group#member
    relation viewer @user @group#member

    permission edit = owner or editor
    permission view = viewer or edit or parent.view
}
```

`@group#member` 讓關係可以存放使用者集合：「此群組的所有成員」。`parent.view` 沿著 `parent` 關係到達資料夾，並在那裡評估資料夾的 `view` 權限；文件指出 "The same traversal rule applies to both `relation.userset` and `relation.permission`"（相同的走訪規則同時適用於 `relation.userset` 與 `relation.permission`）（[modeling](https://fusionauth.io/permify-docs/getting-started/modeling)）。

<Callout title="已對照文件查核，未實際執行">
此 schema 依照截至 2026-11-13 的文件語法撰寫：[modeling 頁面](https://fusionauth.io/permify-docs/getting-started/modeling)，以及維護者的範例 [google-docs-simplified.yaml](https://github.com/Permify/permify/blob/master/assets/example-shapes/google-docs-simplified.yaml)。它尚未經過 Permify 的驗證器執行。

貫穿全站的範例共有五筆元組：

```text
doc:readme#owner@user:anne
group:eng#member@user:beto
doc:readme#viewer@group:eng#member
doc:readme#parent@folder:A
folder:A#viewer@user:chen
```

各個組成部分，皆出自文件：

- 伺服器預設監聽 HTTP 連接埠 3476 與 gRPC 連接埠 3478（[configuration](https://fusionauth.io/permify-docs/setting-up/configuration)）。資料庫區段接受分開的 `writer` 與 `reader` URI。
- 每個 pod 都保有一個行程本地的 [Ristretto](https://github.com/dgraph-io/ristretto) 快取，存放檢查結果；"there is no shared cache layer"（沒有共用的快取層）（[cache](https://fusionauth.io/permify-docs/operations/cache)）。
- 啟用 `distributed.enabled` 時，pod 會將每個請求雜湊到一致性雜湊環上，因此 "subsequent API calls with the same hash will retrieve the response from the instance 2, regardless of which instance that API called from"（具有相同雜湊值的後續 API 呼叫，無論從哪個實例呼叫，都會從實例 2 取得回應）。斷路器會在資料庫停機期間停止對它的呼叫。
- PostgreSQL 以 MVCC 儲存元組：Permify 會 "a separate database snapshot for each write and delete operation"（為每次寫入與刪除操作建立一個獨立的資料庫快照），而選用的垃圾回收器會刪除舊版本。
- 每條 Watch 串流都會 "opens a long-lived connection with a continuous polling loop against the database"（開啟一條長期連線，並對資料庫進行持續的輪詢迴圈）（[Watch operations](https://fusionauth.io/permify-docs/operations/watch)）。

## 一致性

Permify 的 snap token 扮演 zookie 的角色。Write 會傳回它；客戶端將它與資源一併儲存，並在之後的檢查中以 `snap_token` 送回。文件將它描述為 "a token that consists of an encoded timestamp"（由一個編碼的時間戳記構成的權杖），在存取檢查中加以比較，"to ensure that the snapshot of the access control is at least as fresh as the resource timestamp"（以確保存取控制的快照至少與資源的時間戳記一樣新）（[snap tokens](https://fusionauth.io/permify-docs/operations/snap-tokens)）。這就是論文對攜帶 zookie 之檢查的保證："a consistent snapshot no earlier than"（不早於）給定 zookie 的一致性快照（§2.4.4）。

請注意沒有權杖時的行為。論文讓 Zanzibar "choose a reasonably recent snapshot, possibly offering a lower-latency response"（選擇一個相當新的快照，可能提供延遲更低的回應）（§2.4.1）。Permify 則是從其 `transactions` 表讀取最新交易的 ID，並在該快照上評估；結果以包含該 ID 的鍵快取（[snap tokens](https://fusionauth.io/permify-docs/operations/snap-tokens)）。快取鍵為 `check_{tenant_id}_{schema_version}:{snapshot_token}:{check_request}`（[cache](https://fusionauth.io/permify-docs/operations/cache)），因此新的寫入會產生新的鍵，而不是讓舊的鍵失效。

## 與論文的差異

- **屬性與規則。** Permify Schema 加入了 `attribute` 與 `rule`，用於以屬性為基礎的檢查，例如 `permission view = check_ip_range(ip_range) or admin`（[modeling](https://fusionauth.io/permify-docs/getting-started/modeling)）。Zanzibar 的改寫只作用於元組（§2.3.1）。
- **情境元組。** "dynamically added to permission request operations"（動態加入權限請求操作中）的關係，會與儲存的關係一起評估，且永遠不會被寫入（[contextual tuples](https://fusionauth.io/permify-docs/operations/contextual-tuples)）。
- **租戶。** `Tenancy` 服務可以建立、列出與刪除租戶（[service.proto](https://github.com/Permify/permify/blob/master/proto/base/v1/service.proto)）；論文沒有租戶的概念。
- **儲存。** 使用帶有 MVCC 快照的 PostgreSQL，而非 Spanner；Spanner 的 TrueTime 機制會為每次 ACL 寫入加上時間戳記（§2.2、§3.1）。分散式快取可在 "across availability zones (within an AWS region)"（跨可用區域（在一個 AWS 區域之內））運作（[cache](https://fusionauth.io/permify-docs/operations/cache)）。
- **沒有反正規化索引。** 論文以 Leopard 回答深層巢狀群組的檢查（§3.2.4）。Permify 記載的是結果快取與一致性雜湊，而不是集合索引。
- **查找。** `LookupEntity` 與 `LookupSubject` 回答論文 API 未涵蓋的「哪些資源」與「哪些主體」問題。
